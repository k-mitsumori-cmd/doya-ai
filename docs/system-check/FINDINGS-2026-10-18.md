## 3. 急ぎで確かめたいもの（ユーザーの確認か承認が必要）

### 3-1. Stripe の Webhook がボット判定で止められている恐れ（BILL-087、A）

- 本番は、curl などからのアクセスに 403 を返します。応答ヘッダは x-vercel-mitigated: challenge です。
- /api/stripe/webhook も、Stripe の UA を付けた curl で 403 になりました。
- Stripe から届く通知が同じように止められると、解約や支払い失敗が User.plan に反映されません。
  その場合、解約した人に PRO が残り続けます。
- Vercel のログが残っている期間に、Stripe からの POST は 0 件でした。
  ただし、その期間に課金のイベントが無かっただけの可能性もあり、断定できません。
- 確認方法: Stripe ダッシュボードの Webhook 画面で、直近の配送が 2xx かを見ます。
- 対処案: 403 で失敗していれば、Vercel Firewall で /api/stripe/webhook をボット判定の対象から外します。
- 担当案: ユーザー（Stripe と Vercel の画面操作）。
- 状況: ユーザーから確認の許可をもらいました。ただし Claude in Chrome に接続できず、まだ見られていません。
  Stripe CLI もこの Mac には入っていません。

### 3-2. 本番 DB に未反映の列がある恐れ（DB-017〜DB-020、A）

- 次の列とテーブルは、スキーマにはあります。しかし本番へ反映した記録が見当たりません。
  - aio_prompts.archivedAt
  - aishodan_products.archivedAt
  - promane_time_entries.hourlyRateSnapshot
  - asklink_run と asklink_banner（手動 SQL のファイルもありません）
- 未反映なら、該当テーブルへの問い合わせがすべて P2022 か P2021 で 500 になります。
- 確認方法: 本番 DB で列の有無を読み取りで確かめます。
- 担当案: ユーザーの承認後に、doya-db-push の手順で統括側の担当が実施します。
- 状況: 読み取りでの照合は、ユーザーから許可をもらいました。ただし、このセッションの自動モードの安全判定で止まりました。
  ユーザーが Supabase の SQL エディタで次の読み取り専用 SQL を実行すれば、結果が 5 行かどうかで判断できます。

```sql
SELECT table_name, column_name FROM information_schema.columns
WHERE table_schema = 'public' AND (
  (table_name = 'promane_time_entries' AND column_name = 'hourlyRateSnapshot') OR
  (table_name = 'aio_prompts' AND column_name = 'archivedAt') OR
  (table_name = 'aishodan_products' AND column_name = 'archivedAt'))
UNION ALL
SELECT table_name, '(table)' FROM information_schema.tables
WHERE table_schema = 'public' AND table_name IN ('asklink_run', 'asklink_banner');
```

### 3-3. 運用通知の Cron 5 本が定時に動いていなかった（CRON-002、A、修正済み・反映待ち）

- vercel.json の service-operations の Cron 6 本が、?mode= 付きのパスで登録されていました。
- Vercel Cron は、クエリ文字列付きのパスを定時に発火しません（CLAUDE.md に既知の注意あり）。
- mode が無いときの既定値は watch です。そのため watch だけが動き、
  daily、reviews、cost、weekly、travel の通知が止まっていたと見られます。
- 本番ログでも、実行は 15 分ごとの記録しかなく、reviews の 5 分や daily の 50 分の記録はありませんでした。
- このブランチで、mode ごとに独立したルートを 6 本作り、vercel.json の 6 行を差し替えました。
- 反映には main への取り込みが必要です。順番は統括が決めます。
- 反映後は、各時刻の Cron の実行記録で動作を確かめてください。

### 5-8. ドヤスライドのバケットを非公開にする手順（SEC-062）

コードの準備は、ブランチ chore/doyaslide-private-storage（コミット f3065f0f）に入れました。
このブランチは chore/system-check-20261018 の上に積んであります。

入れた作りは次のとおりです。

- DB と API の応答は変えていません。保存している公開 URL の形も、そのままです。
- 画面は、画像を表示する直前に、公開 URL を /api/doyaslide/files/<パス> に読み替えます。
  パスから毎回同じ文字列が決まるので、編集画面の「保存結果の突き合わせ」は壊れません。
- /api/doyaslide/files/ は、本人のファイル（<userId>/...）だけを返します。
  ログインを確かめ、サービス権限で読み出します。スタイル見本は誰でも見られます。
- サーバーで画像を読む処理（ロゴの合成、書き出し、修正の参照画像）も、サービス権限で読み出します。
- 書き出した PDF と ZIP のダウンロードは、1 時間有効の署名付き URL にしました。
- 新しく作るバケットは非公開にします。既存のバケットの設定は、コードからは変えません。
- 既存データの移し替えは要りません。

設定を変える順番は次のとおりです。

1. chore/doyaslide-private-storage を main に出す（順番は統括が決める）。
2. 本番で、新しいスライド、既存のスライド、プロジェクト一覧のサムネイル、PDF と ZIP の書き出しで画像が出ることを確かめる。
3. Supabase の Storage 設定で、doyaslide バケットを非公開にする（ユーザーの承認が要る）。
4. もう一度 2 を確かめる。あわせて、公開 URL を直接開くと読めなくなったことを確かめる。

戻し方: 表示に問題が出たら、Supabase で doyaslide バケットを公開に戻します。
コードは、公開でも非公開でも動くように作ってあります。
