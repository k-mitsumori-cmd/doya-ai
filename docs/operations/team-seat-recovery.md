# チームの人数変更が保留になった場合

対象は `NEW_PRICING_ROLLOUT` の内側の `/api/pricing/seats`。
席数を先に購入し、その範囲で招待する。アカウント作成自体では請求しない。
この手順書は、価格の作成・料金の公開・実決済・返金の承認を兼ねない。

## 利用者ができる確認

契約の持ち主で「チームの管理」を開く。再読み込み後も、サーバーが保留中の
元の操作IDと人数を返す。別アカウントへ切り替えた画面からは操作できない。

| 表示 | 操作と結果 |
|---|---|
| 処理中 | 「状態を再確認する」でGETする。自動で再請求しない。 |
| 元の変更を再開できる | 元の操作ID・人数・Stripe冪等キーを使う。支払処理が未実行なら日割り請求が起こり得るため、確認画面で確定する。 |
| 元の変更結果を確認する | Stripeへの更新を送らない。元操作の証拠を取得し、条件がそろえば控えとポイントを確定する。 |
| 確認できない／運営の確認が必要 | 招待を保留したまま運営へ引き継ぐ。新しい操作IDでやり直さない。 |

20時間以内の再開も、更新直前に現在の所有契約を読み直す。
元の契約・明細・請求間隔・状態が一致し、現在の人数が元の変更前か変更後の人数でなければ、更新せず保留する。

元の要求をStripeへ送った時刻から20時間が過ぎた場合、再開は行わない。
`mode: check` はサーバーでも更新経路へ戻らない。画面の時計に依存しない。
待機期限の5分は作業担当の引継ぎ用であり、課金の成否や未請求を示さない。

## 運営が読み取りで集める記録

まず対象の環境、会社、現在の契約の持ち主を確かめる。個人情報は権限のある
案件記録に限定し、公開のIssue・一般ログ・Obsidianへ顧客の明細や秘密値を貼らない。

1. `SystemSetting` の `team-seat-operation:v1:<companyId>` を読み、
   操作ID、phase、元の要求、Stripe冪等キー、firstSentAt、pointsAt、tokenを照合する。
   値は変更しない。破損して読めない場合も保留を解除しない。
2. 中央の `findActiveLikeSubscriptions` と同じ所有確認で現在の契約を確かめる。
   メールが同じでもCustomerが複数あるため、最後のCustomer IDだけで結論を出さない。
3. Stripeの同じアカウント・モードで、元の冪等キーを持つ
   `customer.subscription.updated` とリクエスト履歴を確認する。
   変更前と変更後の数量、契約ID、明細ID、価格ID、Customerを照合する。
   同じ数量の別操作や、24時間後にキーが再使用された結果を代用しない。
4. 増席の場合は、そのイベントの請求書と該当する按分明細、支払済み状態を確認する。
   現在の契約に付いている別の請求書や、未払いの請求書は証明にならない。
   既存残高で相殺された支払済み0円請求書も、元操作との対応を確かめる。
5. 控えの人数、招待中と参加済み人数、ポイント台帳の元の月・席番号ごとのキーを読む。
   現在のポイント残高だけで、元の付与が完了したと判断しない。

## 証拠に応じた対応

| 判定 | 対応 |
|---|---|
| 元の変更が成功し、現在の所有契約・人数・支払いも一致 | 持ち主の「元の変更結果を確認する」を使う。サーバーで証拠を取り直し、元のポイントキー・付与月・期限と控えを確定する。イベントID・請求書ID・確認時刻が完了記録に残る。 |
| 増席のAPIが明確な `StripeCardError` を返した | 通常経路は失敗記録を保存して保留を解除する。結果確認は同じ失敗を返し、新しいStripe更新を送らない。通信断や減席のエラーには適用しない。 |
| イベントなし、検索上限、読取失敗、契約変更、人数不一致、未払い | 保留を維持する。イベントが見つからないことを未請求の証明にしない。 |
| 元操作から29日以上、または元のポイント権利の期限切れ | 自動確定しない。Stripeの保存済み記録・請求書・監査記録と突き合わせて、人の判断へ引き継ぐ。 |

自動確認の読み取り上限は、所有契約の検索を除いて8 GET
（契約1回、イベント最大5ページ、請求書最大2件）。上限は未請求を意味しない。

証拠がそろわない状態を強制解除する管理API・スクリプトは用意していない。
返金、補償、別月へのポイント付与、手動での人数修正が必要な場合は、
確認した請求と台帳、変更対象、復旧後の人数・ポイントをまとめる。
その具体的な変更の承認を得てから、別の修正として準備・検証する。
行の削除、operationKeyの交換、leaseの書換えで復旧しない。

## 復旧後の確認

- 完了記録と控えが一致し、保留中の操作がなくなったことを読み取りで確かめる。
- 同じ操作の再送が同じ結果になり、Stripe更新やポイントが増えないことを確認する。
- 招待可能数が持ち主・参加済み・招待中の人数を含めて計算されていることを確認する。
- 発生時刻、原因の確認範囲、判断、関連する記録の所在、未完了事項を案件へ残す。
  実行していない決済・返金・顧客変更を完了と書かない。

検証: `node scripts/security-regression/verify-pricing-seat-reconciliation.cjs`、
`node scripts/security-regression/verify-pricing-team-manage-mounted.cjs`、
`python3 scripts/security-regression/verify-pricing-seat-postgres.py`。
専用DBの実Prisma・台帳を使うが、Stripe・認証・通知は合成で、実決済の証明ではない。
