# バナー月間生成枠の競合防止（2026-09-23）

## 確認した問題

通常生成、URLから生成、テンプレート生成の3経路は同じ `UserServiceSubscription.monthlyUsage` を使っていたが、いずれも上限確認と生成後の加算が別操作だった。同時リクエストでは両方が旧使用数を読めるため、月間枠を超える画像生成が可能だった。DB読取失敗を通してしまう経路や、使用数の更新失敗を無視する経路もあった。

## 修正

- 3経路とも、画像API呼出前に共通のDB条件付き更新で枚数を予約する。条件が競合した場合は最新値を読み直す。上限またはDB障害では画像APIを呼ばない。
- 月替わりの使用数リセットも条件付き更新とし、旧月の値を使った上書きを避ける。無料は1リクエスト最大3枚、有料は最大10枚にサーバーで制限する。
- 画像APIが失敗した場合は予約全数、部分成功なら未生成枚数を戻す。`data:image/` 形式以外を成功枚数に含めない。
- バナーのサービス別加入行がまだない有料アカウントは、アカウントのプランから初期行を作る。管理画面の利用枠表示も同じ補完規則に揃えた。
- 通常生成のリクエスト文言・画像説明などをサーバーログへ直接出さない。

## 検証

- モックDBで無料枠15枚に対する10件の並行予約を確認し、成功5件・上限5件となることを確認。
- 通常生成のルートテストで、DB障害・枠到達時に有料画像APIを呼ばないこと、部分成功・全失敗時の返却枚数を確認。
- 既存のURL安全取得、管理画面利用枠、全セキュリティ回帰テスト、TypeScript、対象ファイルのESLintを通過。

## 残る制約

- プロセスが予約後に強制終了した場合や、返却のDB更新に失敗した場合は、未生成分の枠が残る可能性がある。これは超過生成を防ぐ側に倒した扱いで、長期的には予約IDを持つ台帳と期限切れの照合・回収が必要。
- オフラインの並行テストはモックDB上の確認であり、本番の画像生成や実ユーザーの枠を消費する試験は行わない。
- 20:42:35 JST の汎用エラー通知は別件として `docs/incidents/2026-09-23-200846/report.md` で追跡中。通知の元の `console.error` は未特定で、今回の変更で解消したとは判断しない。
