# Stripe Webhook 運営通知の再送キュー

## 原因と対策

従来はWebhooksの請求・解約通知を待たずに受信記録を `processed` にしていた。送信失敗も通知関数内で握りつぶしたため、Stripeが再送せず通知が欠落し得た。

Webhookの業務処理完了後、`StripeWebhookNotification` にイベントID単位で通知内容を保存する。保存できなければWebhookは500を返す。保存後は受信記録を処理済みにし、通知の即時送信を試みる。送信に失敗しても本体は再処理せず、保留行を5分毎の認証付きCronで再試行する。送信時刻ではなく元イベントの発生時刻を表示する。送信済み行は30日経過後に削除する。

## 検証

- 専用PostgreSQL 17で追加DDLの初回・再適用、11列・主キーと索引2件を確認。
- Prismaで受信記録に紐づく通知の作成と読取を確認。外部通知は実行していない。
- 回帰テストでキュー重複防止、旧トークン拒否、同時送信抑制、通知失敗後のバックオフ・再試行、期限切れリースの回収、Cron認証、Webhookのキュー登録失敗・配送失敗時の応答を確認。
- `npm run build` は回帰テスト・型チェック・Next.jsビルド成功。
- 本番DBでは既知の受信記録で接続先を確認し、通知テーブルが無い状態を読取で確認後、追加DDLのみ先行適用。適用後は11列・2索引・0行。既存テーブルと請求データは変更していない。

## 配送の限界と復旧

Slackが送信を受理した直後にDBの `sent` 更新が失敗すると、再送で通知が重複する可能性がある。欠落防止を優先する少なくとも一回の配送であり、完全な一度限りの配送ではない。送信前にDBキューが作れない場合、StripeはWebhooksを再送する。

コードを前版へ戻すと新テーブルを参照しない。通知行は復旧調査のため残し、テーブル削除は不要。ユーザーのメールなどを含む通知内容はDB内に限り保持し、送信済み行は30日後に削除する。実Stripe配送と実Slack送信の往復試験は未実施。
