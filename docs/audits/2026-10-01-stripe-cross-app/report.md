# 共有Stripeアカウントの契約判定

## 発見した問題

- Webhookの契約判定が `metadata.userId` または任意の非空 `planId` をドヤAI契約として扱っていた。他アプリが同じキーを使うと、Webhookが不要な再試行を行い、IDが一致する場合にはドヤAIの契約権限を書き換えうる。
- `checkout.session.completed` は契約の所属を確認する前に `User.stripeCustomerId` を更新していた。
- メール横断の契約探索、決済後の同期、手動再同期、課金監査にも同じ誤判定が波及し、二重契約判定や請求レポートを汚染しうる。手動再同期は各Stripe一覧の先頭100件だけを読んでいた。

## 修正

- 既知のドヤAI価格ID・プランIDと新規契約の `metadata.app=doya-ai` を使う共通判定を追加。他アプリの明示マーカーは除外。旧 `banner-starter` / `banner-business` 価格も認識する。
- 新しいCheckout SessionとSubscriptionのmetadataにアプリ識別子を設定。Webhookは契約の所属、Customer、ユーザーID、有効状態を確認してから統一課金を更新する。顧客IDのみを先行書き込みしない。
- メール横断の探索、決済同期、手動再同期、課金監査を共通判定に揃えた。手動再同期はページング済みの探索を使用し、選択した契約を再取得して所属と本人・顧客ID・状態を検証する。
- 請求イベントに契約が付く場合、契約のアプリ識別子を価格IDより優先し、別アプリの請求通知を作らない。
- 保存済みの契約IDを使う解約の救済経路と、解約取り消し・契約状態の表示でも契約の所属とユーザーIDを再確認する。旧契約はStripe顧客メールで本人を確認して救済する。
- WebhookのSubscriptionに明示された `userId` がDBに存在しなければ再試行扱いにし、同じCustomerやメールの別ユーザーに権限を付け替えない。`userId` のない旧契約だけ顧客・メール照合へ進む。

## 確認

- 別アプリの `userId` と任意の `planId` を持つ契約、別アプリのCheckout、ドヤAIの正規Checkout、ID不一致、旧価格IDを回帰テストに追加。保存済みIDを使う解約・再開・状態表示も別アプリと別ユーザーのケースで確認する。
- `npm run build` に含まれる全セキュリティ回帰テスト、TypeScript、Next.jsビルドで検証する。
- 実際のStripeイベント配信と課金・通知送信は試験していない。本番反映後のCI・Vercel・ヘルスチェックは別途記録する。

## 残る境界

識別マーカーがない旧契約は、既知の価格IDまたは正確に一致する旧プランIDで救済する。別アプリが同じ価格ID・プランIDを再利用した旧データは、metadataだけで完全には区別できない。新しい契約はアプリ識別マーカーを優先する。
