# ドヤ面接官：終了・評価と進行操作の整合性確認

## 修正と検証

- 質問進行：通常進行・深掘り・スキップの全保存経路で、実施中かつ読み取り時の状態が維持されている場合だけ更新する。終了状態や新しい質問番号を遅れた処理が上書きしない。コミット `84727a41`。
- 同意：初回同意だけを保存し、再送時に実施中の状態・同意日時・同意元・応募者名を変更しない。初回保存と終了・応募者情報変更が重なった場合も古い要求を拒否する。
- 録音保存：保存先だけを更新し、評価の実行権を表す更新日時を変えない。保存時にも同意・開始・状態・保管期限・組織の録音設定を確認する。
- 担当者操作：終了・終了取消・応募者情報変更は、読み取り時点の状態・更新日時と組織スコープを保存条件に含める。終了時は新しい発話、取消時は発話の存在、情報変更時は面接開始・期限切れを再確認する。
- 回帰テスト：`verify-mensetsu-advance-atomic.cjs` 14項目、`verify-mensetsu-consent-atomic.cjs` 11項目。どちらも修正前コードで不具合が検出され、修正後コードで成功することを確認。DB・AIはモックであり、本番の実面接を実行した結果ではない。
- 追加テスト：`verify-mensetsu-manager-state-atomic.cjs` 21項目、`verify-mensetsu-recording-lease.cjs` 12項目。録音保存のテストは共通の評価処理と組み合わせ、評価結果の保存・失敗時の状態復旧を確認する。DB・ストレージ・AIはモック。
- 録音保存SQL：実際のPATCHから取得したパラメータ付きSQLを、接続先DBの `READ ONLY` トランザクション内で `EXPLAIN`（`ANALYZE`なし）し、構文・列・条件式を確認した。データ更新は行っていない。
- 発話と評価確定：発話保存・終了通知・評価確定が同じセッション行をロックする。評価確定時に発話IDを照合し、追加発話がある結果は破棄して同じ実行権で再評価する。3回または再試行開始まで180秒を超えた場合は古い結果を保存せず、`completed` に戻して再試行できるようにする。
- 発話と評価の回帰テスト：`verify-mensetsu-transcript-finalization.cjs` 17項目。追加発話・入力取得前の到着・再試行上限・再評価失敗・評価確定後の書き込み拒否・同時採番・最初の発話と終了の競合・空の終了後の自動評価・ロールバック・保管期限・未開始・ログ分類を確認する。DB行ロックとAIはモック。
- 評価開始前の期限確認：初回の確認後に参照例・発話を読み込む間に保管期限を過ぎた場合も、AI呼び出し直前で再確認し、期限後に新しい評価を送信しない。
- 自動評価ログ：状態の競合・再試行待ちの409は警告として記録し、`console.error` を監視する要対応通知へ流さない。評価処理の例外はエラーとして記録し、通知対象を維持する。
- 発話ロックSQL：実際の発話保存APIから取得したロックSQLを、接続先DBの `READ ONLY` トランザクション内で `EXPLAIN`（`ANALYZE`なし）して構文・テーブル・列を確認した。データ変更や実際の行ロック取得は行っていない。
- 全体検証：各修正後に `DOYA_BUILD_NO_WEBPACK_CACHE=1 npm run build` を実行する。GitHub CIと本番デプロイは別途確認する。ビルド成功だけで本番反映済み・全サービスに問題なしとは判定しない。

## クライアント送信の追加再現（2026-10-06）

実際の `useRealtimeInterview.ts` を読み込み、Reactのref・コールバックとfetchを模擬して、以下の動作を再現した。音声接続・AI・本番DBは使用していない。旧コードに対する再現コマンドは `DOYA_TEST_BASELINE=<旧コードの配置先> node docs/audits/2026-10-06-mensetsu-lifecycle/probe-client-delivery.cjs`。この診断の成功は不具合の再現を意味し、合格判定用のCIには含めない。以下はコミット `0e3d0e8a` 時点での現象で、先のサーバー側修正だけでは解消しない。現在の修正状況は次項に記載する。

1. 51件を終了直前に送信し、サーバーが50件保存すると、残る1件をメモリー内に保持したまま終了APIを送る。終了処理はキュー全体を排出しない。
2. 定期送信が応答待ちの間に終了すると、既存の送信を待たずに終了APIを送る。
3. 最後の発話保存が503となると、再送キューへ戻すものの終了APIを送って完了画面へ進む。
4. `pagehide` の終了通知には `aborted:true` だけが含まれ、未送信回答は含まれない。

修正では送信を直列化し、終了前に既存送信と50件ずつのキュー排出を待つ。通信断・応答紛失後の再送を安全にするには、発話ごとの安定したIDを用いてサーバーの重複保存も防ぐ必要がある。離脱通知はブラウザの本文・送信容量上限を考慮し、未保存回答がある状態を保存完了と扱わない。端末の強制終了や完全な通信断時の到達は、sendBeaconだけでは保証できない。

## クライアント送信の追加修正（検証中・未反映）

- 発話確定時にランダムIDを割り当て、サーバーではセッションIDとのハッシュを主キーとして利用する。同一発話の再送は追加保存せず、確認済み件数として返す。再送で内容・時刻・話者・質問番号を変更する要求は拒否する。IDのない旧クライアントは従来の追記動作を保つ。DBスキーマ変更はない。
- 送信処理を直列化し、送信中の回答も確認までメモリーに保持する。終了時は進行中の送信と50件ずつの排出を待つ。確認できない保存件数・HTTPエラー・通信断は成功扱いにしない。終了通知も応答を確認し、未確認時は再試行ボタンへ案内する。発話送信・終了確認には各15秒の中断を設ける。
- `pagehide` の終了要求は未確認発話を含む。終了APIは発話保存を完了してから状態変更と評価を行い、部分保存・保存拒否・形式不正時には終了しない。同時の定期送信・終了通知の再送は同じIDで重複を防ぐ。
- Beaconの容量内（最大50発話・60,000バイト）なら回答を含めた終了を送る。容量超過時は送信可能な回答だけを追記し、回答抜きで終了を送らない。全回答が保存されたとは判定せず、サーバーの中断回収に委ねる。強制終了・完全な通信断・容量超過では全発話の到達は保証できず、永続的な再送保管はまだ実装していない。
- 回帰テスト：再送保存21項目、実クライアントの送信18項目、終了通知の回答保存を含む評価確定21項目。React・通信・DB・AIはモック。実ブラウザの離脱・ネットワーク試験と本番反映は別の確認が必要。

## 短い回答の欠落と再送時刻（追加修正・未反映）

- 同じ「はい」を5秒以内に2回手入力すると、2回目の回答が保存されない現象を実クライアント処理で再現した。文面と時間を使った重複判定を廃止し、Realtimeの `item_id` と `content_index` が同じ通知だけを除外する。`response.done` の保険経路も同じ音声項目・内容パートを識別する。手入力・識別子がない通知・別の音声項目は同じ文面でも保存する。
- [公式のイベント仕様](https://platform.openai.com/docs/api-reference/realtime-beta-server-events/response/output_audio_transcript/done?lang=node.js)で音声項目と内容パートの識別子を照合した。独立した `event_id` では、文字起こし完了とレスポンス完了の保険経路を同一発話として照合できない。
- 発話の相対開始時刻を発話確定時に保持する。再接続で面接開始のrefが変わっても、未確認回答の同じIDと時刻を再送し、サーバーで内容不一致として拒否されることを防ぐ。
- クライアント回帰テストは25項目。手入力の同文回答・別音声項目の同文回答・保険経路の重複・別内容パート・識別子なしを検証する。実際の `start()` と `dc.onmessage` を通信・マイク・WebRTCのモックで実行し、新旧のイベント名と `response.done` が連携することも確認した。AI接続や実マイクの試験ではない。旧コードでは手入力の2件目欠落と再接続時刻の不一致を検出する。

## 未登録の録音ファイルの削除漏れ（再現済み・未修正）

`node docs/audits/2026-10-06-mensetsu-lifecycle/probe-orphan-recording.cjs` は、実際の録音PATCHと削除cronを模擬DB・ストレージで実行する。アップロード済みの録音が存在しても保管期限切れの保存先登録は409で拒否され、DBの `recordingPath` はNULLのままになる。cronは候補者情報・発話を削除する一方、NULLのパスを辿れず音声オブジェクトを残し、`remaining:0` を返すことを再現した。この診断の成功は不具合の再現を意味し、CIの合格判定には含めない。本番の過去発生有無を調べた結果ではない。

次の修正では登録済みパスに依存しないストレージ上の録音追跡と再試行を用意する必要がある。署名付きアップロードの有効期間が残る間に一度削除しても、後からファイルを置かれる可能性を考慮する。保存未完了のパスを既存の `recordingPath` に入れるだけでは、録音ありと表示して未保存ファイルを案内するため不十分。

## 録音アップロードの独立追跡（追加修正・未反映）

- URL発行後、応募者へURLを返す前にセッションの同意・開始・実施中・録音設定・URL期限・保管期限を行ロック内で再確認し、削除タスクを永続化する。ロック待ちで期限を過ぎた要求も拒否する。録音完了の `recordingPath` と評価用の更新日時は変更しない。追跡保存に失敗した場合、署名URLは返さない。
- 既存の `SystemSetting` をサービス専用キー `mensetsu-recording-purge:v1:<sessionId>` で利用する。セッションごとに1件だけ保持し、再発行や同時発行で最終確認の時刻が短くならないようセッション行で直列化する。DBスキーマ変更はない。
- cronは登録済みの `recordingPath` とは別に追跡タスクを処理し、失敗時は5分後の再試行対象として残す。10分の実行権は処理中断後に再取得できる。タスクの形式・セッションID・正規のパスを確認し、別セッションや別ファイルのパスは削除しない。各実行の新規着手を60秒以内に制限し、残るタスクを次回へ保持する。
- 署名URL発行後3時間の最終確認を設け、保管期限を跨いだ後に遅れてアップロードされた音声も再度削除する。保管期限が延びた場合や確認できない場合は削除を延期する。タスクの最終削除も取得した実行権と一致する場合だけ行う。
- `recordingPurge` に処理数・確定数・延期数・失敗数・追跡中の件数を返し、個人情報の未処理件数だけを見て録音まで全処理済みと誤判定しない。失敗は安全な集計値のエラーログに残す。
- `verify-mensetsu-recording-purge-queue.cjs` 26項目。録音POST/PATCH、独立追跡処理、実際のcronを通信・DB・ストレージのモックで連携させ、URLを返す前の追跡、登録拒否後の削除、遅延アップロード、状態変更・期限切れ、並行取得、失敗時再試行、パス検証を確認した。
- 既存ファイルの読み取り調査：手元の接続先で対象バケットの取得は404だった。これは本番の空バケットや過去の未登録音声0件を証明しない。実際の本番設定と既存ストレージの照合・必要な既存分の追跡登録は未完了。新しい追跡処理だけで過去分も修復済みとは扱わない。
