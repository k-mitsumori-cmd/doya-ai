# 管理者ログインのセッショントークン

同じ管理者のログインが同じ秒に重なると、JWTの内容と署名が同一になり、2回目のセッション保存がtokenの一意制約で失敗して500になっていました。隔離DBで、正しい認証情報への応答が200・500になることを再現しています。

トークン生成時に、ログインごとに新しいUUIDをJWT ID（jti）へ設定します。署名と24時間の有効期限は既存の方式を使います。保存済みのJWTにはjtiを必須とせず、DBセッションと管理者の有効状態を確認する既存の検証を通します。

セッション保持数は既存実装の最新4件です。コード内の「最大5つ」という説明を、現在の処理に合わせて修正しました。

CIの `verify-admin-session-nonce-postgres.py` は、アプリの秘密値を継承せず、私有PostgreSQLにスキーマだけを作って10群を検査します。実際の認証関数・ログインPOST・bcrypt・jsonwebtoken・Prismaを使い、JWTの時計、Cookieの境界とCAPTCHA応答は合成です。

- 同じ秒に20個の異なるJWT IDを生成でき、署名・管理者情報・24時間の期限が正しいこと。
- 同じ秒の2回ログインと4件の並行ログインで、有効な異なるセッションを保存できること。
- 6件の並行ログイン後も保持数が4件であり、保持された新セッションを検証できること。
- jtiのない既存形式のJWTも、DBセッションがあれば使用できること。
- 誤パスワード、入力不足、CAPTCHA拒否、期限切れ・署名不正・未保存トークン、無効な管理者を拒否すること。

実アカウントでのログイン・CAPTCHA・パスワード復旧は、この隔離検査の受入範囲に含みません。パスワードや本番の認証設定は、この修正で変更しません。
