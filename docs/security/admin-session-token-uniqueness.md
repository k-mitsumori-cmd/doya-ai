# 管理者ログインのセッション作成

同じ管理者のログインが同じ秒に重なると、同じJWTが生成され、2回目の保存がtokenの一意制約で失敗して500になっていました。また、並行ログインのセッション整理が競合し、4件残すはずのセッションが3件へ減ることをクラウドの私有DBで再現しました。

ログインごとに新しいUUIDをJWT ID（jti）へ設定します。セッション保存では現在のAdminUser行をロックして有効状態を確認し、作成・古いセッションの整理・最終ログイン時刻の更新を同じトランザクションで確定します。保持対象は作成時刻とIDの順で決めます。

保持数は既存実装の最新4件です。コード内の「最大5つ」という説明を、実装に合わせて修正しました。署名と24時間の有効期限は既存の方式を使います。保存済みJWTにはjtiを必須とせず、DBセッションと管理者の有効状態を確認します。

CIの `verify-admin-session-nonce-postgres.py` はアプリの秘密値を継承せず、私有PostgreSQLへスキーマだけを作って13群を検査します。実際の認証関数・ログインPOST・bcrypt・jsonwebtoken・Prismaを使い、JWTの時計、Cookieの境界とCAPTCHA応答は合成です。

- 同じ秒に20個の異なるJWT IDを生成でき、署名・管理者情報・24時間の期限が正しいこと。
- 同じ秒の2回ログインと4件の並行ログインで、異なる有効セッションを保存できること。
- 6件の並行ログインと、それを6回繰り返した後も、保持数が4件で新しいセッションが残ること。
- DB更新を意図的に失敗させたとき、作成・整理・最終ログイン時刻が一緒に戻り、既存セッションが残ること。
- jtiのない既存JWTを検証でき、誤パスワード・入力不足・CAPTCHA拒否・期限切れ・署名不正・未保存トークン・無効な管理者を拒否すること。

トランザクションの範囲はセッション作成・整理・最終ログイン時刻です。成功試行ログとCookieの設定は、ログインAPIの既存処理で行います。実アカウントでのログイン・CAPTCHA・パスワード復旧は、この隔離検査の受入範囲に含みません。
