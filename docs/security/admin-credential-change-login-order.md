# 管理者の認証情報更新と実行中ログイン

パスワードを検証した後、セッションを保存する前に認証情報が更新されると、更新前の情報でログインが成立する競合を防ぎます。

## 再現と変更

私有PostgreSQLで管理者行をロックし、本人用のパスワード再設定を先に、旧パスワードを検証済みのログインを後に待機させました。従来は再設定が既存セッションを削除した後に、旧ログインが有効なセッションを作成しました。

セッション作成の既存トランザクション内で、管理者の有効状態と、ログイン時に検証したpasswordHash・totpEnabled・totpSecretを現在値と比較します。差があればセッションを作成せず、ログインは通常の認証失敗と同じ401を返します。認証情報を含まない失敗理由を記録します。削除済みの管理者でも記録時に外部キーエラーを起こさないよう、管理者IDは設定しません。

プロフィール変更や並行ログインによるupdatedAtの変更は拒否理由にしません。セッションの作成・最大4件への整理・最終ログイン時刻の更新は、従来どおり同じトランザクションです。

## 検証範囲

新しい私有DB試験は、実際のログインPOST・bcrypt・JWT・TOTP・Prismaを使う10条件です。再設定とログインの両順序、2FA有効化、秘密鍵更新、プロフィール更新、無効化、削除、検証済み情報の欠落、別管理者への影響、通常の2FA成功・失敗を確認します。更新前の本番ソースでは最初の条件が失敗することも確認しました。

`python3 scripts/security-regression/verify-admin-credential-fence-postgres.py`で実行します。CIでは既存の管理者セッション試験と別の私有DBを起動し、結果と停止記録を保存します。認証情報変更は合成データの更新処理です。本人用再設定の実コードによる順序試験は、別のローカル証拠として確認しています。

Cookie・CAPTCHA・時計は合成境界です。実HTTPサーバー、本番管理者の正認証、本人による実パスワード再設定は、この試験の検証範囲に含みません。本番の認証情報・顧客データ、スキーマ、環境変数は変更しません。既存セッションの失効は認証情報更新側の処理に依存し、この変更は検証済み情報が古くなった実行中ログインからの新規発行を防ぎます。
