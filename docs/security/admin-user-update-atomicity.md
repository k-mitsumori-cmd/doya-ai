# 管理者ユーザー更新の原子性

管理者の PATCH /api/admin/users は、プラン・役割・全サービス同期・指定した利用カウンタ・返却する更新後情報を同じ Serializable トランザクションで扱う。後段の SQL が失敗した場合はすべて変更前に戻す。入力検証はトランザクション開始前に行う。

統一課金同期は既存の syncUnifiedBilling を保持する。呼び出し元がトランザクションを持つ場合は syncUnifiedBillingInTransaction を使い、独立した確定や入れ子のトランザクションを作らない。通知キュー登録・手動付与保護・全サービスと所有 HR 組織の同期は既存と同じ。外部 Stripe や通知送信は行わない。

P2034 は最大3回で再試行し、各失敗した試行の SQL はロールバックする。既存 withRetry の接続再試行を維持する。

## 検証

既存 CI 登録の verify-admin-user-input-postgres.py が起動する私有 PostgreSQL と実 Prisma/実ルートを使用する。元の入力検証・認証26条件を保持し、後段 SQL 障害3条件、正常な複合保存3条件、P2034 後の再試行成功と上限到達の2条件を追加した計34条件。SQL 障害は私有 DB の trigger、P2034 は実トランザクション内部の制御された例外で再現する。管理者認証と接続再試行境界は合成。実管理者・本番顧客更新・実 Stripe 課金の合格とは区別する。

既存の管理者課金10条件は、同期が呼び出し元の TX を受け取ることを確認して維持する。
