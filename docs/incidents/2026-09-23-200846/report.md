# 2026-09-23 20:08 JST 本番サーバー通知の調査

## 確認できた事実

- 20:08:46–47 JST に同じ汎用文面の通知が短時間に複数届いた。
- 該当時間帯の本番リクエストログには `GET /api/persona/images/:id` が15件あり、すべて HTTP 200。うち11件に `[runtime-alert] delivery` の記録がある。通知は9つの実行インスタンスに分散していた。
- 同時間帯の関連するペルソナAPIも HTTP 200 または 204。確認した範囲では関数の失敗・画像取得失敗は見つからなかった。
- Vercel のエラーレベルログは0件。通知記録に元の `console.error` の引数や呼び出し元が含まれず、発火原因は特定できていない。汎用文面だけで利用者やデータへの影響がないとは断定できない。

## 対処

- `console.error` 通知に安全な照合指紋を付け、既存の `SystemSetting` を使う発生箇所単位の原子的な10分間の共有上限を追加。実行インスタンスをまたいだ通知の多重送信を抑え、DBの上限キーがエラー本文ごとに増えないようにする。
- スタックから呼び出し元が取得できない場合は従来と同じ発生箇所単位でまとめる。通知が失敗した場合は、その通知が取得した共有上限だけを解放する。DBの共有上限が使えない場合も通知自体は継続する。
- 通知と安全な診断ログには照合指紋を記録し、エラー本文・画像ID・リクエスト内容は含めない。

## 検証と残る確認

- オフライン回帰テストでは、30インスタンスの同時取得で1件だけが上限を取得し、11インスタンスからの汎用エラー通知も1件に収まった。
- 実際のPostgreSQLで無効な既存値、競合、期限内の再取得を確認した。
- 元の `console.error` の原因はログに残っていないため未解明。次に同じ通知が出た場合は、照合指紋、デプロイID、同時刻の関数ログ、利用者操作と画像表示を確認する。復旧確認までは「解消済み」と案内しない。
