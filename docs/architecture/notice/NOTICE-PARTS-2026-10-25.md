# ドヤくんの知らせ（ポップアップと案内）の設計

2026-10-25 作成。ブランチは `feat/notice-parts` です。見本は https://claude.ai/artifact/3n7KxcEPrxB1rVbB81sfjj にあります。

## 1. 目的

ツールの中で出す知らせを、1つの部品にそろえます。アプリのように、楽しく分かりやすく使えるようにします（ユーザーの依頼、2026-10-25）。

## 2. 共通の決まり

- 同時に出すのは1つだけです。順番は、エラー → 承認待ち → 新機能 → ヒントです。
- エラーは、表示中の承認待ち・新機能・ヒントより先に出します。表示中のものは列に戻します。
- 作業中（入力中・POST の通信中・ツールが `holdBusy()` した間）は出しません。エラーだけは作業中でも出します。
- once の知らせは、閉じたら二度と出しません。見た記録は、ユーザーごとに端末へ残します（DB には書きません）。
- 767px 以下は下からのシートで、下へ引くと閉じます。768px 以上は右下のカードです。
- ドヤくんの絵を添えます。ドヤくんの表示オフ（DoyaPowerFx の mascot）なら文字だけにします。
- 動きを減らす設定では動かしません。絵文字は使いません。
- 外部の広告（HubSpot の CTA）とは別物です。広告を隠す仕組みは `ServicePopupGuard` のままです。

ツールから使うときは、次のように書きます。

```tsx
const notice = useNotice()
notice.notify({ title: '保存しました', action: { label: '取り消す', onClick: undo } })
notice.push({ id: 'quote:first', kind: 'hint', once: true, pose: 'point', eyebrow: 'ヒント', title: '…' })
notice.tip(buttonEl, { id: 'quote:rate', title: '粗利率', body: '…', once: true })
const release = notice.holdBusy() // 長い生成の間。終わったら release()
```

旗が off のとき、`useNotice()` はどれも何もしません。ツールの側で旗を見る必要はありません。

## 5. 次の候補（他社の使いやすさの調べ、メインの提案リスト 9章）

画面に関わるものを、知らせの共通部品のあとの候補として並べます。順番の考え方は次の3つです。

- 今ある部品（知らせ・エージェント・シェル）の上に足せるものを先にします。
- 本物のエージェントを広げる前に、安全の決まりを入れます。
- DB の表を新しく作るものは、設計を先に出して、実装はあとにします。

| 順 | 項目 | 他社調べの順位 | 大きさ | 先に要るもの | 担当の案 |
|---|---|---|---|---|---|
| 1 | エージェントの1回あたりのドヤパワーの上限 | 10 | 小 | 確認の画面（済み）・runner | 実行の仕組みの担当と画面（UI リニューアル） |
| 2 | スケルトン表示と先読み | — | 小〜中 | シェル（済み） | UI リニューアル |
| 3 | 3案の横並び | 4 | 中 | 各ツールの生成 API が複数の案を返すこと | UI リニューアル（バナー・コピー・スライドから） |
| 4 | 版の履歴と復元 | 5 | 中〜大 | 版を残す DB の表 | 設計を先に出す。スライド・見積もりから |
| 5 | エージェントの再生 | 7 | 中 | 作戦と実行の記録をサーバーに残すこと（今は端末だけ） | 実行の仕組みの担当と画面 |

## 6. 残りの2つの設計（案。実装の前にメインと統括の確認を取る）

### 6.1 保存の「取り消す」（提案リスト (14) の残り。見積書は 2026-10-26 に入れた）

- 何をするか: 保存のトーストに「取り消す」を出し、押すと、保存の直前の内容に戻します。
- 戻し方: 画面は、保存の直前に送った内容と、サーバーから読んだ保存前の内容を覚えておきます。「取り消す」で、保存前の内容をもう一度同じ API（見積書なら `PATCH /api/quote/documents/{id}`）に送ります。新しい API や表は作りません。
- 決まり:
  - 取り消せるのは、トーストが出ているあいだ（5秒）だけです。
  - 取り消しのあいだに別の保存が入ったら、取り消しはやめて「ほかの変更があったので、取り消せませんでした」と出します（版の番号か更新日時で見分ける）。
  - 送信・承認・PDF の確定など、外に出る操作は取り消しの対象にしません。
- 最初に入れるツール: 見積書の編集（`src/lib/quote/use-document-detail.ts` の save）。保存の前の内容をフックの中で持つ形にし、画面（`documents/[id]/page.tsx`）はトーストのボタンを出すだけにします。
- 他社調べの「版の履歴と復元」（§5 の 4）が入ったら、取り消しは版の復元の1つとして作り直します。

### 6.2 前のツールの成果物を次で使う（提案リスト (7)）

- 何をするか: ツールを切り替えたとき、直前のツールで作ったものを、次のツールで使えるよう提案します。例: 見積書を作ったあとにスライドへ移ると、「さっき作った見積書を、提案スライドの材料に使いますか」と出します。
- 受け渡しの形: 画面どうしでは、成果物そのものを渡しません。渡すのは、種類・id・表示名・開く URL の4つです（`{ kind: 'quote' | 'persona' | ..., id, title, href }`）。端末に、直近の3件だけを残します（ユーザーごとのキー。DB には書きません）。
- 次のツールの側: 受け取れる種類を表にしておき（例: スライドは quote・persona・seo の記事を受け取れる）、合うものがあるときだけ、知らせのカードを出します。「使う」を押すと、そのツールの入力欄に、id を付けた URL（例 `/doyaslide/new?from=quote:<id>`）で開きます。中身は、次のツールのサーバーが、本人の組織の範囲で読み直します（IDOR を避けるため、画面から中身を渡さない）。
- 最初に入れる組み合わせ: 見積書 → スライド（経営ホームのエージェントと同じ流れ）。スライドの作成画面が `from` を読んで、題と詳しい内容を下書きに入れるところは、スライドの担当と分けて作ります。
- 入れる前に要る確認: スライドのサーバーが見積書を読むときの権限（組織が別のときは読まない）を、統括に確かめてもらいます。

#### 6.2 の決まり（統括の権限の点検、2026-10-26）

方向（画面から中身を渡さず、サーバーが読み直す）は、このままでよいと確かめてもらいました。実装の前に、次を守ります。この経路では RLS を使わないので、Prisma の where が唯一の防御です。

1. 見積書の組織の決め方: slug なしの `getQuoteContext()` は使いません（既定の組織に切り替わり、ほかの組織の見積書が静かに 404 になるため）。`src/lib/quote/access.ts` に `loadQuoteForHandoff(userId, documentId)` を1つ作ります。`quoteDocument.findFirst({ where: { id, organization: { members: { some: { userId, status: 'ACTIVE', role: { in: 有効なロール } } } } }, select: … })` で、id とメンバーシップを1回で引きます。スライドの側に、見積書の判定を写しません。
2. 404 と 400: ほかの組織・存在しない・削除済みは、どれも同じ 404 と同じ文言にします。id は cuid の形と長さを確かめます。kind は許可の一覧（quote・persona・seo）で照らし、外れたら 400 にします。
3. 読む列: title、clientCompany、明細（品名・数量・単価）、合計、status だけです。発行者（インボイス番号・角印）、confirmedBy、notes は渡しません。
4. 下書き（draft）の見積書: 材料にしてよいですが、金額には「未確定」と付けます。
5. 画面から来る title と href は信じません。スライドの題や下書きには、サーバーで読み直した doc.title を使います。href はサーバーで取りに行かず（SSRF の経路を作らない）、referenceUrl にも使いません。画面で router.push に使うときは、同じオリジンの相対パスに限ります（`/` で始まり、`//` や `\` で始まらず、許可したパスの接頭辞に合う）。
6. 外の検索に出さない: `src/app/api/doyaslide/structure/route.ts` は、project.title と customBrief の先頭200字を、SerpAPI の検索語にしています。見積書から作ったプロジェクトでは、Web 検索をしないか、見積書の中身を検索語に使わない別の入力で渡します。題には顧客名を入れません。
7. 写しの扱い: 見積書の中身は、ユーザー単位のスライドのプロジェクトに写しとして残ります。組織を抜けたあとも本人には残り、ほかのメンバーには見えません。この扱いでよいとします（統括の判断）。
8. 端末の履歴: localStorage の title には顧客名が入りえるので、ログアウトしたときに消します。
9. サーバーで読むのは、本人が「材料にする」を押してからです。知らせのカードを出すだけの段階では、見積書を読みません。
10. 回帰の検査 `scripts/security-regression/verify-doyaslide-quote-handoff.cjs` を足し、`run.cjs` に登録します。確かめることは次のとおりです。
    - ほかの組織や INVITED なら 404 で、Gemini と SerpAPI を1回も呼ばない
    - where に id と組織の両方がある
    - 削除済みならプロジェクトを作らず、ドヤパワーも減らない
    - 不正な id なら 400
    - 画面の title と href を使わない
    - 検索語に顧客名と金額が入らない
    - select に発行者と confirmedBy が入らない
    - draft の扱い
    - href の確かめ方（`//evil`、`https:`、`/\evil`、`javascript:` を拒む）

6.2 は、スライドのサーバー（`src/app/api/doyaslide/*`）と見積書の読み方（`src/lib/quote/access.ts`）に手を入れます。始める前に、触るファイルをメインに伝えます。

#### 6.2 の実装（2026-10-26）

- サーバー: ブランチ `feat/quote-slide-handoff`（main から）。`loadQuoteForHandoff`、`POST /api/doyaslide/projects/from-quote`、構成づくりの Web 検索を内部の目印で止める分岐、回帰の検査 `verify-doyaslide-quote-handoff.cjs`。
- 画面: ブランチ `feat/notice-handoff-ui`（`feat/notice-parts` から）。
  - 見積書の詳細を開いたとき、種類・id・時刻だけを端末に残す（3件まで・1日以内だけ使う）。表示名は残さない（顧客名が入りえるため。セキュリティの点検 2026-10-26）。
  - スライドの作成・一覧を開いたとき、知らせのカードで「材料にしますか」を1回だけ出す。押したときだけサーバーに `{ kind, id }` を送る。
  - 移る先は、サーバーが返した id から作り、形を確かめる。
  - ログアウトのとき、記録を消す。
