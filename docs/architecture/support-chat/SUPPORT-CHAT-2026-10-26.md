# 気軽に聞けるチャット（サポートチャット）の設計

2026-10-26 作成。ブランチは `claude/doya-support-chat-cbad90` です。
旗 `SUPPORT_CHAT_ROLLOUT` の内側で作ります。既定は off で、off のあいだは今の動きを変えません。

## 1. 目的

ユーザーの依頼（2026-10-26）の要約です。

- 画面の右下に、気軽に問い合わせできるチャットのボタンを置く。
- 使い方が分からない、という質問には、AI が分かりやすく答える。
- クレームや、運営者にしか対応できないことは、運営者に Slack で確実に伝える。

ヘルプ専用の画面とよくある質問の表は、まだありません。使い方の答えの材料は、次の3つです。

- `src/lib/services.ts` の各ツールの `name`・`description`・`features`・`href`・`status`
- `src/lib/unified-plan.ts` の料金とトライアルの日数
- `reference/11-billing-spec.md`（課金の正本。答えには書き写さず、料金ページへのリンクで返す）

料金は新しいプランの準備中です（`claude/doya-new-pricing-dd27ff`、旗 `NEW_PRICING_ROLLOUT`）。
そのため、チャットは金額を文章に直書きしません。`unified-plan.ts` の値を読み、料金ページへのリンクを添えます。

## 3. 全体の流れ

```
右下のボタン → チャットの画面
  ├ よくある質問の候補を押す / 自由に書く
  ├ 判定（決まりで分ける。AI より先に行う）
  │   ├ 運営が必ず対応するもの → 「運営に伝える」の画面へ（AI は答えない）
  │   └ 使い方・料金・ドヤAIの説明 → AI の答え（根拠のリンクつき）
  │         └ 分からないとき → 無理に答えず「運営に伝える」を出す
  └ 運営に伝える → 受付番号と返信の目安を表示 → Slack（要対応）と ServiceFeedback に残す
```

## 4. 答えの範囲と、運営へ渡す条件

### 4.1 AI が答えてよいこと

- ドヤAI の説明（何ができるか、どのツールを使えばよいか）
- 各ツールの使い方（`services.ts` の説明と機能の一覧の範囲）
- 料金の仕組みの説明（無料とプロの違い、ドヤパワーの考え方）。金額はリンク先の料金ページを正とする

### 4.2 AI が答えないこと（必ず運営へ渡す）

決まり（`src/lib/support-chat/rules.ts`）で、AI より先に判定します。AI の答えにも同じ判定をかけます。

| 分類 | 例 | Slack の重さ |
|---|---|---|
| クレーム | 「ひどい」「返金して」「対応が悪い」 | 要対応 |
| 支払い | 請求、領収書、カード、二重の請求、返金 | 要対応 |
| 不具合 | 動かない、エラーが出る、画面が真っ白 | 要対応 |
| 解約 | 解約したい、やめたい、退会 | 要対応 |
| データの削除 | データを消してほしい、個人情報の削除 | 要対応 |
| 個別の相談 | 見積り、請求書払い、導入の相談、契約の変更 | 要対応 |
| 情報の漏れ・不正 | 乗っ取り、不正利用、情報が漏れた | 緊急（@channel） |

- 判定は言葉の一覧で行います。迷ったら運営に渡す側に倒します。
- 運営に渡すときも、利用者を待たせないよう「受付番号」と「返信の目安」をすぐ出します。

### 4.3 分からないときは無理に答えない

- 材料の中に当てはまるものが無ければ、「この内容は運営からお答えします」と返し、「運営に伝える」を出します。
- 答えには、根拠にしたツールのページか料金ページのリンクを必ず添えます。リンクが付けられない答えは出しません。

## 6. AI に使うモデルと見込み額

### 6.1 モデル（2026-10-26 ユーザー決定: Claude Haiku 5.5）

答えは Claude Haiku 5.5（`claude-haiku-5-5`）で作ります。実装は `src/lib/support-chat/claude.ts` です。

決めた経緯は次のとおりです。

1. 最初は gemini-2.5-flash を提案し、ユーザーが承認した（1回 約0.3円）。
2. 開発ルールに「製品の中の AI も、頭を使う所は Opus、軽い所は Sonnet 以下」とあることが分かった（Obsidian の開発ルール）。
3. A（Gemini）・B（Claude Sonnet 5.5）・C（Claude Haiku 5.5）を示し、ユーザーが C を選んだ。答えは資料から選んで短く書く軽い仕事なので、一番軽いモデルで足りる。

呼び方の決まり（claude-api スキルの資料「Migrating to Claude Haiku 5.5」で確かめた）:

- モデル ID は日付の付かない `claude-haiku-5-5`。`SUPPORT_CHAT_AI_MODEL` で変えられる。
- 公式の SDK `@anthropic-ai/sdk` を使う（0.133.0 に固定。2週間以上前に出た版）。キーは今の `ANTHROPIC_API_KEY`。
- Haiku 5.5 は `temperature` などを送ると 400 になるので送らない。思考は止めず、`effort: 'low'` にする（資料のおすすめ）。
- 前置き（prefill）は 400 なので、JSON は構造化出力（`output_config.format`）で受け取る。
- 思考の分も `max_tokens` に入るので、上限を 1,500 にした。
- 安全の判定で断られた（`stop_reason: refusal`）ときは「分からない」にし、「運営に伝える」を出す。
- 失敗したら再試行は1回だけで、そのあとはモックの答えにする。

### 6.2 Gemini を残すか

Gemini（`gemini.ts`）は、自動の切り替え先にはしません。1回の質問で有料の AI を2つ呼ぶと、見込み額が読めなくなるからです。
Claude が長く止まったときに人の判断で替えられるよう、`SUPPORT_CHAT_AI=gemini` で選べる予備として残します（承認済みの gemini-2.5-flash）。
`SUPPORT_CHAT_AI=mock` にすると、有料の AI を呼ばずにモックで答えます。

### 6.3 1回あたりの見込み

| 項目 | 見込み |
|---|---|
| 入力 | 約3,000トークン（資料 2,000 ＋ 会話 1,000） |
| 出力 | 約400トークン（思考を含めて最大 1,500） |
| Claude Haiku 5.5 の単価（入力 10万トークン以下） | 入力 100万トークンあたり 0.10ドル、出力 0.50ドル |
| 1回あたり | 約0.0005ドル（約0.08円）。思考が増えて出力が 1,500 になっても 約0.001ドル（約0.15円） |

単価は claude-api スキルの料金表（2026-10-06 時点）です。1ドル=150円で計算しました。

### 6.4 1日の上限と月の見込み

- 全体の1日の上限は 800回（`SUPPORT_CHAT_AI_DAILY_LIMIT`）にします。上限に達したら AI を止め、モックの答えと「運営に伝える」だけにします。
- 上限まで毎日使われた場合で、1日 約0.4ドル（約60円）、月 約12ドル（約1,800円）です。
- 1人1日30回の上限があるので、1人が使える額は 1日 約2.4円までです。

### 6.5 ドヤパワーを使わない理由

- 問い合わせは、利用者の困りごとを減らすためのもので、成果物を作る機能ではない。
- 不具合や支払いの相談でポイントが減ると、苦情が増える。
- 1回 約0.3円で、ドヤパワーの1ポイント（原価 3〜4円の想定）より安い。数える手間の方が高くつく。

## 7. 運営からの返信と履歴のための表（最終の形）

2026-10-26 にユーザーが「本番の DB に足す」と決めました。足すのは次の2つの表です。

| 表 | 中身 |
|---|---|
| `support_ticket`（SupportTicket） | 受付1件。受付番号・分類・状態・重さ・画面・伏せ字のあとの内容・端末の情報・返信の希望・担当・初めて返信した時刻・最後に返信した時刻・利用者が読んだ時刻・完了の時刻・満足度 |
| `support_message`（SupportMessage） | 受付ごとのやり取り。利用者・AI・運営の発言、AI の根拠のリンク、返信を書いた管理者、メールを送った時刻 |

- モデルは `prisma/schema.prisma` の末尾、User には `supportTickets SupportTicket[]` を足しました。
- 本番に流す SQL は `prisma/manual-migrations/2026-10-26-support-chat.sql` です。`prisma migrate diff` の出力をもとに、`IF NOT EXISTS` をつけて何度流しても同じ結果になる形にしました。
- 追加だけで、既存の表とデータは変えません。元に戻すときは、この2つの表を消します（この2つの表のデータだけが消えます）。
- SQL はコードの反映より前に流します。流す前に旗を on にしても、受付は `ServiceFeedback`（serviceId `support`）に残るので、取りこぼしません（`src/lib/support-chat/store.ts`）。
- 反映の手順は `doya-db-push` スキルに従います。流すのは、統括のセッションでユーザーの承認を得たあとです。

### 7.1 返信の流れ

1. 利用者が「運営に伝える」で送る → `support_ticket` と `support_message` に残り、Slack に「要対応」が届く。
2. 運営は管理画面の「サポートの受付」（`/admin/support`、Slack のリンクから開ける）で読み、返信を書く。
3. 返信は `support_message`（role staff）に残り、状態は「お返事待ち」になる。利用者が返信を希望していれば、Resend でメールも送る。
4. 利用者のチャットのボタンに未読の数が出る。「お問い合わせの履歴」から返信を読み、続けて書ける（Slack に「追記」が届く）。
5. メールのリンク（`/home?support=受付番号`）から開くと、チャットがその受付を開く。

## 10. まだ良くない点

- AI が使えないときのモックの答えは、材料の言葉と合わない聞き方には「運営に伝える」を出すことが多い。
- 本物の AI（Claude Haiku 5.5）の答えは、まだ一度も実際には確かめていない。手元から本番のキーを使う操作は止められたので、反映のあと preview で1回試す。
- 運営の返信は管理画面から書く。Slack のスレッドからはまだ書けない。
- 祝日を営業時間外として扱っていない。
- スクリーンショットはまだ添付できない。
- 知らせの部品（UIリニューアルのセッション）の見た目のトークンを、CSS に書き写している。部品の側にトークンが1つにまとまったら、そちらを読むように直す。
- 画面の確認は、確認ページ（ログインなし・モック）で 1280px と 375px を見ただけです。ログインした状態の本物の枠と、知らせのカードが同時に出たときの重なりは、preview にしてから確かめます。

## 11. 次の改善の提案

- よくある質問の材料を、ツールごとに3〜5件ずつ足す（今はツールの説明と機能の一覧だけ）。
- 届いた質問のうち「分からない」で返したものを数え、材料を足す順番を決める（M4）。
- 運営の返信を Slack のスレッドから書けるようにする（Slack のアプリが要るので、設定はユーザーの承認のあと）。
- 不具合のときに、画面の操作の履歴（直近のクリックとページの移動）を添える。
- 解約の相談では、解約の前に「一時停止」や「無料プランへの切り替え」を案内する（運営の方針を決めてから）。
- 祝日の表を持ち、営業時間外の判定に入れる。
