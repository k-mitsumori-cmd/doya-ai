# 退会から90日後に、作成したデータを消す処理の設計

作成日: 2026-11-22。状態: 設計のみ。コードは書いていない。本番の DB・Cron・旗には触っていない。

## 1. 決まったこと

2026-11-22 に三森さんが、退会したあと、作成したデータを消すまでの期間を90日と決めた。
退会の API（`POST /api/account/delete`、api-contract.md 3.7）は、退会の時点で User を匿名化し、`deletedAt` と `anonymizedAt` を入れる。
この資料は、その90日後に、ユーザーが作成したデータを消す処理を設計する。

## 2. 何を消すか

対象は、`deletedAt` が90日より前のユーザー（以下「期限切れのユーザー」）に紐づく、次のデータ。

| 区分 | 内容 | 扱い |
|---|---|---|
| ツールのデータ | 各ツールの表のうち、持ち主が `userId` で決まるもの（生成物、プロジェクト、履歴など） | 消す |
| アップロードと生成物のファイル | Supabase Storage に置いた画像・音声・動画・資料 | 消す。表の行より先に、ファイルを消す |
| 退会のあとに残った個人情報 | ツールの組織のメンバー表（kintai、sfa、shodan、aio、mensetsu、quote、aishodan、income、expense）の、メールの控え | 消す、または匿名にする（実装時に表ごとに決める） |
| 会社（AccountCompany）の行とドヤパワーの台帳 | `AccountCompany.userId` は必須で、匿名化したユーザーを指したまま残っている | 決定待ち（5 章） |

「どの表が userId で持ち主を決めるか」の一覧は、実装のときに `prisma/schema.prisma` から機械的に作り、この資料へ書き足す。人の記憶では作らない。
表の数が多い（103モデル）ため、一覧にない表が残らないよう、一覧と schema の差を調べる試験を置く（7 章）。

## 3. 何を残すか

| 残すもの | 理由 | 備考 |
|---|---|---|
| `User` の行（匿名化済み） | 外部キーの参照先として必要。請求の控えを持つ | 物理削除はしない |
| 「最初の100」「初月無料」の記録（`doya_power_starter_claims`。メールのハッシュと userId） | 二重付与を防ぐ | `User` への外部キーを持たない。個人を特定できない形 |
| 請求・会計上の記録（Stripe の顧客・契約の控え、請求の履歴） | 法定の保存期間がある | 期間は要確認。会計・税務の専門家に確認するまで、消さない |
| 監査ログ（管理者の操作、課金の変更の記録） | 不正の調査と、課金の説明のため | 個人情報を含む列は、匿名化の時点で消してある前提。含む列があれば実装時に洗い出す |
| 削除の実行記録（件数だけ） | 実行したことの証明 | 個人情報は入れない（4 章） |

## 4. 実行の仕組み

- Vercel Cron で毎日1回、`/api/cron/data-retention` を呼ぶ。`Authorization: Bearer ${CRON_SECRET}` で保護する（既存の Cron と同じ）。
- 旗 `DATA_RETENTION_ENABLED` で制御する。既定はオフ。オフのときは何もせず、`200` と「無効」を返す。
- 対象の選び方: `deletedAt <= 今 - 90日` で、まだ削除が終わっていないユーザー。`User` に完了の印（`dataPurgedAt`）の列を足す案が最も単純。列の追加は DB の変更なので、承認が要る（8 章）。列を足さない場合は、削除の実行記録の表で終了を管理する。
- 1回の実行で処理するユーザーは上限を決める（例: 20人）。時間切れで途中終了しても、次の日に続きから再開できる。
- 表ごとに順に削除する。順番は、子の表から親の表へ（外部キーの向きに従う）。ファイルは、表の行を消す前に消す。1つのユーザーの削除は、表ごとに小さな単位に分け、長い1つのトランザクションにしない。
- 冪等にする。同じユーザーを2回処理しても、結果は同じ（すでに消えた行は、0件として扱う）。
- 失敗したら、そのユーザーを「失敗」として記録し、次の日に再実行する。連続して失敗が続くユーザーが出たら、Slack へ通知する（件数とユーザー ID の接頭辞だけ。名前・メールは出さない）。
- ログには、表の名前と削除した件数だけを出す。メール、名前、本文など、個人情報は出さない。
- 一度に大量を消さないよう、`DELETE` は主キーの範囲で分けて実行する。

## 5. 決定待ち

1. 会社の行の扱い。持ち主が退会したあと、90日後に、会社の行とドヤパワーの台帳を消すか、残すか。ほかの会社のメンバーがいる会社は、退会の API が止めるため、残るのは、ほかにメンバーがいない会社だけ。おすすめは、メンバーがいない会社に限り、90日後に消す。
2. 90日の間に、同じアカウント（同じ Google・Apple）で再登録したとき、元のデータを戻すか。おすすめは「戻さない」。理由は、匿名化の時点でメール・名前を消しており、元の人だと確かめる手段が無いため。戻す場合は、匿名化を取り消す設計が別に要る。
3. 請求・会計上の記録の保存期間（法定の期間）。会計・税務の専門家に確認する。

## 6. 取り消し（90日の間）

90日の間は、データは消えず、匿名化したユーザーに紐づいたまま残る。
ただし、利用者がアプリや Web から、元のデータを見ることはできない（ログイン手段を消してあるため）。
再登録しても、元のデータは戻さない案を、おすすめとする（5 章の2）。

## 7. 試験の案

純粋な関数に分けて、DB なしで試験する（既存の `account-delete.ts` と同じ作り）。

- 期限の判定: `deletedAt` がちょうど90日前（含む）、89日と23時間（含まない）、`null`（含まない）。
- 冪等: 同じユーザーを2回処理しても、2回目は0件。
- 途中失敗: 3つ目の表で失敗したとき、1・2つ目は消えたまま、次の実行で3つ目から再開する。
- 旗がオフ: 何も削除しない。
- ログ: 出力に、メール・名前の文字列が含まれない。
- 一覧の網羅: schema の `userId` を持つモデルの一覧と、削除の対象の一覧の差が、許可した例外（3 章の残すもの）だけになる。
- 最初の100の記録: 削除の前後で、`doya_power_starter_claims` の行数が変わらない。
