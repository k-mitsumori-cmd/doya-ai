# プッシュ通知の設計（ドヤバディのアプリ）

作成日: 2026-11-18。状態: 設計だけ。送信は作っていない。サーバーに入っているのは、端末のトークンを置く列と登録の API（`api-contract.md` の 3.12）だけ。
従う決まり: 本番への通信（Expo のプッシュ API）と本番の環境変数・DB の変更は、三森さんの承認のあと。Apple の Developer・署名は、株式会社スリスタの物だけを使う。

## 1. 方針

- 通知は、アプリを開いていない間に、「長い処理が終わった」などを知らせるために使う。使う人にとっての価値が、通知の許可を求める理由になる。
- 通知の許可は、最初の起動では聞かない。理由は、許可の画面を出す前に、何が届くのかを使う人が知らないと、断られやすく、断られると同じ端末では、アプリの中から許可を求め直せない（設定アプリから変えてもらうしかない）ため。
- 通知の許可を断っても、アプリのすべての機能を使える。通知は、あくまで「知らせ」で、条件にしない（Apple の審査ガイドライン 4.5.4 の趣旨。推測。最新版は申請の前に確かめる）。
- 通知の本文に、個人情報（氏名・メールアドレス・会社名・案件名・生成した文章の中身）を入れない。画面のロック中にも表示されるため。本文は固定の文にし、詳しい内容は、アプリを開いてから見せる。

## 2. 許可を聞くタイミング

1. 最初の起動、ログインの直後には聞かない。
2. 使う人が、時間のかかる処理（例: 記事の生成、動画の取り込み）を始めた直後に、アプリの画面で理由を説明する。例の文: 「処理が終わったら、通知でお知らせします。通知を受け取りますか。」（ボタンは「通知を受け取る」「あとで」）。
3. 「通知を受け取る」を押したときだけ、OS の許可の画面を出す。「あとで」を押したら、OS の画面は出さず、その処理の間は再び聞かない（次に長い処理を始めたとき、最大でも週に1回まで）。
4. OS の許可の画面で断られたら、アプリの中の再度の依頼は出さない。設定の画面に、「通知はオフです。端末の設定から変更できます」と案内を出す。
5. 許可を得たら、Expo のプッシュトークンを取り、`POST /api/app/auth/devices/{id}/push-token` で登録する（3.12）。

## 3. 通知の種類（案）

| 種類 | 送る場面 | 本文（固定の文の例） | 初期の状態 |
|---|---|---|---|
| 長い処理の完了 | 使う人が始めた処理が終わったとき | 「処理が完了しました。アプリで結果をご確認ください。」 | 許可したらオン |
| 招待 | 会社・チームへの招待を受けたとき | 「ドヤバディへの招待が届いています。」（招待した人の名前は入れない） | オン |
| 期限 | 契約・トライアルの期限が近いとき | 「ご利用の期限が近づいています。詳しくはアプリでご確認ください。」 | オン |
| お知らせ（運営） | 障害・メンテナンスなどの大事なお知らせ | 「ドヤバディからのお知らせがあります。」 | オン |

- 宣伝の通知は、最初の版では作らない。作るときは別のオフ設定を付け、初期はオフにする。
- 通知を押すと開く画面の指定（ディープリンク）は、固定のパス（例: `/m/...`）だけを持ち、個人情報を載せない。

## 4. 端末のトークンの扱い

- `AppDevice.pushToken`（Expo のプッシュトークン。`ExponentPushToken[...]`）に置く。行は、アプリのログイン1回（トークンの系統の最新の行）に対応する。
- 登録できるのは、その端末の行を持つセッションだけ（Bearer のセッションの id と `AppDevice.sessionId` が一致し、生きている行）。他人・他の端末の行には登録できない。
- プッシュトークンは物理的な端末（アプリのインストール）を指す。1つのインストールで同時に使えるアプリのログインは1つなので、同じトークンが別の行に登録されたら、新しい登録を優先し、ほかの行（ほかのユーザーの行を含む）からは外す。トークンを知らない人は登録できず、トークンの推測は現実的でない。競合は、DB の部分一意索引（生きている行の `pushToken` は一意）で守る。
- リフレッシュ（トークンの替え）では、新しい行にトークンを引き継ぐ。ログアウト・端末の失効・退会（行ごと削除）で、トークンは消える。
- 将来の送信側は、`revokedAt IS NULL` かつ `rotatedAt IS NULL` で、`expiresAt` が未来の行にだけ送る。失効の直前の確認と書き込みのずれがあっても、失効した行には送らない。
- Expo は、無効になったトークン（アプリの削除など）を、送信の結果（`DeviceNotRegistered`）で知らせる。そのときは、その行の `pushToken` を null にする。
- 使う人が設定でオフにしたら、`{ "token": null }` で登録を消す（3.12）。OS の許可を後から切られた場合は、次の起動で許可の状態を確かめ、切られていればトークンを消す。

## 5. 送り方

- サーバーから、Expo の Push API（`https://exp.host/--/api/v2/push/send`）へ、固定の本文とトークンを送る。1回の呼び出しで100件まで（Expo の上限。確認する）。送ったあと、受け取りの確認（receipt）を調べ、無効なトークンを消す。
- Expo の Push API の利用は有料ではないが、本番の通信なので、今回は実装しない。実装するときは、三森さんの承認を得る。Expo のアクセストークンの設定（有効にする場合）は、環境変数に置き、コードに書かない。
- iOS の実機への送信は、Apple の APNs の鍵（株式会社スリスタの Apple Developer のもの）を Expo に登録して行う。この設定は、三森さんの操作。
- 送信は、旗 `APP_AUTH_ENABLED` に加えて、別の旗（例: `APP_PUSH_ENABLED`）でオン・オフできるようにする。既定はオフ。

## 6. Apple の要件

- アプリの中で、通知を許可してもらう理由を、OS の画面より前に説明する（2章）。
- 通知を断っても、アプリを使える（1章）。
- Push Notifications の機能（Capability）を、アプリの App ID で有効にする（株式会社スリスタの Apple Developer）。
- 通知の内容は、App Store の審査ガイドラインの、広告の通知の扱いに従う（宣伝の通知は、許可と、オフにできる設定が要る。推測。最新版は申請の前に確かめる）。
