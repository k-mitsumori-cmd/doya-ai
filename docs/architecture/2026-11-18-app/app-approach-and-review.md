# ドヤバディ iOS アプリ化の下調べ：作り方の比較と Apple の審査・課金の決まり

作成日：2026-11-18（下調べ担当）。コードは変更していません。Apple の公式ページは 2026-11-18 に取得しました。
この文書は事実と選択肢を集めたものです。どの案にするかは三森さんと統括が決めます。

## 1. 結論の下書き（比較表）

| 観点 | (a) Web を包む（Capacitor） | (b) React Native / Expo で作り直す | (c) PWA |
|---|---|---|---|
| ログイン | Google のログインは埋め込み WebView では使えない。システムのブラウザ経由か、ネイティブのログイン部品が要る | 画面はネイティブなので、ネイティブのログイン部品を使える。ただし今の API は Cookie 前提で、トークン方式の窓口を足す必要がある | Safari の Cookie をそのまま使える。ログインの追加作業は無い |
| 作る量 | 小さい。外側の殻と、端末機能の接続だけ | 大きい。画面を作り直す（ツールは約30本） | 最小。manifest と Service Worker など |
| Web との同期 | 最も容易。Web を直せばアプリも変わる（リモート読み込みの場合） | 画面を2系統で保守する。API だけ共有 | 完全に同じ |
| 審査（4.2） | 単なる Web の包みは却下の恐れが最も高い。端末機能と専用の画面で補う必要がある | 通りやすい | 審査は無い。ただし App Store には載らない |
| プッシュ通知 | プラグインで可能 | 可能 | iOS 16.4 以降、ホーム画面に追加した PWA で可能（未確認、下の7章） |
| Mac の Simulator | 確認済みの手順がある（ANIMALITY） | 確認済みの手順がある（呪い日記・Expo） | Simulator の Safari で足りる |
| 向く場面 | 最短で App Store に出す。端末機能は少なめ | 長く育てる前提で、体験を端末に合わせる | App Store 掲載が不要なとき |

下書きの方向性（判断は統括）：最初は (a) を土台にして、Apple 向けの専用機能を足す案と、(b) を最初から作る案の2つが現実的です。(c) は「App Store に載せる」目的を満たさないので、補助の位置づけです。いずれの案でも、課金は Stripe を正とし、アプリは契約の状態を読むだけにする設計が、審査上もっとも安全です（5章）。

## 2. 作り方の比較（詳細）

### 2.0 いまのリポジトリの事実

- Next.js 15.5.25 / React 18 / next-auth 4.24.15 / Prisma。Capacitor、Expo、WebView の記述は、このリポジトリの `package.json` と `src` には無い。
- 認証は NextAuth の Google OAuth のみ（`src/lib/auth.ts`）。`PrismaAdapter` を使い、`session.strategy` は指定していないため、既定の「データベースのセッション」になる（`reference/05-auth-payments.md` にも JWT を使う記述は無い）。ブラウザは `next-auth.session-token` の Cookie でセッションを持つ。`maxAge` は 24 時間。
- `getServerSession` を使う API ルートのファイルは 180 個。Bearer トークンでユーザーを判定する窓口は、ユーザー向け API には見当たらない（Bearer は cron、運営用、ライブのトークン発行などに限られる）。つまり、いまの API はブラウザの Cookie 前提で、ネイティブ画面から直接呼ぶには窓口の追加が要る。
- `allowDangerousEmailAccountLinking` は未設定。別のログイン方法（Apple など）を足すと、同じメールでも別ユーザーになる、または `OAuthAccountNotLinked` で止まる。アカウントの整合性は別担当の文書（account-integrity.md）で扱う。
- サービス定義は `src/lib/services.ts` に 32 件（うち `coming_soon` が 10 件）。`src/app` の直下には約 35 の画面系ディレクトリがある。アプリ化の対象にする本数は、統括が決める必要がある。
- 課金は `User.plan` を正とし、Stripe Checkout で 1 人あたり月額（reference/11-billing-spec.md が正本）。

### 2.1 (a) Capacitor（Web を包む）

ログイン
- Google は、埋め込みのユーザーエージェントへ OAuth の認可要求を向けることを禁じている（Google OAuth 2.0 ポリシー「Use secure browsers」。取得日 2026-11-18）。WKWebView の中で Google のログインを開くと、拒否される。
- 回避策は2つある。①ログインの時だけシステムのブラウザ（ASWebAuthenticationSession）を開き、結果をアプリに戻す。②ネイティブの Google ログイン部品で ID トークンを得て、サーバーで検証してセッションを作る。どちらも、いまの NextAuth の Cookie 方式に「アプリ専用のログイン窓口」を足す作業になる（未実装）。
- Web の画面を `server.url` で本番から読み込む形にすると、Cookie は本番ドメインのものとして扱われ、Web と同じセッションを使える（この点は設計上の推論で、このリポジトリでは未検証）。
- トークンを端末に置く場合は Keychain を使う。Apple のガイドライン 5.1.1(v) は、資格情報やトークンを端末の外に保存することを禁じている。

作る量・保守
- 外側の殻、アイコン、起動画面、端末機能のプラグインが作る対象。画面は Web のものをそのまま使う。
- Web の機能追加がアプリにも自動で入る（リモート読み込みの場合）。ただし Apple は、審査後に機能を大きく変える更新に注意を求めるため、運用の決まりは別途要る（未確認）。

審査
- ガイドライン 4.2「アプリは、ウェブサイトを包み直したもの以上の機能・内容・UI を持つこと」。この文面に、単なる Web の包みが当たる。
- 通すには、プッシュ通知、ファイルやカメラ、共有、端末内の下書きなど、Web ではできないことを少なくとも1つは入れる必要がある。

端末機能（プラグインの候補）
- プッシュ通知：Web 版の通知（ドリップ・Slack など）の代わりに、依頼の完了や承認待ちを知らせる。
- カメラ・写真・ファイル：バナー、画像、面談の素材、名刺や書類の取り込み。
- 共有シート、外部リンクはアプリ内の Safari で開く。
- オフライン：生成系のツールが多く、ほぼ意味が無い。履歴の閲覧程度。

前のドヤアプリ（ANIMALITY）で分かっていること
- ANIMALITY は Capacitor 8.5.3 で、`www` の HTML/JS を WKWebView（`capacitor://localhost`）に入れ、Simulator で動かした（Obsidian「アニマル製薬_11_iOSアプリの構成」）。
- Xcode を開かずに `xcodebuild ... -destination 'platform=iOS Simulator,name=iPhone 17 Pro' -derivedDataPath ...` で起動する手順も記録されている。
- 審査の人はメールのコードを受け取れないため、「Apple でのサインイン」とデモ用アカウントを用意する、と決めてある（同「決めることと注意点」）。
- その案件は Web 版が静的 HTML/JS。ドヤバディは Next.js の SSR で Cookie 認証なので、そのまま同じ手順にはならない。

### 2.2 (b) React Native / Expo（作り直し）

ログイン
- 画面がネイティブなので、Google と Apple のネイティブのログインを使える。トークンは Keychain（`expo-secure-store`）に置く。
- いまの API は Cookie 前提のため、「ネイティブのログインで得たトークンをサーバーで検証し、Bearer で呼べる窓口」を追加する必要がある。`getServerSession` を使う 180 個のファイルを、共通の関数に置き換えるか、窓口を絞って対応する範囲を決める。
- 窓口を足すと、認可の入口が増える。認可の漏れを防ぐ点検が要る。

作る量
- 画面を作り直す。ツールは 30 本前後あり、全部をアプリにするのは現実的でない。統括が、アプリに入れる本数（例：ダッシュボード、通知、契約の状態、生成の履歴、数本のツールの入口）を決める必要がある。
- 生成系の入力画面は Web のほうが作りやすい。アプリは「見る・承認する・通知を受ける」中心にする、という切り分けも可能（案であり、未決定）。

保守・同期
- Web とアプリで画面が2系統になる。API と型を共有し、機能の差を一覧で管理しないと、Web にあってアプリに無い機能が増える。

審査
- ネイティブ画面なので、4.2 に当たる危険は小さい。

前の作業で分かっていること
- 呪い日記とヘイシャ系のゲーム（`~/Code/games/heisha-genkai` など）は Expo と EAS（`eas.json`）で作られ、`ios/` もある。このリポジトリには `asc-shot-upload.cjs` と App Store Connect の売上取得（`src/lib/appstore-sales-core.ts`）があり、App Store Connect の API キーがすでに運用されている。つまり、Apple の開発者アカウントは少なくとも1つ存在する。名義（個人か組織か）は未確認。

### 2.3 (c) PWA

- ホーム画面に追加して使う Web。Cookie のセッションがそのまま使えるので、ログインの問題は無い。
- App Store には載らない。審査も無いので、4.2 や課金の決まりも当たらない。
- ホーム画面に追加する手順を利用者に案内する必要がある。通知の対応状況は未確認（7章）。
- 「アプリを作る」目的が App Store への掲載なら、(c) では足りない。社内向けの先行利用には向く。

## 3. Mac の Simulator までの道筋と必要な容量

現状（2026-11-18 に確認）
- Xcode 26.6（ビルド 17F113）が入っている。iOS 26.5 のシミュレーターのランタイムも入っている。
- `~/Library/Developer/CoreSimulator` は約 11GB。ANIMALITY、わたし文庫などの端末が既にある。`iPhone 17 Pro` の端末もある。新しいランタイムの取得は不要。
- `~/Library/Developer/Xcode` は約 513MB。
- このリポジトリの `node_modules` は約 939MB。
- 起動ディスクの空きは約 16GB（`df`）。「ルールの入口」の決まりは、空きが 10GB 未満ならビルドやインストールをしない。

見積もり（実測ではなく、私の経験からの推定。未確認）

| 案 | 追加で要る容量の目安 | 内訳 |
|---|---|---|
| (a) Capacitor | 約 2〜3GB | 小さな `node_modules`（数百 MB）、SwiftPM の取得、Xcode のビルド結果（DerivedData） |
| (b) Expo | 約 3〜6GB | `node_modules`（約 1GB）、CocoaPods、DerivedData。EAS のクラウドビルドを使えば手元は減る（無料枠は未確認） |
| (c) PWA | ほぼ 0 | 既存の Simulator の Safari で確認 |

道筋（(a) の場合）
1. Web 側に「アプリ専用のログイン窓口」を設計する（コード変更は別担当）。
2. 別の作業フォルダに Capacitor の殻を作る。このリポジトリの本体には入れない（`doya-ai/` と混ざらないように、`app/` のような専用の場所を統括が決める）。
3. `xcodebuild` で、既存の iPhone 17 Pro の端末に入れて起動する。DerivedData は作業用の場所（スクラッチ）に置き、終わったら消す。
4. 起動前に空きを確かめる。10GB 未満なら止める。

前のドヤアプリ（`~/Code/tools/doya-app`）の注意
- これは「アプリの画面をスマホで見て、画面ごとにフィードバックを送る」道具で、ドヤバディのアプリではない。`xcrun simctl io screenshot` で Simulator の画面を取り込む仕組みを持つ。ブランチ `feat/app-morning-digest-3apps` と `feat/app-motion-20261110` は、このリポジトリの中で別のアプリ（ANIMALITY など）の通知・動きに関する作業で、ドヤバディのアプリ化は未着手。
- 画面の確認には、この道具をそのまま使える（`apps.json` に追加し、`sim` に UDID を入れる）。

### 4.1 課金（3.1.x）

| 節 | 内容（要約） |
|---|---|
| 3.1.1 | アプリ内の機能やコンテンツの解放は、アプリ内課金（IAP）を使う。ライセンスキーや QR コードなど、独自の方法は使えない |
| 3.1.1(a) | 他の購入方法へのリンクは、地域ごとの権限（StoreKit External Purchase Link Entitlement など）を申請して使う。米国のストアでは、権限なしでボタン、外部リンク、行動喚起が許される。そのほかのストアでは、権限が当てはまらない限り、IAP 以外の購入方法を指すボタンやリンクをアプリとメタデータに入れられない |
| 3.1.2 | 自動更新のサブスクリプションは、7日以上、継続する価値があること。SaaS やクラウドの支援も例に挙がる。すべての端末で使えること |
| 3.1.3 | 次の種類のアプリは IAP 以外の購入方法を使える。ただし、米国のストアを除き、アプリの中で他の購入方法を勧めることは一般にできない。アプリの外で利用者に連絡することは可能 |
| 3.1.3(b) 複数のプラットフォーム | 他で購入した内容やサブスクリプションをアプリで使える。ただし、同じものをアプリ内でも IAP で買えること、が条件 |
| 3.1.3(c) 企業向けサービス | 従業員や学生向けに、組織へ直接販売するアプリは、企業の利用者が購入済みの内容にアクセスできる。個人、単独のユーザー、家族への販売は IAP を使う |
| 3.1.3(f) 無料の単体アプリ | 有料の Web の VoIP、クラウドストレージ、メール、Web ホスティングの無料の付属アプリ。アプリ内で購入せず、購入を促す表示も無いこと |

ドヤバディに当てはめた読み方（解釈であり、Apple の判断ではない）
- 3.1.3(f) は列挙された4種類（VoIP、クラウドストレージ、メール、Web ホスティング）に限る書き方で、ドヤバディの生成ツール群は当てはまらない可能性が高い。この節を根拠にするのは危険。
- 3.1.3(c) は「組織へ直接販売」と書く。ドヤバディが法人のチームに 1 人あたりの月額で販売している点は合う。ただし、個人でも契約できる状態（アプリや Web で個人が申し込める）だと、個人向けとみなされ、IAP が必要になる恐れがある。「個人の契約を受けるか」は事業側の判断（6章）。
- 3.1.3(b) は、アプリでも IAP で同じプランを売ることが条件になる。ドヤバディの課金（Stripe、`User.plan` の単一参照、reference/11-billing-spec.md）に、IAP の経路を足す作業は大きい（反映の経路が増え、不変条件に影響する）。
- 「アプリは Web で契約した状態を読むだけ」の設計は、アプリの中で購入の呼びかけ（価格、契約ボタン、外部の購入ページへのリンク）を出さなければ、上の3.1.3の「他の購入方法を勧めない」と衝突しにくい。ただし、Apple が BtoB の SaaS で実際にどう審査するかは、公式の文面だけでは確定しない。未確認。

### 4.2 外部の購入ページへの誘導（米国と日本）

米国
- ガイドライン 3.1.1(a)：米国のストアでは、権限なしで外部の購入への行動喚起を入れられる。
- 米国の裁判（Epic v. Apple）：第9巡回区は 2025-12-11 の判断で、Apple の制限が外部リンクでの購入を事実上禁じているとした。一方で、リンクへの手数料の全面禁止は広すぎるとして差し戻し、Apple は「合理的に必要な費用」の範囲の手数料を取れるとした。Apple のリンクより目立たせることは禁じてよい、とも述べている（Fenwick の解説、https://www.fenwick.com/insights/publications/ninth-circuit-largely-upholds-ruling-in-epic-v-apple 、取得日 2026-11-18）。
- 2026 年に入ってからの経過は、二次情報（MacRumors などの検索結果）による。再審理の申立ては 2026-03 に退けられた。2026-04 の末に、最高裁への申立ての間、命令を止める措置を取り消す判断が出た。2026-08 時点では、手数料の最終的な率は決まっていない。最高裁の判断は確認できていない。以上は不確か。公式の判決文で確かめる必要がある。
- 日本のストアには、この裁判の結果は及ばない（米国のストアの話）。

日本
- 携帯ソフトウェア競争促進法（スマホ新法）の対応として、Apple は 2025-12-17 に発表し、iOS 26.2 から利用できるようにした（Apple の発表）。
- 日本では、IAP と並べて代替の決済方法を入れられ、アプリから Web サイトへのリンクで取引を完了させることもできる。
- 手数料（デジタルの商品とサービス）：App Store の手数料は、多くの開発者で 10%（小規模事業者プログラムの会員と、2年目以降のサブスクリプションを含む）、それ以外は 21%。IAP を使う場合は、決済処理費が別に 5%。リンク先の Web サイトでの取引には、ストアサービス手数料が 15%（上と同じ対象は 10%）。
- 制限：Kids カテゴリのアプリは Web へのリンクを入れられない。13 歳未満の利用者には取引のリンクを出せない。18 歳未満に出す場合は保護者の確認画面が要る。
- 日本のストアで外部リンクを入れる手続き（権限の申請の要否、審査での扱い）は、今回取得した Apple のページでは確認できなかった。未確認。
- 注意：契約が Web（Stripe）で、アプリがリンクを出さない設計なら、手数料は発生しない。リンクを出すと、日本では約 10〜15% の手数料が Apple に発生する可能性がある（Apple の発表の文面。適用条件の細部は未確認）。

### 4.3 ログイン（4.8）

- Facebook、Google、X、LinkedIn、Amazon、WeChat などの第三者・ソーシャルログインを主なログインにする場合は、次の条件を満たす同等のログイン（実質的には「Apple でサインイン」）も出す。条件：データ収集を名前とメールに限る、メールを非公開にできる、同意なく広告用に操作を集めない。
- 例外：①自社のアカウントシステムのみを使う、②代替マーケットプレイス、③教育・企業・ビジネスのアプリで、既存の学校または職場のアカウントを必須とする、④政府や業界の電子 ID、⑤特定の第三者サービスのクライアント。
- ドヤバディは Google の個人・組織を問わないログインで、職場のアカウントを必須にしていない。③ に当たると主張できるかは不確か。Apple でログインを足す前提で見積もるのが安全。
- Apple でログインを足すと、メールの非公開（中継アドレス）で別ユーザーが作られ、Web の既存ユーザーと二重になる危険がある。これは account-integrity.md の対象。

### 4.4 アカウントの削除（5.1.1(v)）

- アカウントを作れるアプリは、アプリの中でアカウントを削除する機能を持つこと。
- 重要な機能がないアプリはログイン無しで使えること。個人情報は、中核の機能に関係する場合だけ求める。
- 第三者サービスの資格情報を取り消し、データへのアクセスを止める手段をアプリの中に置く。資格情報やトークンを端末の外に保存してはならない。
- ドヤバディでは、削除するとチーム、課金（Stripe の契約）、組織のデータがどうなるかを決める必要がある（削除の API は別担当の文書で扱う）。

### 4.5 プライバシー（5.1.1(i)、App Privacy）

- プライバシーポリシーの URL を、App Store Connect の情報と、アプリの中の両方に置く。ポリシーには、収集するデータ、使い道、第三者（解析、SDK、外部の AI を含む）、保存と削除の方針を書く。
- App Store Connect で「App Privacy」を申告する。申告には、使う第三者の SDK が集めるデータも含める。名前、メール、ユーザー ID を保存するなら申告が要る。
- 5.1.2(i)：外部の第三者の AI にデータを渡す場合は、渡すことを明示し、同意を得る。ドヤバディは Gemini や OpenAI に入力を渡すため、この表示が要る。解釈であり、Apple の個別の判断は未確認。
- ドヤバディの `/privacy` ページは存在する。アプリ向けの申告に足りるかは未点検。

### 4.6 登録（Apple Developer Program）

- 年 99 ドル。地域により現地の通貨の価格になる（日本の価格は登録の画面で表示される。約 12,800 円という記録が Obsidian にあるが、公式の確認は未了）。
- 個人：本人の法的な氏名、2 要素認証、成年。D-U-N-S は不要。
- 組織：D-U-N-S 番号が必須。法人として Apple と契約できること（屋号、通称、支店は不可）。Account Holder は組織を拘束する権限を持つ人。組織のドメインのメール。組織のドメインと結びついた、公開された、内容のある Web サイト。
- 処理にかかる日数は、公式ページに記載が無い。D-U-N-S の取得は、Obsidian の記録で「数日〜2週間」。
- 申し込みはしていない。

### 4.7 審査で落ちやすい点

- 2.1(a)：ログインのあるアプリは、デモアカウントの情報を提出し、バックエンドを動かしておく。法的な理由でデモアカウントを作れない場合は、Apple の事前の承認を得て、アプリに全機能が見えるデモモードを持つ。
- 審査の人は、メールのコードや社内の SSO を受け取れない。Google のログインだけだと入れないため、Apple でサインインか、固定のデモアカウントが要る。
- 4.2：Web の包みと判断されること。
- 5.1.1(v) のアカウント削除、5.1.1(i) のポリシーの URL の不備。
- 3.1.1：アプリ内で機能を解放するのに IAP を使っていない、または外部の購入を勧めている。
- 2.1(b)：IAP を使うなら、審査の人から見える場所で動くこと。

## 5. 課金の設計の選択肢（Stripe を正とし、アプリは状態を読むだけにする案を軸に）

共通の前提：契約の正本は `User.plan`（Stripe から同期）。アプリはこれを読むだけにして、アプリの中でプランを変更・購入させない。

### 案 1：読むだけ（推奨の候補）

内容
- アプリでは「現在のプラン」「利用状況」だけを表示する。価格、契約や変更のボタン、Web の契約ページへのリンクは出さない。
- 契約や変更は Web で行う。アプリは「契約の案内は Web で行ってください」とだけ書くか、何も書かない（文言の許容範囲は Apple の審査で変わる。未確認）。

良い点
- Stripe が唯一の正本のまま。IAP の経路を足さないので、課金の不変条件（INV-1〜12）が増えない。
- 3.1.1 と 3.1.3 に衝突しにくい。手数料が Apple に発生しない。
- 開発量が最小。

困る点
- アプリから契約に進めず、アプリで知った人が Web に移る手間が出る。
- 審査の人が「どうやって使うのか」を理解できるよう、レビュー用の説明（既に契約済みのチームのアカウントを使う）が要る。
- 個人でも契約できる状態だと、個人向けの販売とみなされる恐れ（3.1.3(c)）。未確認。

### 案 2：アプリから Web の契約ページへ誘導する

良い点：契約への導線ができ、獲得の効率が上がる。
困る点：米国のストア以外では、権限の申請が要る（3.1.1(a)、3.1.3(a)）。日本では、リンク先の取引に約 10〜15% のストアサービス手数料が Apple に発生する可能性がある。審査の文面の不確かさが大きい。

### 案 3：IAP を並べて提供する（3.1.3(b)）

良い点：審査上は最も標準的。アプリ内で契約が完結する。
困る点：手数料が 10〜21% と決済処理費 5%（日本）。IAP の契約を `User.plan` に反映する経路が増え、Stripe の契約と二重契約になる危険がある。課金仕様の大きな変更になる。

### 案 4：アプリで契約の説明を一切出さず、組織の管理者だけが Web で契約する

案 1 に近い。BtoB の組織の「管理者」が契約し、メンバーはアプリでログインして使うだけ。アプリのログイン画面や説明には、契約の話を入れない。3.1.3(c) の趣旨に最も合うが、Apple の実際の判断は未確認。

## 6. 三森さんに決めてほしい点

1. アプリの作り方
   - A案：Capacitor（Web を包む）。最短で形になる。4.2 で却下される危険があるため、通知など端末機能を足す前提。
   - B案：Expo で作り直す。審査に通りやすく、長く育てやすい。作る量が多く、API にトークンの窓口を足す。
   - C案：まず PWA だけ。審査が無く速い。App Store には載らない。
2. アプリに入れる機能の範囲：全 30 本前後か、「見る・通知を受ける・承認する」に絞るか。
3. 課金の見せ方：5章の案 1〜4 のどれか。「アプリは読むだけ」（案 1）を基準にする案を、まず提案する。
4. 個人でも契約できるようにするか：Web で個人の契約を受けると、3.1.3(c) の「組織へ直接販売」から外れる恐れがある。法人のチームだけにするか。
5. 「Apple でサインイン」を付けるか：付けると 4.8 を満たせる。付けない場合は、③の例外（職場のアカウントを必須）を主張できる設計にするか。付けるなら、既存の Web ユーザーとの紐づけ（メールの中継アドレスの対応）の設計が要る。
6. Apple Developer の名義：組織の名義（D-U-N-S が要る。既に取得済みの法人があれば早い）か、個人か。既存の呪い日記と同じアカウントを使うかどうか。
7. 審査用のデモアカウントを、固定のチーム（契約済みの状態）で用意してよいか。
8. アカウントの削除の挙動：チームの管理者が削除したときの、課金とデータの扱い。
9. 日本のストアだけで出すか、世界で出すか（外部リンクの規則が地域で違う）。
