## 1. 結論

1. いまの作りのまま Apple のログインを足すと、同じ人に別のユーザーができます。ログイン手段は Google だけで、NextAuth がメールでユーザーを突き合わせます。Apple の「メールを隠す」では、メールが一致しません。会社・契約・ドヤパワーは User に付くため、すべて2つに分かれ、2つめは無料のままになります。
2. アプリを作る前に、認証の土台（第2段）を直す必要があります。土台なしでアプリを先に作ると、あとから重複したアカウントを統合する作業が要ります。
3. 作り方のおすすめは、Expo の殻に、ツール画面を既存の Web（WebView）で表示する形です。ログイン・ホーム・通知・アカウント設定だけをネイティブにし、ツール画面は Web のまま表示して、あとから画面ごとにネイティブにします。理由は次のとおりです。
   - Google は、埋め込み WebView でのログインを拒否します。ログインはネイティブで行い、サーバーが発行した使い捨てのコードで Web 側のセッションに渡す形が必要です。
   - 単なる Web の包み（Capacitor だけ）は、Apple の審査ガイドライン 4.2（最低限の機能）で却下される恐れが最も高いです。ネイティブのログイン・通知・設定を持つ殻なら、通る見込みが上がります。ただし、通ると確定はしません。
   - ツールは約30本あり、すべてを作り直すと量が大きすぎます。
   - 同じ作りの Expo と EAS は、呪い日記・ヘイシャ系で運用済みです。App Store Connect の API キーも運用されています。
4. 課金は、Stripe（Web で契約）を正とし、アプリは契約の状態を読むだけにします。アプリの中に価格・契約ボタン・購入ページへのリンクを出さなければ、Apple の手数料がかからず、審査も通りやすいです。
5. ER 図から、アプリ化に関わる弱い点が見つかりました（後述）。特に、User の削除が止まる所と、削除したときにメンバーの行が持ち主を失って残る所は、アプリで必須になるアカウント削除に直結します。

## 2. アカウントが壊れる場合（要約。詳細は account-integrity.md）

| 場合 | いまの作りで起きるか |
|---|---|
| Web は Google、アプリは Apple で同じ人なのに別のユーザー | 起きる。メールが同じなら OAuthAccountNotLinked で本人が入れない。違えば別のユーザーができる |
| Apple の「メールを隠す」で別人になる | 起きる。Apple はメールを最初の1回しか返さない |
| 管理画面の Google の条件が弱くなる | ログイン手段を足すと起きる。@surisuta.jp のメールだけを見ている（admin-google-session.server.ts:7-10） |
| 利用者が自分で退会できない | 起きる。管理者の API だけで、物理削除。User を消すと会社・メンバー・ドヤパワーの口座が Cascade で一緒に消える |
| 初月無料と「最初の100」が、メールの違いで二重に付く | 起きる。Gmail の +タグや Apple の隠したメールで新しい人として扱われる |
| アプリから API を呼べない | 起きる。Cookie のセッションで24時間。Bearer の窓口が無く、Origin を見る API が6本ある |
| 同じユーザーが会社を2つ作る | 起きない（userId の一意と upsert） |
| 招待をメールの違いで受ける | 受けられない（トークンとメールの一致を求めている）。Apple の隠したメールでは、本人でも受けられない |
| Google の未確認メールからの乗っ取り | 起きない（allowDangerousEmailAccountLinking が未設定） |

## 3. ER 図から見つかった、アプリ化に関わる点（schema.prisma）

- InterviewXProject の user に onDelete の指定が無く（1613行付近）、User の削除が止まります。
- 各ツールのメンバー表（Kintai・Sfa・Shodan・Aio・Mensetsu・Quote・Aishodan・Income・Expense）の userId に外部キーが無く、User を消すと行が残ります。
- 会社まわりの userId（account_company_members など）も外部キーの無い文字列です。
- 会社のメンバーの一意制約は (companyId, email) だけで、(companyId, userId) がありません。
- 契約の状態が4か所（User の列、Subscription、UserServiceSubscription、account_company_billing）にあります。
- 端末・リフレッシュ・プッシュのトークンの表が、まだありません。

## 4. 設計の方針（おすすめ）

- 結び付けの関数を1つにし、Web とアプリが同じ関数を通る。同じメールの既存ユーザーがいれば自動では結び付けず、前に使ったログイン手段でのログインか、メールの確認コードを挟む。
- User.email は自動では書き換えない（Stripe の顧客をメールで横断する決まり INV-6 のため）。メールの正規化は別の列に持つ。
- パスワードのログインは作らない（NextAuth の Credentials は JWT 専用で、足すと全員のログインが切れる）。
- アプリの認証は、NextAuth のまま、トークン発行の API を足す。サーバーで id_token を確かめ、1時間の Session の行と、90日の端末ごとのリフレッシュトークンを出す。トークンは iOS の Keychain に置く。middleware で Bearer を Cookie に置き換え、既存の API は書き換えない（この置き換えが Next.js 15.5 で動くかは未確認。第2段の最初に試す）。
- 退会の API を足す。匿名化して残し、作ったデータは決めた期間のあとで消す。Apple の連携の取り消しも行う。
- 重複の見つけ方は、読み取り SQL（件数だけを返す形）15本。実行は、三森さんの承認のあと。

## 6. 三森さんに決めてほしい点（選べる形）

1. アプリの作り方
   - A. Expo の殻＋ツール画面は Web を表示（おすすめ）
   - B. Capacitor の包みだけ（最短だが、審査で却下の恐れが最も高い）
   - C. すべてをネイティブに作り直す（量が大きい）
2. アプリのログイン手段
   - A. Google と Apple（おすすめ。Google があるアプリでは Apple でのサインインが事実上必要。審査ガイドライン 4.8）
   - B. A にメールのコードを足す
3. アプリで料金を払えるようにするか
   - A. 払えない。契約は Web だけで、アプリはログインして使う（おすすめ）
   - B. App Store の課金も入れる（Stripe との二本立てで、契約を同じ人に付ける決まりが要る。課金の正本の改修になる）
4. 同じメールの既存ユーザーがいるときの結び付け
   - A. 毎回、確認の手順を挟む（おすすめ）
   - B. 両方がメール確認済みのときだけ自動
5. 退会
   - A. 匿名化して残し、決めた期間のあとでデータを消す（おすすめ）
   - B. すぐに物理削除
6. すでに2つに分かれた人
   - A. ログイン手段だけを主のユーザーに移す（おすすめ）
   - B. データの持ち主も付け替える（表ごとの設計が要る）
7. Apple Developer の名義
   - A. 組織（D-U-N-S 番号・組織のドメインの公開サイト・年 99 ドルが要る）
   - B. 個人（手続きは軽いが、名義が個人になる）
   - ※すでに Apple の開発者アカウントが1つあるようですが、名義は未確認です。
8. 出す国
   - A. 日本だけ
   - B. 世界
