アカウントまわりの ER 図

2026-11-18 ／ 正本：prisma/schema.prisma（6,367 行・266 モデル、枝 docs/doya-app-design-20261118 の cf09146ad 時点）

ドヤバディ（ドヤAI）をアプリにするときに、Web とアプリでログインアカウントが食い違わないようにするための図です。表名は「モデル名」と「実際のテーブル名」の両方を書いています。同じ内容の Mermaid 版は account-er.md にあります。

本番の DB・Stripe・環境変数は読んでいません。本番に表があるか、実データ、実際の外部キーの制約は、この図からは分かりません。「推測」と書いた所は、スキーマだけでは断定できない所です。

凡例

User（アカウントの中心）認証（NextAuth）管理画面の認証（Userと別）会社・メンバー・役割課金（Stripe）ドヤパワーツールのデータ（userId 持ち主）ツールの組織外部キーなし（文字列だけの関係）削除を止める可能性外部・未ログイン
実線：外部キーあり（消したときの動きを添える） 赤の点線：外部キーなし（列に ID が入る約束だけ）

スマホでは図を横にスクロールして読めます。

1 認証（NextAuth）

ログイン方法は Google OAuth だけです（src/lib/auth.ts）。session.strategy を指定していないため、NextAuth v4 の既定どおり Session 表を使う方式と考えられます（推測）。管理画面の認証は User と無関係の別の仕組みです。

2 会社（チーム）とメンバーと役割

「1つのアカウントに会社は1つ」です。AccountCompany.userId が一意で、会社を作った人（持ち主）を表します。持ち主はメンバー表に行を持たず、1人目として数えます。メンバー表の userId は、招待中は null で、外部キーはありません。

3 課金とドヤパワー

契約の状態は、User の列、Subscription、UserServiceSubscription、会社単位の account_company_billing の4か所に分かれます。ドヤHR とナグサメは、それぞれ別に Stripe の列を持ちます。課金の正本は reference/11-billing-spec.md で、料金判定は User.plan を単一の参照先とする方針です。

4 ツールのデータの持ち主

持ち主は、ユーザー（userId）、ツールごとの組織（organizationId。組織表は10種類）、プロマネのワークスペースの3種類です。未ログインでも使えるツールは guestId も持ちます。会社と各ツールの組織は、account_company_tool_orgs の文字列でつながるだけで、外部キーはありません。

5 User を消したとき

直接の子の動きです。子の子は、各モデルの onDelete に従います（全部は追い切れていません）。

会社が消えたあと消える：members / billing / role_settings / doya_power_accounts（grants・transactions）/ power_pack_purchases。残る：role_events / tool_orgs / member_departments / record_authors / doya_power_starter_claims。各ツールの組織は消えない

会社の持ち主が消えると、各ツールの組織とそのデータは、持ち主のいない形で残ります（推測：アプリ側に退会時の後始末があるかは未確認）。Stripe の顧客や契約は DB の外にあり、DB の削除では止まりません。

6 気づいた点

重大なものを上に並べます。行番号は prisma/schema.prisma のものです。

  • 重大
    User の削除が止まる可能性がある

    InterviewXProject.user だけ onDelete の指定が無い（L1613）。必須の関係なので Restrict 扱いとなり、この行を持つユーザーは削除できない。退会機能とアプリのストア審査のアカウント削除に直結する。実際の本番DBの制約は未確認。

  • 重大
    User を消すと、ツールのメンバー行が持ち主を失って残る

    KintaiMember L2417、SfaMember L3131、ShodanMember L3388、AioMember L3521、MensetsuMember L3656、QuoteMember L3908、AishodanMember L4068、IncomeMember L5296、ExpenseMember L5676 の userId に外部キーが無い。HrOrganizationMember（L2139）だけは外部キーがある。

  • 重大
    「同じ人」を表す列が、外部キーの無い文字列になっている

    AccountCompanyMember.userId L5985、AccountCompanyMemberDepartment.userId L6092、AccountCompanyRecordAuthor.userId L6064、DoyaPowerStarterClaim.userId L6108。Web とアプリで同じ User ID を使う前提を、DB は守らない。

  • 重要
    会社のメンバーは、メールで招待して userId を後から入れる作り

    一意制約は (companyId, email) だけ（L5996）で、(companyId, userId) は無い（L5985）。同じ User が別メールの行で同じ会社に2回入る可能性がある（推測：アプリ側で防いでいるかは未確認）。User.email（L60）は DB 側で小文字にそろえる制約が無く、招待メールと Google のメールで大文字小文字が違うと一致しない可能性がある（推測）。

  • 重要
    契約の状態が4か所にある

    User の列 L140〜144、Subscription L205、UserServiceSubscription L171、account_company_billing L6004。ほかに HrOrganization L2114〜2118 と MitsuboshiNagusameSubscription L2082〜2084。plan の値の表記が表ごとに違う（L144、L178、L2083）。アプリ内課金を足すと5か所目になる。

  • 重要
    Stripe との結び付きが一意でない所がある

    Subscription.stripeCustomerId L212 は索引のみ、User.stripeCustomerId L140 は一意。account_company_billing.stripeSubscriptionId L6008 は索引のみで、同じ契約が複数の会社に付くことがスキーマ上は排除されていない。account_company_billing に Stripe の顧客IDの列は無い。

  • 重要
    持ち主が userId・organizationId・companyId で混在している

    会社と各ツールの組織は外部キーでつながらず、account_company_tool_orgs（L6074）の文字列でつなぐ。IncomeOrganization.companyId L5271 と ExpenseOrganization.companyId L5651 も外部キーなし。ドヤパワーは会社単位、旧プランは User 単位。

  • 重要
    未ログインの guestId から User へ引き継ぐ表・列が無い

    16モデルが guestId を持つ（SeoArticle L421 付近ほか）。引き継ぎ処理はコード側の話で、スキーマには痕跡が無い（推測：実装は未確認）。

  • 重要
    モバイルアプリ用のトークン・端末の表が無い

    端末の登録、リフレッシュトークン、プッシュ通知トークンの表が見当たらない（TenkaiApiKey は別物）。ログイン方法は Google OAuth だけで、Cookie のセッションが前提に見える（推測）。Apple でのログインを足すなら、同じメールの Account を結び付ける方針が要る（allowDangerousEmailAccountLinking は src/lib/auth.ts に無い）。

  • 軽微
    FKなしの子の表

    SfaAccount L3182 ほか7表（L3209・L3232・L3256・L3284・L3329・L3351）の organizationId、IncomeInvoiceSequence L5535。組織を消すとこれらが残る。

  • 軽微
    索引が足りない可能性

    Account L18 と Session L37 に userId の索引が無い（推測：行数が少ないうちは影響しない）。

  • 軽微
    トークンの保管

    Account.access_token・refresh_token・id_token（L24〜27）は Text で、暗号化の指定は見当たらない（推測：アプリ側で暗号化しているかは未確認）。

  • 軽微
    役割と状態の語がツールごとに違う

    KintaiMember L2422 は system_admin など、HrOrganizationMember L2146 は MEMBER、AccountCompanyMember L5986 は admin | member | guest。status も ACTIVE と active が混在。すべて文字列で列挙型ではない。

  • 軽微
    「消さない」を DB が守っていない

    DoyaPowerTransaction L6161 の「消さない・書き換えない」はコメントのみ。grantId L6170 は外部キーなし。AccountCompanyRoleEvent は DB のトリガーで守るとコメントにある（L6024）が、スキーマには現れない。

  • 軽微
    本番に無い表が混在している可能性

    会社のメンバーと課金の控え（L5976）、役割の3表（L6023）、ドヤパワー（L6121）、HomeAgentRun・HomeAgentTask（L6183）に「本番DBにはまだ無い」とのコメントがある。現在の本番の状態は未確認。

確かめきれなかった点

  • 本番 DB・Stripe・環境変数は読んでいません。本番に表があるか、実データの件数、実際の外部キーの制約は未確認です。
  • session.strategy を明示していないため、Session 表に実際に行が入るかは、実行を見ていません（NextAuth v4 の既定の挙動からの推測）。
  • User 削除の「子の子」までの全経路は追っていません（直接の子のみ）。
  • 退会・アカウント削除の処理、ゲストからの引き継ぎ処理が、アプリのコード側にあるかは確認していません。
