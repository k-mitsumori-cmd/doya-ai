## A. 重大（実装前に設計を直すべき）

### A-1. §11.5 step-up 再認証（Google `prompt=login` / `max_age=0` / `auth_time`）は Google では成立しない（推測・高確度）
- 場所: README §11.5、§9.1 `POST /api/auth/step-up`、§13 #34、schema-draft L811 `ReauthChallenge.authTime`
- 根拠: Google OIDC が公式にサポートする `prompt` は `none|consent|select_account` のみで `login` は未定義。`max_age` も Google の認可パラメータ一覧に無く、Google の ID トークンに `auth_time` クレームは含まれない（（推測）Google 公式ドキュメントの記憶に基づく。実装前に実機で id_token を decode して確認すること）。
- 何が起きる: 「`auth_time` が 5 分以内」を検証できないため step-up は常に失敗するか、検証をスキップして「再ログインしていないのに stepUpAt を更新」する形骸化した実装になる。§11.5 が守るとした支払い変更・メンバー削除・エクスポート・external 承認の全てに影響。
- 直し方: Google 経由の step-up は「新規 code 交換が成功し `sub` が一致」までを保証範囲とし（Google 側がセッション再利用すれば無音で通る点を明記）、本当に再認証を求めるなら WebAuthn/パスキー（`navigator.credentials`、`userVerification: 'required'`）を step-up 専用に追加する。`ReauthChallenge.authTime` は削除。

### A-2. `BillingAccount.stripeCustomerId @unique` と「会社の Customer＝旧 owner の Customer」「1 ユーザー会社 3 つまで」「個人会社自動生成」が両立しない
- 場所: schema-draft L318、README §7.2 手順 3、§7.1 個人利用、§7.4 `company.max_per_user` 既定 3
- 根拠: `prisma/schema.prisma` L140 `User.stripeCustomerId String? @unique`、L2107 `HrOrganization.stripeCustomerId String? @unique`。`src/app/api/hr/billing/checkout/route.ts` L66-141 は **User 側の** Customer を使う（設計書の記述どおり）。`stripe/webhook/route.ts` L200-203 のコメント「checkout は customer_email で都度 Customer を作るため顧客レコードが分裂」。
- 何が起きる: 同一 owner が「個人会社」＋「実会社」（または SFA 会社と HR 会社が名寄せされず 2 社）を持つと、同じ `stripeCustomerId` を 2 つの `BillingAccount` に書けず移行バッチが P2002 で停止する。逆に Customer が分裂しているユーザーは webhook の `metadata.companyId → BillingAccount.stripeCustomerId` 突合に失敗して `syncUnifiedBilling` へ落ち、会社契約が反映されない。
- 直し方: `BillingAccount.stripeCustomerId` の `@unique` を外し `@@index` に（または会社ごとに Stripe Customer を**新規作成**し、既存 Subscription は Stripe 側で `customer` 付け替え不可なので「次回更新時に新 Customer で再契約」を移行手順に明記）。webhook 突合は `metadata.companyId` を主キー、`stripeCustomerId` は補助に。

### A-3. schema-draft は「書いてある通り」には `prisma validate` を通らない
- 場所: schema-draft L775-795 `SessionDevice`（`user` relation 無し）、L893-894 の「User に追加」コメント `companyMemberships CompanyMember[]` / `sessionDevices SessionDevice[]`
- 根拠（実測）: 既存 schema＋draft を結合して `npx prisma validate`:
  - 結合のみ → `CompanyMember.user ... missing an opposite relation field on the model User`（User 側の追記がコメントにしか無いため、移植時に忘れると即失敗）。
  - コメント通り User に `sessionDevices SessionDevice[]` を足す → `The relation field sessionDevices on model User is missing an opposite relation field on the model SessionDevice`（`SessionDevice` に `user User @relation(...)` が無い）。
  - `SessionDevice.user` を補うと validate 通過（`prisma format` が補う差分も無し）。
- 直し方: `SessionDevice` に `user User @relation(fields:[userId], references:[id], onDelete: Cascade)` を追加。User/Session/Account への追加列はコメントではなく実際の model 断片として書き、結合 validate を CI（`verify-core-schema-draft.cjs` 等）で回す。

### A-4. `FeatureFlag @@unique([key, companyId])` は `companyId NULL` で一意にならない（全体フラグ・kill switch が重複可能）
- 場所: schema-draft L862-875
- 根拠: Postgres の UNIQUE は NULL 同士を区別する（既存 schema の `datasource provider = "postgresql"` L9-13）。`companyId String?` を含む複合 unique は「全体既定」行を何行でも作れる。
- 何が起きる: `agent.kill_switch` の全体行が 2 行でき、`findUnique`/`findFirst` がどちらを返すか不定。緊急停止が効かない／解除できない。
- 直し方: `companyId` を NOT NULL にして全体既定は `'*'` 等の番兵値にするか、`key` 単独 unique の `GlobalFeatureFlag` と会社別を分ける。`AuditLog`・`SecurityEvent` の `companyId?` も同様に「会社なし」の扱いを定義する。

### A-5. `Company` 配下の `onDelete: Cascade` が課金・監査・台帳を道連れにする（§10.6「3 年保持」と矛盾）
- 場所: schema-draft L71, L317, L338, L366, L419, L440, L696（`CompanyMember / BillingAccount / CompanySubscription / UsageLedger / AgentConversation / AgentRun / Notification` が Cascade）、L659 `AuditLog` は SetNull、README §10.6「3 年保持（会社削除後も匿名化して保持）」、§13 #35「purge は専用バッチで順序固定」
- 何が起きる: Phase4 の purge バッチや運用ミスで `Company` を物理削除すると `UsageLedger`（課金の正本）・`CompanySubscription`・全 `AgentRun/ToolCall` が消え、`AuditLog` は `companyId=NULL` になって「どの会社の記録か」を失う。連鎖ハッシュ（§10.6）も会社キーを失い検証不能。
- 直し方: 課金・監査・台帳系は `onDelete: Restrict`（削除を拒否）にし、論理削除のみ許す。`AuditLog.companyId` は FK を外して文字列保持（SetNull を使わない）。

### A-6. middleware 既定拒否の許可リストに、実在する公開ルートの漏れが多数（確認済み）

- 根拠（`getServerSession`/`CRON_SECRET`/admin ガードのいずれも無い route.ts を実測）:

  - `/api/drip/unsubscribe`（配信停止。401 は特商法/迷惑メール対策上も問題）
  - `/api/inbound-email`（`x-inbound-secret` で守る受信 webhook）
  - `/api/service-activity`, `/api/operational-error`（`x-client-error-token` で守る外部アプリ受け口）
  - `/api/interviewx/public/[token]/*`（5 ルート、ゲスト回答）
  - `/api/hr/organization/invite/[token]` GET（招待確認。sfa 等は session 有り、hr は無し）
  - `/api/seo/preview`, `/api/banner/image`, `/api/doyaslide/style-preview`, `/api/banner/test/health`, `/api/tenkai/health`, `/api/aishodan/scenarios/[id]/preview` 以下の公開配信系
  - 設計書は `/api/feedback/report` と書くが実在は `/api/feedback`（session 有り）。`/api/health` は実在。
  - 画面: `/m/[token]`, `/interviewx/respond/[token]`, `/shodan/[orgSlug]/p/[id]`（公開提案ページ）, `/cunning/live`, 各 `/<svc>/invite/[token]`, `/privacy`, `/aishodan/preview`, `/banner/landing`
- さらに重要: 設計書は「`/api/seo/guest/*` 等を個別列挙」とするが **そのようなパスは存在しない**。ゲスト（`guestId` Cookie）は `/api/seo/articles`, `/api/seo/articles/[id]/outline`, `/api/interview/projects`, `/api/swipe/*`, `/api/copy/*`, `/api/movie/*`, `/api/adimage/concepts` 等 **ログイン済みと同じルート** を共有している（grep `guestId` 54 ルート）。「セッション Cookie の存在」を Edge で要求すると seo/interview の「1 時間お試し」が丸ごと 401 になる。

### A-7. Phase3 以降に新規作成される `Company` には旧 `*Organization` が無く、既存 577 ルートが `organizationId=null` で動かない
- 場所: README §6.2「`organizationId` には `CompanyContext.legacy.organizationId` を入れる」、§6.4 手順 6「`getOrCreateOrganization` は 409 で `/api/company` POST へ誘導」、§12 Phase3
- 根拠: 全組織型サービスの route は `ctx.organizationId` で `where` を書く（例 `src/lib/quote/document.ts` L14 `nextQuoteNo(organizationId)`、`src/lib/aio/dashboard.ts` `readAioDashboard(orgSlug)`、`src/lib/promane/timesheet-read.ts` L25 `workspaceSlug`）。Phase4 まで旧モデルは残る前提。
- 何が起きる: Phase3 で `/api/company` 経由で作られた会社は `CompanyServiceLink` が無い → `legacy.organizationId = null` → 旧 route 全部が 500 か空結果。§5.1 の「メンバー 1 人・データ 0 の組織は Company 化しない」と合わせると、既存の個人ユーザーが Phase3 以降に初めて SFA を開いた瞬間に 409 で行き止まり。
- 直し方: Phase2〜4 の間は **逆方向の二重書き込み**（`Company` 作成時・サービス有効化時に旧 `*Organization` と owner Member を自動生成し `CompanyServiceLink` を張る）を必須にする。`getOrCreateOrganization` は 409 ではなく「Company を確保してから旧組織を作る」ラッパーに置き換える。

### A-8. 承認後・Cron 回収時の「依頼者の権限で再評価」が、設計した `requireCompanyAccess` の署名では呼べない
- 場所: README §6.2（`getServerSession` → Session 行 → `Session.companyId` 前提）、§8.5「`requireCompanyAccess(serviceId, tool.minServiceRole, {userId: run.requestedBy})`」、§8.4 Cron 回収
- 何が起きる: Cron（`/api/cron/agent-runs`）や承認者のリクエストで advance する時、依頼者のセッションは存在しない。`opts.userId` は §6.2 の `opts` に無い。`stepUpAt` も Session 列なので「承認に step-up が要る」を依頼者以外で評価できない。実装者が `getServerSession` をスキップする「裏口」を作ることになり、既定拒否の原則が最初に崩れる場所になる。
- 直し方: セッション非依存の `evaluateCompanyAccess({userId, companyId, serviceId, minRole})`（純関数＋DB 1 クエリ）を core に分離し、`requireCompanyAccess` はその薄いラッパーにする。エージェントは前者だけを使い、`actorSnapshot` との差分は「縮小方向のみ反映」と明記。

### A-9. 外部影響ツールの冪等キーに `attempt` が含まれており、再試行で有料 API が二重実行される
- 場所: schema-draft L558 `idempotencyKey "<runId>:<stepId>:<attempt>"`、README §8.4「再試行で二重作成しない」
- 何が起きる: `aio.runScan`（4 社の有料 LLM）、`banner.generate`、`shodan.generateSlides` がタイムアウト後に attempt+1 で再実行されると下流キーも変わり、2026-08-24 の gpt-image-1 事故と同型の多重課金になる。
- 直し方: external は `runId:stepId` 固定（attempt は `ToolCall.attempt` 列に）。`ToolCall` の unique は `@@unique([stepId, attempt])` に分離。

### A-10. ツール登録のリスク区分に「有料 LLM を承認なしで大量に回す」ものが混在

## B. 中

### B-1. セッション失効（`revokedAt` / `sessionsInvalidBefore`）を NextAuth `session` コールバックで検査しても、失効を「返せない」
- 場所: README §6.2 処理順 1、§11.3 手順 3、§11.6
- 根拠: `node_modules/next-auth/core/routes/session.js` L98-125: DB 戦略では `adapter.getSessionAndUser` が返した行を `callbacks.session` に渡し、戻り値をそのまま返す。コールバックに「セッション無効」を表す戻り値は無い（空オブジェクトを返しても Cookie は残る）。
- 何が起きる: `requireCompanyAccess` を通らない 590 ファイル（`@/lib/prisma` 直 import、実測）とユーザー単位 10 サービスでは失効済みセッションが生き続ける。
- 直し方: `PrismaAdapter` をラップし `getSessionAndUser` で `revokedAt IS NULL AND createdAt > sessionsInvalidBefore` を満たさない場合 `null` を返す（NextAuth が Cookie を消す）。設計書の「コールバックで積み、ここでは再読しない」は adapter 側に移す。

### B-2. テナント Prisma 拡張 `rewriteUniqueToScoped` は戻り値・型・複合 unique を壊す
- 場所: README §10.2 コード、§13 #37
- 根拠: `update/delete → updateMany/deleteMany` は `{count}` を返しレコードを返さない。`findUnique({ where: { userId_serviceId } })` のような複合 unique、`include/select`、`upsert`、`$transaction` 内の `tx`（拡張クライアントで `$transaction` すると `tx` も拡張されるが、既存 `prisma.$transaction` 経由は素通り）が未定義。`SeoJob` のリース取得は `$queryRaw`（`seo/lib/job-execution.ts` L20-30）で拡張をすり抜ける。
- 直し方: `update/delete` は「`findFirst` で所属確認 → 元の `update`」の 2 クエリにする（戻り値維持）。raw SQL は別途 lint で `companyId`/`organizationId` 条件の明示を要求。

### B-3. ユーザー単位モデル（`Generation`, `SeoArticle`, `AdImageBrand` 等）は「個人会社」化してもテナント列が無く、拡張で守れない
- 場所: README §6.4 手順 5、§10.2 `TENANT_MODELS`
- 根拠: `User` 配下の 1:N モデル多数（schema L68-120）。`TENANT_MODELS` は `companyId | organizationId | workspaceId` の 3 種しか想定していない。
- 直し方: `userId` を第 4 のテナント列として `expected = ctx.userId` に写像するか、これらはスコープ外と明記する。

### B-4. `CompanyServiceLink @@unique([companyId, serviceId])` と owner-email 名寄せが衝突する
- 場所: schema-draft L189、README §5.1 名寄せ 1
- 何が起きる: 同じ owner が同一サービスに 2 組織（例: SFA を 2 つ）を持つと、名寄せで同じ `Company` に 2 本目の Link を張れず移行バッチが止まる。「空組織は Company 化しない」ルールで一部は回避できるが、両方にデータがあるケースの扱いが未定義。
- 直し方: unique を `[serviceId, legacyOrganizationId]` だけにし、1 会社 N 旧組織を許す（読み替え時は `isPrimary` を持つ）か、該当ケースを「人が決める」行列に必ず落とす。

### B-5. `CompanyMember @@unique([companyId, userId])` ＋「removed 行は残す」で再招待が P2002
- 場所: schema-draft L84-85, L100、README §11.6
- 直し方: 受諾 API を「既存 removed 行があれば `status=active, removedAt=null` に更新」の upsert に規定し、`verify-billing-seat-limit.cjs` に再入社ケースを追加。

### B-6. `CompanyInvitation` に `(companyId, email, status=pending)` の一意性が無い
- 場所: schema-draft L127-148
- 何が起きる: 同じメールに pending 招待が複数でき、席上限チェックが招待単位で擦り抜ける。

### B-7. `User` 削除 Cascade で owner が消え、owner 不在の会社ができる
- 場所: schema-draft L76 `CompanyMember.user onDelete: Cascade`、README §9.1「owner 降格は別 owner が居るときのみ」
- 直し方: `Restrict` にし、ユーザー削除 API 側で「owner なら先に移譲」を強制。

### B-8. `AgentRun.requestedBy / ApprovalRequest.requestedTo / AgentConversation.userId / Notification.userId / UsageLedger.userId` に FK が無い
- 場所: schema-draft L442, L591, L420, L697, L368

### B-9. Stripe webhook の既存ロジックは `metadata.app === 'doya-ai'` と `metadata.userId` 一致を要求しており、会社 Checkout が無音で捨てられる
- 場所: README §7.3

- 直し方: `handleCheckoutCompleted` の冒頭で `metadata.companyId` 分岐を入れる位置を明記し、会社 Checkout の metadata 仕様（`app='doya-ai', companyId, userId(操作者)`）を固定。

### B-10. 席数（`seats`）と Stripe `quantity` の同期が未設計

### B-12. `x-vercel-cron` ヘッダは存在しない（推測）
- 場所: README §6.5「`timingSafeEqual`＋`x-vercel-cron` ヘッダ確認」
- 根拠: 既存コードで `x-vercel-cron` の利用は 0 件。Vercel Cron は `Authorization: Bearer $CRON_SECRET` と `user-agent: vercel-cron/1.0` を付ける（（推測）公式仕様の記憶）。ヘッダを必須にすると 35 本全部が 401。
- 直し方: `requireCron` は Bearer の `timingSafeEqual` のみ。UA は参考情報。

### B-13. Vercel Cron の本数上限に近づく（推測）
- 新規 3 本（`agent-runs`, `security-scan`, `audit-verify`）で 35→38。Pro プランの上限 40（（推測））に迫るため、既存の `*/15` 5 本・`*/5` 4 本の統合を先に検討。設計書の「`*/5` が 5 本」は実測 **4 本**。

### B-14. advance の壁時計 240 秒と、LLM リトライ仕様が両立しない
- 場所: README §8.3「429/5xx/timeout は指数バックオフ 3 回、その後プロバイダ・フォールバック」、§8.4「LLM は 60s」「ツール external 120s」「最大 4 並列」
- 何が起きる: 1 回 60s × 3 回 ＋ フォールバック 1 回 ＝ 240s を 1 step で使い切り、`maxDuration=300` の関数ごと落ちてリースが残る（§13 #15 の「1 step が 300s を超えると死ぬ」をそのまま踏む）。
- 直し方: run 全体の `AbortSignal` を advance 入口で作り、LLM・ツールの timeout は「残り時間 − 安全余裕」で動的に決める。

### B-15. `CompanyProfile` 自体が外部由来テキストから作られているのに、エージェントは「信頼できるデータ」として毎回読む
- 場所: README §8.2 `company.getProfile`（全 run の最初に自動呼び出し）、§8.5 プロンプトインジェクション (1)
- 根拠: `src/lib/shodan/ai.ts` L239 `draftOwnProfile(research)` は自社サイトを `safeFetchText` で取得した本文から LLM で生成（`research.ts` L228-230）。`MensetsuCompanyProfile` も `sourceUrl` 由来。
- 直し方: `CompanyProfile.fieldSources` に `origin: 'scraped' | 'human'` を持ち、scraped 由来の列は `<untrusted>` で包む。

### B-16. エージェントのコスト計測が初期フェーズでは実質ゼロ
- 場所: README §7.4「LLM 実コストは `LlmCallLog.costMinor` に記録」、§8.3「既存 29 直接 fetch はこの設計の必須作業ではない」
- 根拠: ツールが呼ぶ `nanobanner.ts`, `shodan/ai.ts`, `gemini-text.ts`, `doyalist/collect/web-scraper.ts` は gateway を通らない。`LlmCallLog` に残るのはプランナーの呼び出しだけで、予算超過検知（`creditBudget`）は静的見積りのみ。
- 直し方: Phase3a の前に、ツールが呼ぶ lib の LLM 呼び出しだけは gateway 経由に寄せる（優先順を §8.3 に追加）。

### B-17. 同時セッション「2 端末」既定は、モバイルのアプリ内ブラウザ・プライベートウィンドウで誤ロックアウトを量産する
- 場所: README §11.3
- 根拠: `doya_device` Cookie は Cookie jar 単位。LINE/Instagram のアプリ内ブラウザ、Safari と Chrome、PWA は同じスマホでも別端末として数えられる。「PC 1＋スマホ 1」の想定どおりには動かない。
- 直し方: 既定 3〜4、`SessionDevice.kind` を UA から推定して「同一 kind の置換」を優先、Phase3 の強制前に通知のみ期間の失効候補件数を集計して閾値を決める。

### B-18. `Session` テーブルへの `@@index` 追加は書き込み中のホットテーブルをロックする
- 場所: README §12 Phase1（Session 拡張列・index）、§13 #14
- 根拠: `prisma db push` は `CREATE INDEX CONCURRENTLY` を使わない。`Session` は `updateAge: 60`（`src/lib/auth.ts` L189）で全ユーザーが 1 分ごとに UPDATE する。
- 直し方: Session/User の index は `doya-db-push` とは別に手書き SQL `CREATE INDEX CONCURRENTLY` で先行作成し、その後 `db push` に合わせる手順を Phase1 に明記。`AuditLog` の 5 本の index も同様に段階追加。

### B-19. `AuditLog` 連鎖ハッシュの `FOR UPDATE` 直列化と `connection_limit=3` の相性
- 場所: README §10.6、§13 #38
- 根拠: `src/lib/prisma.ts` L39-45（`pgbouncer=true`, `connection_limit=3`）。全 ToolCall・全機微 GET・全会社変更で会社ごとに head 行をロックすると、4 並列ツール×2 run で接続を食い尽くす。
- 直し方: 連鎖ハッシュは同期 INSERT ではなく、`AuditLog` を追記した後に日次 cron でバッチ連鎖（「次の行」が確定してから hash を埋める）にするか、ハッシュ対象を会社設定・課金・メンバー変更に限定。

### B-20. CSRF 対策の `x-requested-with` 必須化は既存フロントの fetch 全部を壊す
- 場所: README §10.7 CSRF
- 根拠: `src/lib/org-fetch.ts` は `fetchOrgJson`（GET 専用、12 行）のみで、状態変更 API の呼び出しは各画面の生 `fetch`。付与を必須にした瞬間に POST が全滅する。
- 直し方: `Origin`/`Sec-Fetch-Site` 検査（ブラウザが自動付与）だけを必須にし、カスタムヘッダは report-only→段階導入。

### B-21. `CompanySubscription.currentPeriodStart/End` NOT NULL と Stripe API の変更（推測）
- 場所: schema-draft L347-348
- 根拠: 依存 `stripe ^14.10.0`（旧 API 版固定）。Stripe API 2025-03 以降は `current_period_*` が Subscription から Item へ移動している（（推測））。SDK を上げた瞬間に NOT NULL 違反。nullable にしておく。

### B-22. `KnowledgeSource.rawText String @db.Text` NOT NULL で `type=url` の未取得状態を表せない／`RateLimitBucket.updatedAt @updatedAt` は raw `UPDATE ... RETURNING` では更新されない
- 場所: schema-draft L278, L855。小さいが「設計どおり実装すると動かない」類。

### B-23. 移行 SQL の表名
- 場所: README §5.1 Kintai 行「`FROM kintai_members m LEFT JOIN "User"`」
- 根拠: 既存 schema は `@@map` を 157 箇所使うが、`KintaiMember` の実表名は確認が必要（Prisma 既定なら `"KintaiMember"`）。ドライランスクリプトは Prisma 経由で書く方が安全。

### B-24. Phase2 ロールバック後の再開に再同期手順が無い
- 場所: README §12 Phase2「`core.dual_write` OFF で旧書き込みのみ」
- 何が起きる: OFF の間に旧 Member が変わると `CompanyMember` が古くなる。再 ON 時の reconcile（旧→新の差分適用）が無いと、shadow 差分 0 件が二度と達成できない。`scripts/ops/tenant-reconcile.ts` を追加。

### B-25. 設計の「Session.companyId を既定、`?company=` が最優先」は IDOR ではないが、リンク誘導で会社切替が起きる
- 場所: README §6.2 処理順 2
- 所属チェックがあるので越権はしない（既存 `orgSlugFrom` と同じ）が、`?company=` がセッションより優先されるため「別会社で作業中に貼られたリンクを踏んで別会社に書き込む」事故が残る。書き込み系では `?company=` と `Session.companyId` の不一致を 409 にする。
