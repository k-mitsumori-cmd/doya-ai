## 0. 完成の定義（2026-10-19 追加。ユーザーの指示による再発防止）

UI の作業は、次をすべて満たして初めて完成とする。ビルドの成功・エラー0件・点検の S 級 A 級 0 件だけでは完成としない。

1. ログインした状態で 375px と 1280px のスクリーンショットを撮り、見本（/ui-renewal）と並べて比べる。差があれば完成としない
2. 切り替えを確かめる。読み込みは中身の場所だけに出る、全面が青くならない、ちらつかない、表示がずれない（CLS を測る。0.1 未満）
3. アニメーション、日本語の改行（1文字だけの行を出さない）、キービジュアル・空状態の画像の有無を確かめる
4. デザインの点検役（高性能のモデル）が、スクリーンショットを見て批評し、毎回改善の提案を10件以上出す
5. 完了の報告には、毎回「まだ良くない点」と「次の改善の提案」を添える

この文書は、§1 ユーザーの指摘、§2 こちらで見つけた問題（下の「調べて分かったこと」）、§4 改善の提案、の3つに分けてある。

## 3. チェックリスト（直す順）

### P0: 切り替え・読み込み・ちらつき（共通の部分。共通部品の担当）

- [ ] **C-1** 組織を選ぶ入口（`/shodan`・`/aio`、今後増えるもの）を、全画面の読み込みにしない。入口のリダイレクトはサーバー側（server component の `redirect()`）で行い、最後に使った組織へ直接移る。左のメニューのリンク先も、最後に使った組織のページにする（F-1・F-2）
- [ ] **C-2** 枠の中のツールの部品と、ページ本体の `h-screen` / `min-h-screen` / 全画面の読み込みを、枠に入ったときだけ外す。枠の中の読み込みは、中身の領域（ToolFrame の body）にだけ出す（F-3〜F-5）
- [ ] **C-3** 全ツールの route に `loading.tsx` を置き、中身の領域に骨組み（`ds/Skeleton`）を出す。外枠・左のメニュー・見出しは消さない（F-7）
- [ ] **C-4** `src/app/(shell)/template.tsx` で、中身の入れ替えに短い入りのアニメーション（不透明度＋ 4〜8px の上下、180ms）を付ける。`prefers-reduced-motion` では動かさない。Next.js 15 の View Transitions（実験機能）は、安定するまで使わない（F-6）
- [ ] **C-5** 左のメニューを押した瞬間に、選択の表示を変える。`<Link prefetch>` を付ける（F-6）
- [ ] **C-6** 利用量のパネルは、枠の側で1回だけ作り、ページが変わっても作り直さない。数字だけを更新する（F-15）
- [ ] **C-7** バナーの dashboard が、旧来の DashboardLayout を出さないようにする。枠が有効なときは、すべての画面で BannerShellFrame（ToolFrame）にする（F-8）
- [ ] **C-8** 確かめ方: 本番の形（`next start`、UI_SHELL_SERVICES=all）で、全ツールの間を左のメニューで移り、150ms ごとの記録で「全画面の読み込み」「外枠の消失」「色の全面の変化」が0回であること。375px と 1280px

## 5. 開発基盤の計画の 2 番を最優先にする案

今回の品質の問題は、ログインした後の画面を、本番に出す前に確かめる場所が無いことが根にある。クラウドのセッションも、どれもログイン後の画面を見られなかった。そこで、開発基盤の計画（ブランチ docs/dev-foundation の `docs/architecture/dev-foundation-plan.md` §2）のうち、次を UI の直しより先に行うことを提案する。

| 順 | やること | 工数 | 月額 | 決めてほしいこと |
|---|---|---|---|---|
| 1 | 検証用の DB（Supabase の別プロジェクト）を作り、テスト用の組織・ユーザー・各ツールの見本データを種まきスクリプトで入れる | 1.5 日 | 約 1,500 円 | 別プロジェクトにしてよいか |
| 2 | Vercel の Preview の環境変数を、検証用 DB・Stripe のテストモード・検証用のストレージに向ける。従量課金の AI は Preview では止める | 0.5 日 | 0 円 | — |
| 3 | Preview だけで有効な「メールとパスワードのログイン」を足す（`VERCEL_ENV !== 'production'` のときだけ）。本番で読み込まれないことを CI で確かめる | 1 日 | 0 円 | この方式でよいか |
| 4 | これで、PR ごとのプレビューの URL で、ログイン後の全画面を 375px と 1280px で確かめられる。§0 の完成の定義の 1〜3 を、ここで行う | — | — | — |

合計で約3日、月額は約1,500円の見込み。

**決定（2026-10-19）: 見送り。** ユーザーの原文は「検証用のDBとテスト用のログインは、今は見送ってください。」。代わりに、次の手順で確かめる。

- ログインした画面は、ユーザーのアカウントでログイン済みの Claude アプリの内蔵ブラウザで、本番を見てスクリーンショットを撮る。データを作る・変える・消すボタンと、課金が発生する操作（画像生成・AI の実行）は押さない
- 本番に出す前の確認ができないので、各ツールの直しは「スイッチ（UI_SHELL_SERVICES）で戻せる」形を保つ。本番に出したら、すぐに内蔵ブラウザで確かめ、問題があればスイッチで戻す
- §4.1 の24画面の点検は、この手順で行った

### 5.1 本番の中のプレビューの切り替え（2026-10-19 決定。ユーザーの原文「公開するまでにプレビューで教えてください」「おすすめで進めてください」）

直した見た目は本番に入れるが、ふつうの利用者には今の画面のまま見せる。ユーザー本人のアカウントだけが、切り替えて新しい見た目を確かめられるようにする。ユーザーの確認が済んだら、スイッチで全員に出す。

| 部品 | 中身 |
|---|---|
| 環境変数 `UI_NEXT_ROLLOUT` | `off`（新しい見た目を誰にも出さない）／`preview`（切り替えた管理者だけ）／`all`（全員）。既定は `preview` |
| 環境変数 `UI_PREVIEW_EMAILS` | 新しい見た目を見てよい人のメール（カンマ区切り）。最初はユーザー本人だけ |
| `src/lib/ui-next.ts` の `isUiNext()` | サーバー側で判定する。`all` なら真。`preview` なら、cookie `doya_ui_next=1` があり、かつログイン中のメールが `UI_PREVIEW_EMAILS` にあるときだけ真。メールは毎回サーバーで確かめるので、ほかの人が cookie を手で付けても、今の画面のまま |
| `/api/ui-preview?on=1`（`?on=0` で戻す） | ログイン中で、メールが `UI_PREVIEW_EMAILS` にある人だけが使える。cookie を立てて（httpOnly・secure・sameSite=lax・30日）、元のページへ戻す。それ以外の人には 403 |
| 画面の右下の小さな札 | 新しい見た目のときだけ「新しい見た目で表示中」と「元に戻す」を出す |
| 直した見た目の分け方 | P0 などの直しは、`isUiNext()` が真のときだけ使う。サーバーの layout で判定し、クライアントの部品には props か context で渡す |
| テスト | `isUiNext()` の組み合わせの単体テスト。許可されていないメールの人が cookie を付けても今の画面のままであることの、セキュリティの回帰テスト |
| 全員に出すとき | `UI_NEXT_ROLLOUT=all` にして再デプロイする。戻すときは `preview` か `off` に戻して再デプロイする（コードは戻さなくてよい） |

ユーザーに見てもらう手順: ログインしたブラウザで `https://doya-ai.surisuta.jp/api/ui-preview?on=1` を開く → 新しい見た目になる → 見てほしい画面の一覧を順に開く → `?on=0` で元に戻る。

この仕組みを本番に入れること自体は本番の変更なので、統括のセッションでユーザーの承認を得てから入れる。
