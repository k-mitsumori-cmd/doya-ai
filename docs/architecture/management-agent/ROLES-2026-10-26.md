# 会社の中の権限（オーナー・管理者・マネージャー・メンバー・ゲスト）の仕様（2026-10-26）

- ブランチ: `claude/doya-roles-a3caa7`（origin/main `2f873e53` から）。main には入れていない
- 判定の関数: `src/lib/company-roles/`（テスト: `npm run test:roles`）
- 旗: `COMPANY_ROLES_ROLLOUT`（off / shadow / preview / all。既定は off）
- **⚠️ スキーマは案だけ。** 本番DBには流していない。流す SQL は §8。統括がユーザーの承認を取ってから流す
- 前提: 新しい料金のブランチ（`claude/doya-new-pricing-dd27ff`）が足す `account_company_members` の上に作る

## 0. 要点

- ユーザーの依頼（2026-10-26）は「社員が勤怠などを全部直せないように、オーナー・依頼者・メンバーの権限を調整できるようにしたい」というものです。
- 今の各ツールの API には、社員が勤怠を直接直せる道はありませんでした（§2）。困るのはこれからです。会社にメンバーを招く作り（新しい料金）が入ると、会社の誰がどこまでできるかを決める場所が無いまま、人が増えます。
- そこで、会社単位の役割を5つ置きます。オーナー・管理者・マネージャー・メンバー・ゲストです（§1）。
- 会社の役割は、各ツールの役割の「上限」として使います。ツールの中で使える役割は、ツールの役割と会社の上限の低いほうです（§4）。会社の役割で、ツールの役割が上がることはありません。
- 判定はサーバーだけで行います。旗が off のあいだは何も変わりません。shadow で「止めるはずだった操作」を記録して確かめてから、止める側に切り替えます（§5）。

## 1. 今の権限の作り（調べた結果）

### 1.1 ツールごとの役割

| ツール | 組織とメンバーの表 | 役割の値（低い順） | 判定の関数 |

| HR | `HrOrganization` / `HrOrganizationMember` | MEMBER < MANAGER < ADMIN < OWNER（大文字） | `src/lib/hr/access.ts` の `hasMinRole`、評価は `evaluation-access.ts` |
| プロマネ | `PromaneWorkspace` / `PromaneMember` | guest < member < admin < owner（順番の表は無く、配列で判定） | `src/lib/promane/auth.ts` |
| 経費（支出の管理） | `ExpenseOrganization` / `ExpenseMember` | member < manager < admin < owner | `src/lib/expense/access.ts`、`member-policy.ts` |
| 収入 | `IncomeOrganization` / `IncomeMember` | member < manager < admin < owner | `src/lib/income/roles.ts` |
| 見積 | `QuoteOrganization` / `QuoteMember` | member < manager < admin < owner | `src/lib/quote/types.ts` |
| 営業管理・商談・AI 診断・面接・AI 商談 | `Sfa*` / `Shodan*` / `Aio*` / `Mensetsu*` / `Aishodan*` の Member | member < manager < admin < owner | 各 `src/lib/{svc}/types.ts` |
| 運営 | `User.role` | USER / ADMIN（運営の管理画面だけ） | `src/lib/admin-auth.ts` |

- どのツールも「組織を作った人がそのツールの最上位」になり、ほかの人はツールごとに招待されます。ツールの組織どうしはつながっていません。
- 会社（`account_companies`）には、会社単位の役割がありません。`userId` が unique なので、1人に1社です（2026-10-19 のユーザーの判断「1アカウント1会社」）。
- 新しい料金のブランチが `account_company_members` を足します。役割は admin / member の2つだけで、今は持ち主しか管理できません（PRICING-NEW の B7・F5 で「未決」）。
- 会社のメンバーとツールの役割は、まだつながっていません。会社に入っても、各ツールでは別に招待されるまで何もできません。

### 1.2 料金・ドヤパワー・エージェント

- 料金と支払いは、すべて本人（`User.plan`）単位です。会社の誰かが、ほかの人の契約を変える道はありません。HR だけは、組織の OWNER しか Checkout できません。
- ドヤパワーは、本人が持ち主の会社の分だけを読みます（`src/lib/doya-power/charge.ts`）。body の companyId は受け取りません。追加購入の API は main にまだありません（新しい料金のブランチで、持ち主だけが買える形で作っています）。
- エージェントの実行は本人単位です。道具の呼び出しは本人の cookie で各ツールの API を呼ぶので、各ツールの判定がそのまま効きます。

### 2.1 勤怠（15本）

| 操作 | API | 通る役割 | 結果 |
|---|---|---|---|
| 打刻 | `POST /api/kintai/clock` | 有効な社員なら誰でも | 時刻はサーバーの今だけ。社員の番号はログインした人に固定 |
| 勤怠の直接の修正・上書き | なし | — | 勤怠を直接書き換える API が無い。勤怠は「打刻」「再計算」「申請の承認」でしか変わらない |

| 申請 | `POST /api/kintai/requests` | 有効な社員なら誰でも | 自分の分だけ。打刻の修正は未来の時刻を拒む |

| 社員の登録・変更・無効化・招待 | `/api/kintai/employees/**` | hr_admin 以上 | 自分の役割は変えられない。同じか上の役割は付けられない |
| 部署・就業ルール | `/api/kintai/departments/**`・`work-rules/**` | hr_admin 以上 | すべて組織の二重条件あり |
| 招待の受け入れ | `POST /api/kintai/invite/[token]` | 招待のメールと同じ人 | 役割は招待のときのまま。受け入れる側では変えられない |

見つかった点:

| 重さ | 内容 | 場所 |
|---|---|---|
| 中 | hr_admin が、同じ hr_admin を DELETE で無効化できる。PATCH では「同じか上の人は変えられない」で止まるのに、DELETE だけ止まらない | `src/app/api/kintai/employees/[id]/route.ts` の DELETE（195 行付近） |
| 低 | 招待中の社員のメールを PATCH で直しても、前のメールの招待リンクが使える | 同じファイルの PATCH と `invite/[token]` |
| 低 | manager は、同じ部署なら上の役割の人の申請も承認できる | `requests/[id]/route.ts` |
| 低 | 承認のコメントと申請の中身に長さの上限が無い | `requests/route.ts`・`requests/[id]/route.ts` |

社員（employee）や manager が、他人や自分の勤怠を不正に直せる道は見つかりませんでした。中の1件は管理者どうしの話なので、旗とは別の小さな直しとして出します（§10）。

## 3. 会社の役割と「できること表」

### 3.1 役割

| 役割 | できること | 人数 |
|---|---|---|
| オーナー | 契約と支払い、ドヤパワーの追加購入、役割の変更、会社の削除 | 会社に1人（`account_companies.userId`） |
| 管理者 | すべてのツールの設定と承認、ほかの人のデータの修正、メンバーの招待 | 何人でも |
| マネージャー | 自分の部署の人の申請の承認。ほかの人のデータは直せない | 何人でも |
| メンバー | 自分のデータだけ。勤怠は打刻と申請だけで、直接は直せない | 何人でも |
| ゲスト | 共有された画面を見るだけ | 何人でも |

決まり:

- 自分で自分を承認できません。管理者も同じです。会社に1人しかいない場合のために、オーナーだけは自分の分を承認できます（記録には残します）。
- 自分の役割は変えられません。管理者は、自分より下の役割の人しか変えられず、自分より下の役割しか付けられません。
- オーナーの役割は、招待や変更では付けられません。引き継ぎは別の手順です（新しい料金の B9 と同じく、契約が移るので運営の手作業にする案）。
- 知らない役割の値は、いちばん低いゲストとして扱います。

### 3.2 「依頼者」の扱い（ユーザーに確認したいこと）

ユーザーの言葉「オーナー権限と依頼者とそのメンバー」の「依頼者」は、次の3つのどれかだと考えます。

| 案 | 依頼者とは | この仕様での扱い |
|---|---|---|
| A | ドヤAI に申し込んだ人（契約した人） | オーナーと同じ。会社に1人 |
| B | 申請やエージェントの仕事を頼む人（社員の側） | 役割ではなく、操作の立場。申請を出す人は承認できない（§3.1）。エージェントは頼んだ人の権限で動く（CHECKLIST AGT-08 と同じ） |
| C | 社外の人（取引先・外注先など、仕事を頼んでくる人） | ゲスト。共有された見積や案件を見るだけ。会社の席には数えない案もある |

おすすめは「A をオーナー、B は操作の立場として決まりに入れる、C はゲスト」です。3つとも、この仕様の5つの役割で表せます。

## 4. 各ツールの役割とのつながりと移行

### 4.1 上限の表

ツールの中で使える役割は、ツールの役割と、下の表の上限の低いほうです（`effectiveToolRole`）。

| 会社の役割 | 勤怠 | HR | プロマネ | そのほか（owner/admin/manager/member） |
|---|---|---|---|---|
| オーナー | system_admin | OWNER | owner | owner |
| 管理者 | hr_admin | ADMIN | admin | admin |
| マネージャー | manager | MANAGER | member | manager |
| メンバー | employee | MEMBER | member | member |
| ゲスト | employee（見るだけ） | MEMBER（見るだけ） | guest | member（見るだけ） |

- 例: 勤怠で system_admin の人でも、会社でメンバーなら、勤怠の中では一般（employee）として扱います。
- ツールの役割の文字列は変えません（HR の大文字、勤怠の hr_admin）。各ツールの今の `hasMinRole` と組織の二重条件は、そのまま残します。

### 4.2 今の会員を新しい役割に割り当てる

1. 会社の持ち主（`account_companies.userId`）がオーナーです。最初の人です。
2. `account_company_members` の行の役割（新しい料金の admin / member）は、そのまま引き継ぎます。
3. それぞれの人について、会社のツールの組織（オーナーが入っている組織）での役割を写して、いちばん高いものを「案」にします（`proposeCompanyRole`）。

| ツールの役割 | 会社の役割の案 |
|---|---|
| 勤怠の system_admin・hr_admin、HR の OWNER・ADMIN、ほかの owner・admin | 管理者（オーナーにはしない） |
| 勤怠の manager、HR の MANAGER、ほかの manager | マネージャー |
| 勤怠の employee、HR の MEMBER、ほかの member | メンバー |
| プロマネの guest | ゲスト |

4. 案と今の役割が違う人、旗を on にするとツールの中の役割が下がる人（`wouldBeClamped`）を、オーナーに一覧で見せます。オーナーが決めるまで、自動では書きません。
5. 決めた結果は、役割の変更の記録（`kind = migrated`）に残します。

注意: 自分でツールの組織を作った人は、その組織の最上位です。会社の組織と別なら、会社の役割の案には数えません。

| shadow | 判定するが止めない。止めるはずだった操作を `[company-roles:shadow]` としてログに出す |
| preview | `UI_PREVIEW_EMAILS` の人だけ止める。ほかの人は shadow と同じ |
| all | 全員止める |

決まり:

- 会社の役割は userId だけから決めます。body や query の companyId・role は信じません。
- 持ち主ならオーナーです。行に owner と書かれていても、持ち主でなければオーナーにしません。
- 止める側（preview・all）で DB が読めないときは、止めます。shadow では今のまま通します。
- API での使い方は、各ツールの今の判定の前に1行足す形です。

```ts
const auth = await authorizeCompanyActionForSession({ userId, email, permission: 'kintai.request.approve.department', target: { isSelf, sameDepartment } })
if (!auth.allowed) return NextResponse.json({ error: 'この操作の権限がありません。会社の管理者に依頼してください。' }, { status: 403 })
```

- 部署が同じかどうかは、各ツールの部署（勤怠は `KintaiEmployee.departmentId`、HR は社員の部署）をサーバーで読んで渡します。会社単位の部署は、今は作りません。

## 6. 画面

### 6.1 招待のときに役割を選ぶ

- 場所: 新しい料金のメンバーの画面（`/api/pricing/members`・`/pricing/join`）の招待の欄に、役割の選択を足します。
- 選択肢は、招待する人が付けられる役割だけです（`grantableCompanyRoles`）。オーナーは管理者からゲストまで、管理者はマネージャーからゲストまでです。
- 既定はメンバーです。各選択肢の下に、1行の説明（`COMPANY_ROLE_DESCRIPTION`）を出します。
- 375px では、役割の選択を縦に並べたラジオボタンにします。

### 6.2 役割を変える

- メンバーの一覧の各行に、今の役割と「役割を変える」を出します。変えられない行（自分・オーナー・同じか上の役割）には出しません。
- 変えるときは、確認の画面で「何から何へ」「できなくなること」を出します。例: 「メンバーにすると、勤怠の承認ができなくなります」。
- 旗を on にするとツールの中の役割が下がる人には、一覧で印を付けます（§4.2 の 4）。

### 6.3 変更の記録

- 誰が・いつ・誰を・何から何へ変えたかを残します（`account_company_role_events`。§8）。招待・参加・変更・外す・移行の5つです。
- 記録は追記だけで、直せません・消せません。会社を消しても残します（ドヤパワーの台帳と同じ考え方）。
- 管理者以上が、メンバーの画面の「変更の記録」で見られます。

## 7. 新しい料金・知らせとのつながり

- 人数課金: ゲストも含めて、招待中と参加の人を席に数えます（新しい料金の `seatsUsed` のまま）。ゲストを席に数えない案は §9 で確認します。
- 支払い: 契約・支払い方法・人数の変更・ドヤパワーの追加購入は、オーナーだけです。新しい料金のブランチの「持ち主だけ」と同じです。管理者にも人数の変更を許すか（B7）は、この仕様では「許さない」にしました。
- 料金のページ: オーナー以外には「オーナーに相談してください」と出します（PRICING-NEW の表と同じ）。
- 知らせの部品（承認待ち）: 承認できる人にだけ出します。勤怠の申請はその部署のマネージャーと管理者、見積の確定はマネージャー以上です。判定は `canCompany` をサーバーで使い、結果だけを画面に渡します。
