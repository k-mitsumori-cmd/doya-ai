## 0. 要点

- ユーザーの依頼（2026-10-26）は「社員が勤怠などを全部直せないように、オーナー・依頼者・メンバーの権限を調整できるようにしたい」というものです。
- 今の各ツールの API には、社員が勤怠を直接直せる道はありませんでした（§2）。困るのはこれからです。会社にメンバーを招く作り（新しい料金）が入ると、会社の誰がどこまでできるかを決める場所が無いまま、人が増えます。
- そこで、会社単位の役割を6つ置きます。オーナー・管理者・マネージャー・請求の担当・メンバー・ゲストです（§3）。
- 会社の役割は、各ツールの役割の「上限」として使います。ツールの中で使える役割は、ツールの役割と会社の上限の低いほうです（§4）。会社の役割で、ツールの役割が上がることはありません。
- 判定はサーバーだけで行います。旗が off のあいだは何も変わりません。shadow で「止めるはずだった操作」を記録して確かめてから、止める側に切り替えます（§5）。

## 1. 今の権限の作り（調べた結果）

### 1.1 ツールごとの役割

- どのツールも「組織を作った人がそのツールの最上位」になり、ほかの人はツールごとに招待されます。ツールの組織どうしはつながっていません。
- 会社（`account_companies`）には、会社単位の役割がありません。`userId` が unique なので、1人に1社です（2026-10-19 のユーザーの判断「1アカウント1会社」）。
- 新しい料金のブランチが `account_company_members` を足します。役割は admin / member の2つだけで、今は持ち主しか管理できません（PRICING-NEW の B7・F5 で「未決」）。
- 会社のメンバーとツールの役割は、まだつながっていません。会社に入っても、各ツールでは別に招待されるまで何もできません。

### 1.2 料金・ドヤパワー・エージェント

- 料金と支払いは、すべて本人（`User.plan`）単位です。会社の誰かが、ほかの人の契約を変える道はありません。HR だけは、組織の OWNER しか Checkout できません。
- ドヤパワーは、本人が持ち主の会社の分だけを読みます（`src/lib/doya-power/charge.ts`）。body の companyId は受け取りません。追加購入の API は main にまだありません（新しい料金のブランチで、持ち主だけが買える形で作っています）。
- エージェントの実行は本人単位です。道具の呼び出しは本人の cookie で各ツールの API を呼ぶので、各ツールの判定がそのまま効きます。

### 2.1 勤怠（15本）

| 操作 | API | 通る役割 | 結果 |
|---|---|---|---|
| 打刻 | `POST /api/kintai/clock` | 有効な社員なら誰でも | 時刻はサーバーの今だけ。社員の番号はログインした人に固定 |
| 勤怠の直接の修正・上書き | なし | — | 勤怠を直接書き換える API が無い。勤怠は「打刻」「再計算」「申請の承認」でしか変わらない |
| 再計算 | `POST /api/kintai/attendance/recalculate` | hr_admin 以上 | 打刻から計算し直すだけ。値は入れられない |
| 申請 | `POST /api/kintai/requests` | 有効な社員なら誰でも | 自分の分だけ。打刻の修正は未来の時刻を拒む |
| 承認・却下 | `PATCH /api/kintai/requests/[id]` | manager 以上 | 自分の申請は system_admin しか承認できない。manager は同じ部署の人だけ |
| 社員の登録・変更・無効化・招待 | `/api/kintai/employees/**` | hr_admin 以上 | 自分の役割は変えられない。同じか上の役割は付けられない |
| 部署・就業ルール | `/api/kintai/departments/**`・`work-rules/**` | hr_admin 以上 | すべて組織の二重条件あり |
| 招待の受け入れ | `POST /api/kintai/invite/[token]` | 招待のメールと同じ人 | 役割は招待のときのまま。受け入れる側では変えられない |

見つかった点:

| 重さ | 内容 | 場所 |
|---|---|---|
| 中 | hr_admin が、同じ hr_admin を DELETE で無効化できる。PATCH では「同じか上の人は変えられない」で止まるのに、DELETE だけ止まらない | `src/app/api/kintai/employees/[id]/route.ts` の DELETE（195 行付近） |
| 低 | 招待中の社員のメールを PATCH で直しても、前のメールの招待リンクが使える | 同じファイルの PATCH と `invite/[token]` |
| 低 | manager は、同じ部署なら上の役割の人の申請も承認できる | `requests/[id]/route.ts` |
| 低 | 承認のコメントと申請の中身に長さの上限が無い | `requests/route.ts`・`requests/[id]/route.ts` |

社員（employee）や manager が、他人や自分の勤怠を不正に直せる道は見つかりませんでした。中の1件は管理者どうしの話なので、旗とは別の小さな直しとして出します（§10）。

## 3. 会社の役割と「できること表」

### 3.1 役割

| 役割 | できること | 人数 |
|---|---|---|
| オーナー | 契約と支払い、ドヤパワーの追加購入、役割の変更、会社の削除 | 会社に1人（`account_companies.userId`） |
| 管理者 | すべてのツールの設定と承認、ほかの人のデータの修正、メンバーの招待 | 何人でも |
| マネージャー | 自分の部署の人の申請の承認。ほかの人のデータは直せない | 何人でも |
| 請求の担当 | メンバーと同じことに加えて、料金と請求を見る、請求書を確定・発行・取り消す。支払い方法や人数は変えられない | 何人でも |
| メンバー | 自分のデータだけ。勤怠は打刻と申請だけで、直接は直せない | 何人でも |
| ゲスト | 共有された画面を見るだけ | 何人でも |

決まり:

- 自分で自分を承認できません。管理者も同じです。会社に1人しかいない場合のために、オーナーだけは自分の分を承認できます（記録には残します）。HR の評価だけは、§3.4 の切り替えで決めます。
- 請求の担当は、順番の上ではメンバーと同じです。料金と請求の操作だけを、表の「請」で足します。
- 自分の役割は変えられません。管理者は、自分より下の役割の人しか変えられず、自分より下の役割しか付けられません。
- オーナーの役割は、招待や変更では付けられません。引き継ぎは別の手順です（新しい料金の B9 と同じく、契約が移るので運営の手作業にする案）。
- 知らない役割の値は、いちばん低いゲストとして扱います。

### 3.2 「依頼者」の扱い（2026-10-26 ユーザーが決定）

ユーザーの言葉「オーナー権限と依頼者とそのメンバー」の「依頼者」は、次の3つのどれかだと考えます。

| 案 | 依頼者とは | この仕様での扱い |
|---|---|---|
| A | ドヤAI に申し込んだ人（契約した人） | オーナーと同じ。会社に1人 |
| B | 申請やエージェントの仕事を頼む人（社員の側） | 役割ではなく、操作の立場。申請を出す人は承認できない（§3.1）。エージェントは頼んだ人の権限で動く（CHECKLIST AGT-08 と同じ） |
| C | 社外の人（取引先・外注先など、仕事を頼んでくる人） | ゲスト。共有された見積や案件を見るだけ。会社の席には数えない案もある |

2026-10-26 にユーザーが「全部おすすめで」と決めました。A はオーナー、B は操作の立場（自分の申請は自分で承認できない。エージェントは頼んだ人の権限で動く）、C はゲスト（共有された見積や案件を見るだけ）です。3つとも、この仕様の役割で表せます。

### 3.4 会社ごとに切り替えられる決まり

オーナーが `/home/roles` の「権限の決まり」で変えます。保存先は `account_company_role_settings.policy`（JSON）で、行が無ければ初期値です。変えたら記録（`kind = policy_changed`）に残します。正本は `src/lib/company-roles/policy.ts`。

| 項目 | 選べる値 | 初期値（2026-10-26 決定） | 今のツールの動き |
|---|---|---|---|
| 請求書を確定・発行できる人（`invoiceIssueMin`） | マネージャー以上 / 管理者以上（どちらも請求の担当は可） | マネージャー以上 | マネージャー以上 |
| 契約の金額を直せる人（`contractEditMin`） | メンバー以上 / マネージャー以上 / 管理者以上 | マネージャー以上 | メンバー以上 |
| 見積を確定できる人（`quoteFinalizeMin`） | マネージャー以上 / 管理者以上 | マネージャー以上 | マネージャー以上 |
| 自分で作った見積を自分で確定してよいか（`quoteSelfFinalize`） | よい / ほかの人が確定する（オーナーは可） | ほかの人が確定する | よい |
| 自分が評価される側の評価を確定してよい人（`hrSelfFinalize`） | 誰もできない / オーナーだけ / オーナーと管理者 | オーナーだけ | オーナーと管理者 |

- 見積の「作った人」は、新しい表 `account_company_record_authors` に、旗が off でない間だけ残します。行が無い見積（旗を入れる前に作ったもの）は、作った人が分からないので、止める側に倒します（管理者とオーナーだけが確定できる）。

## 4. 各ツールの役割とのつながりと移行

### 4.1 上限の表

ツールの中で使える役割は、ツールの役割と、下の表の上限の低いほうです（`effectiveToolRole`）。

| 会社の役割 | 勤怠 | HR | プロマネ | 収入 | そのほか（owner/admin/manager/member） |
|---|---|---|---|---|---|
| オーナー | system_admin | OWNER | owner | owner | owner |
| 管理者 | hr_admin | ADMIN | admin | admin | admin |
| マネージャー | manager | MANAGER | member | manager | manager |
| 請求の担当 | employee | MEMBER | member | admin | member |
| メンバー | employee | MEMBER | member | member | member |
| ゲスト | 使えない | 使えない | guest | 使えない | 使えない |

- 例: 勤怠で system_admin の人でも、会社でメンバーなら、勤怠の中では一般（employee）として扱います。
- ツールの役割の文字列は変えません（HR の大文字、勤怠の hr_admin）。各ツールの今の `hasMinRole` と組織の二重条件は、そのまま残します。
- 収入は請求書の仕事なので、請求の担当の上限を管理者にしました。請求書の確定・取り消しは、§3.4 と表の「請」で会社の決まりとしても確かめます。
- ゲストは、ゲストの役割があるプロマネでだけ見られます。ほかのツールは使えません。
- つなぐ場所は2つです。①各ツールの入口（`get{Svc}Context`）で、ツールの役割に上限を当てる（`ceilToolRole`）。②書き込みのトランザクションの中で DB から役割を読み直すところで、入口の役割より上に上げない（`lowerToolRole`。例: 勤怠の `lockCurrentKintaiActor`）。
- 会社の上限は、そのツールの組織が属する会社での役割で決めます（2026-10-26 統括の監査の重大1への対応）。組織が属する会社は、その組織を作った人（いちばん古いメンバーの行。役割や状態では絞らない。プロマネはワークスペースの作成者）の会社です。作った人が会社の持ち主ならその会社、持ち主でなく会社のメンバーなら、その会社です（`src/lib/company-roles/tool-orgs.server.ts`）。自分で別の会社を作っても、ほかの会社の組織ではその会社での役割が当たります。
- 組織が会社に属していない（作った人が会社を持っていない）ときは、上限を当てません。会社のメンバーでない人（ツールだけに招かれた人）は、メンバーの上限です。
- §3.4 の会社の決まりの判定も、同じく組織が属する会社で行います。会社に属していない組織では止めません（重大2への対応。上限と同じ扱い）。組織を指定しない会社そのものの操作では、会社に入っていない人を止めます。

### 4.2 今の会員を新しい役割に割り当てる

1. 会社の持ち主（`account_companies.userId`）がオーナーです。最初の人です。
2. `account_company_members` の行の役割（新しい料金の admin / member）は、そのまま引き継ぎます。
3. それぞれの人について、会社のツールの組織（オーナーが入っている組織）での役割を写して、いちばん高いものを「案」にします（`proposeCompanyRole`）。

| ツールの役割 | 会社の役割の案 |
|---|---|
| 勤怠の system_admin・hr_admin、HR の OWNER・ADMIN、ほかの owner・admin | 管理者（オーナーにはしない） |
| 勤怠の manager、HR の MANAGER、ほかの manager | マネージャー |
| 勤怠の employee、HR の MEMBER、ほかの member | メンバー |
| プロマネの guest | ゲスト |

4. 案と今の役割が違う人、旗を on にするとツールの中の役割が下がる人（`wouldBeClamped`）を、オーナーに一覧で見せます。オーナーが決めるまで、自動では書きません。
5. 決めた結果は、役割の変更の記録（`kind = migrated`）に残します。

注意: 自分でツールの組織を作った人は、その組織の最上位です。会社の組織と別なら、会社の役割の案には数えません。

## 6. 画面と API

### 6.1 招待のときに役割を選ぶ

- 部品: `src/components/company-roles/RolePicker.tsx`。役割ごとに、名前と1行の説明（`COMPANY_ROLE_DESCRIPTION`）を縦に並べたラジオボタンです。375px でも崩れません。

- 招待そのものは、新しい料金の `/api/pricing/members`（持ち主だけ）です。受け付ける役割を `grantableCompanyRoles` にそろえることを、新しい料金のセッションに依頼しました（返事待ち）。

### 6.2 メンバーと権限の画面（`/home/roles`）

- 旗が off、または会社に入っていない人には 404 です。最初の表示の中身はサーバーで作って渡すので、読み込みの表示は出ません。
- 上から「あなたの役割」「メンバー」「権限の決まり」「今までのツールの役割から見た案」（オーナーだけ）「変更の記録」（管理者以上）です。375px では1列に積みます。
- 役割を変えられる行にだけ、役割の選択を出します（自分・オーナー・同じか上の役割の人の行には出しません）。
- 変えるときは、確かめの画面に「できなくなること」（`lostAbilities`）を出します。例: 「部署の人の申請の承認ができなくなります。」
- shadow のあいだは、「いまは確かめの期間で、まだ止めていない」と画面の上に出します。

### 6.3 API

| API | 何をするか | できる人 |
|---|---|---|
| `GET /api/company/roles` | 自分の役割・できること・メンバーの一覧・決まり | 会社の人（一覧はメンバー以上） |

### 6.4 変更の記録

- 誰が・いつ・誰を・何から何へ変えたかを残します（`account_company_role_events`）。種類は、招待・参加・変更・外す・移行・決まりの変更の6つです。招待・参加・外すの記録は、新しい料金の API から書いてもらいます（依頼済み）。
- 記録は追記だけで、直せません・消せません（DB のトリガー）。会社を消しても残します。

## 7. 新しい料金・知らせとのつながり

- 人数課金: ゲストも含めて、招待中と参加の人を席に数えます（新しい料金の `seatsUsed` のまま）。ゲストを席に数えない案は §9 で確認します。
- 支払い: 契約・支払い方法・人数の変更・ドヤパワーの追加購入は、オーナーだけです。新しい料金のブランチの「持ち主だけ」と同じです。管理者にも人数の変更を許すか（B7）は、この仕様では「許さない」にしました。
- 料金のページ: オーナー以外には「オーナーに相談してください」と出します（PRICING-NEW の表と同じ）。
- 知らせの部品（承認待ち）: 承認できる人にだけ出します。勤怠の申請はその部署のマネージャーと管理者、見積の確定はマネージャー以上です。判定は `canCompany` をサーバーで使い、結果だけを画面に渡します。

## 11. 社員ごとの部署（部署ごとの入口の段階3。2026-10-26 追加）

UI リニューアルの「部署ごとの入口（ドヤマーケAI・ドヤセールスAI・ドヤ人事AI・ドヤ管理AI）」（`DEPARTMENTS-2026-10-26.md` §6 の段階3）のために、メンバーごとに部署を持ちます。

- 部署の id は marketing・sales・hr・admin です。正本は UI 側の `src/lib/departments.ts`（`feat/departments`）で、このブランチでは同じ4つを `src/lib/company-roles/departments.ts` に持ちます。入ったら、そちらから import する形に直します。
- 保存先は新しい表 `account_company_member_departments`（companyId・userId・departments）です。持ち主は `account_company_members` に行が無いので、companyId と userId で持ちます。`account_company_members` には列を足しません。
- 読む口: サーバーの関数 `getMemberDepartments(userId)`（`departments.server.ts`）と `GET /api/company/me/departments`。どちらも `{ primary: DepartmentId[]; all: boolean }` を返します。オーナーと管理者は `all: true` です。
- 旗が off、新しい料金の表が使えない、会社に入っていない、表が読めない、のどれでも `{ primary: [], all: true }`（全部を出す。今のメニューと同じ）を返します。
- 決める口: `PUT /api/company/members/[id]/departments`（管理者以上。持ち主は id に `owner`）。変えたら記録に残します（`kind = departments_changed`）。画面は `/home/roles` の「部署」の欄です。
- 部署はメニューの並びに使うだけで、権限の判定には使いません。マネージャーの「自分の部署」の承認は、今までどおり各ツールの部署で判定します。
