## 1. 常時確認の仕組み（system-watch）

### 1.1 何をするか

1. 10分ごとに、下の「2. チェックリスト」の自動の項目（今は約70件）を、読むだけで確かめます。
2. 前回までの結果と比べて、知らせる必要があるものだけを Slack に送ります。送り口は共通の `postSlack`（`src/lib/slack/notify.ts`）で、見出しは「【緊急/要対応】ドヤAI｜エラー：件名」にそろいます。
3. 状態は SystemSetting の `watch:v1:state:free` に、最後の実行時刻は `watch:v1:last-run:free` に残します。DB に書くのはこの2つだけです。

### 1.2 知らせ方の決まり

- 一時的な揺れでは知らせません。画面・API・外部サービスは2回続けて（20分）失敗したら、DB の整合と設定は1回で知らせます。
- 同じ失敗は間引きます。続いている失敗は6時間ごとに、回数を添えて知らせ直します。設定の不足は24時間ごとです。
- 失敗の中身（状態コードやエラーの種類）が変わったら、すぐ知らせ直します。
- 知らせた失敗が直ったら、「直りました」と止まっていた時間を知らせます。
- 旗の値が変わったら「設定の値が変わりました」を知らせます（お知らせの扱い）。
- Slack に送れなかったときは「知らせた」ことにせず、次の回にもう一度送ります。

### 1.3 通知に書くこと

1件ごとに、次を書きます。「読み込めませんでした」だけの通知は出しません。

- どこが: 分類（画面・API・DB・台帳・cron・外部サービス・設定・旗）と名前
- 確認した URL
- 状態コード（応答が無ければ「なし」）
- エラーの要約: 本文の先頭、DNS・タイムアウト・接続拒否・証明書の区別、件数
- 最初の失敗の時刻、続いている時間、連続した回数
- 直し方の候補（確認ごとに2〜3個）

通知の例（画面が500を返したとき）:

```
【要対応】ドヤAI｜エラー：画面「ドヤバナーAI（/banner）」の確認に失敗しました
発生時刻：2026/10/26 9:10:00（日本時間）

■ 画面：ドヤバナーAI（/banner）（新しい失敗）
- 確認した URL: https://doya-ai.surisuta.jp/banner
- 状態コード: HTTP 500
- エラー: HTTP 500（期待 200）: Internal Server Error
- 補足: 812ms
- 最初の失敗: 2026/10/26 9:00:00（約10分前から、2回続けて失敗）
- 直し方の候補:
  1. Vercel の最新のデプロイが Ready か、Runtime Logs に同じ URL のエラーが出ていないかを見る
  2. 直前のコミットでこの画面のファイル（src/app/(shell)/<ツール>/）を変えていないかを見る
  3. DB の確認も失敗しているなら、先に DB（Supabase）の状態を見る
```

### 1.4 有料の確認（1日1回・承認まで止めてある）

モデルの情報を読むだけでは、クレジット切れ・利用上限・課金の停止は分かりません。
そこで、3社のいちばん安いモデルに、1日1回だけ「OK とだけ返してください」と頼みます（`src/lib/system-watch/paid-checks.ts`）。

| 確認 | モデル | 単価（100万トークンあたり、入力 / 出力） | 1回の量 | 1回の見込み |
|---|---|---|---|---|
| `paid:gemini-generate` | gemini-2.5-flash（思考なし、出力16まで） | $0.30 / $2.50 | 入力 約15 / 出力 約5 | 約 $0.00002 |
| `paid:claude-generate` | claude-haiku-4-5-20251001（出力16まで） | $1.00 / $5.00 | 入力 約30 / 出力 約5 | 約 $0.00006 |
| `paid:openai-generate` | gpt-4o-mini（出力5まで） | $0.15 / $0.60 | 入力 約15 / 出力 約5 | 約 $0.00001 |

- 回数: 1日1回ずつ、合わせて1日3回（毎朝 8:40）
- 見込み額: 1日 約 $0.0001（約0.02円）、1か月 約 $0.003（約0.5円）
- 画像の生成（gpt-image-2）の確認は入れていない。単価と回数が決まってから別に承認を取る。
- 有効にする方法: ユーザーの承認の後、SystemSetting に `watch:v1:paid-enabled` = `true` の行を足す。値が `true` でなければ、この3つは呼ばない。

#### エージェントの有料の確認（B1・B2。2026-10-26 ユーザー承認、1日 約10円まで）

エージェントの担当（local_bf659a4c）の `FAILURE-CHECKLIST.md` §7.2 を、system-watch-paid に入れた（`src/lib/system-watch/agent-checks.ts`）。スイッチは別で、`watch:v1:paid-agent-enabled` = `true` のときだけ動く。本番で有効にするのは、統合のときに統括の承認の流れで行う。

| 確認 | 中身 | 1回の見込み | 1日 |
|---|---|---|---|
| `paid:agent-research-samples`（B2） | 会社の調査だけを、見本の2つ目と3つ目で通す（gemini-2.5-flash を2回） | 約2.4円 | 1回 |
| `paid:agent-sales-prep`（B1） | 商談の準備を1回通す（会社の調査・見積の案・スライドの構成を同時に）。見積とスライドは Haiku 5.5 | 約1.8円（上限 約10円） | 1回 |

- 合計の見込み: 1日 約4.2円、1か月 約130円（承認は1日 約10円まで）。上限の日は1日 約12円になり得るが、次の止める仕組みで10円台に収める。
- 1日の上限: 安い確認から順に1つずつ回す。回す前にその日の累計の見込み額（SystemSetting `watch:v1:paid-spend:<日本時間の日付>`）を見て、10円に届いていたら残りを回さない。失敗した確認も、費用は出たとみなして足す。前提がそろわず回さなかった確認は足さない。
- B1 はテスト用のユーザー（`SYSTEM_WATCH_TEST_USER_ID`）として呼ぶ。cron の中で、そのユーザーだけに15分有効なセッションを作り、`/api/agent/tasks` を3つ呼び、終わったら消す。テスト用のアカウントが無いうちは回さず、費用にも数えない（失敗として知らせない）。
- B1 は見積とスライドのプロジェクトを、テスト用の会社に1日1件ずつ作る。ドヤパワーの旗が on なら、その会社の台帳から 31 減る。無料のプランは1日10しか回復しないので、テスト用の会社はプロにしておく必要がある。
- 見本の会社は、毎日読みに行くので、他社ではなく自社のサイト3つにする（2026-10-26 ユーザー指示、メイン経由）。2026-10-26 に手元で AI なしで読み、取得・文字コード・本文の長さ・NUL に問題が無いことを確かめた。1日1回・1URL 1回までにする。
  - 1つ目 https://surisuta.jp/ … 会社のサイト。JavaScript で描く（本文 約8文字、題は「株式会社スリスタ」）。社名「スリスタ」と `diagnostics.jsRendered=true` を期待する。B1 が読む。
  - 2つ目 https://doyamarke.surisuta.jp/ … ドヤマーケのメディア（本文 約4,000字、UTF-8）。B2 が読む。
  - 3つ目 https://doya-ai.surisuta.jp/ … ドヤAI（本文 約2,400字、UTF-8）。B2 が読む。
  - 社名の取り出しは AI なので、2つ目と3つ目は社名の中身を照らし合わせず、社名が取れたかだけを見る。
  - Shift_JIS のサイトの見本は、他社のサイトになるので外した。文字コードの読み分けはテスト（`checks.test.ts`）で確かめる。
  - 無料の「AI なしで読めるか」（`agent:sample-sites`）は、有料の確認が止まっている日だけ1日1回読む。結果はその日のあいだ使い回す。
  - 差し替えは SystemSetting `watch:v1:sample-company-urls`（か環境変数 `SYSTEM_WATCH_SAMPLE_COMPANY_URLS`）。差し替えたときは社名を見ない。
- 見る所: 3つの ToDo の結果（失敗したら札の cause と actions）と、本番のログの `[shodan/preparations] research failed` の stage・code・reason。

## 4. テスト用のアカウントの案（作成はユーザーが行う）

ログインした後の画面と、会社の登録・生成・保存の流れを確かめるには、テスト用のアカウントが要ります。本番の利用者のデータに触れないよう、次の形を提案します。

1. ユーザーが Google Workspace に確認用のアドレス（例: `doya-watch@surisuta.jp`）を作り、本番に1回ログインする。
2. そのアカウントで会社「【確認用】ドヤAI」を登録する。プランは無料のままにする。
3. Vercel の環境変数に `SYSTEM_WATCH_TEST_USER_ID`（そのユーザーの ID）を足す。
4. system-watch に「テスト用の会社として読む」確認を足す。cookie は使わず、cron の鍵で守られたサーバーの中で、そのユーザーの会社・ドヤパワーの残高・各ツールの利用回数を読むだけにする（NextAuth のセッションは24時間で切れるため、cookie を持ち続ける形にはしない）。
5. 生成を伴う確認（エージェントで会社の調査を1件など）は、このテスト用の会社だけで、有料の確認として1日1回にする。見込み額はエージェントの担当の洗い出しを待って出す。

### 4.1 テスト用の会社のプラン

- テスト用の会社はプロにする（エージェントの担当と合意。2026-10-26）。B1 はドヤパワーを1日31使う（見積1・スライド30）。無料の回復は1日10（貯まるのは100まで）なので、2〜3日で足りなくなる。プロは毎月3,000で、31×31日＝961に収まる。
- 無料のままだと各ツールの枠でも止まる（見積書は累計3件、スライドは月3件、商談準備は月5件）。
- ユーザーの本物の会社とは分ける（台帳と枠を混ぜない）。
- プロにするのは課金の設定に関わるので、統括を通してユーザーの承認を取る（`BILLING_MANUAL_GRANT_EMAILS` などの手動付与を使うかも、そこで決める）。

### 4.2 テスト用の記録を月1回まとめて消す手順（実行は統括の承認の後）

B1 を回すと、テスト用のユーザーに、商談準備の記録・見積書の下書き・スライドのプロジェクトが1日1件ずつ増える。月に1回、次の順で消す。

1. 消す前に、対象がテスト用のユーザー（`SYSTEM_WATCH_TEST_USER_ID`）とその組織のものだけであることを、件数で確かめる。消す対象のツールは、商談準備（shodan の準備）・見積書（quote の書類）・スライド（doyaslide のプロジェクトと保存先のファイル）の3つ。
2. 件数と消す範囲（期間・ID の一覧）を統括に出し、ユーザーの承認を取る。
3. 承認の後、各ツールの画面か API の「削除」を、テスト用のユーザーとして使って消す（DB を直接消さない。保存先のファイルも各ツールの削除の処理で消える）。
4. 消した件数を、この文書と Obsidian の [[ドヤAI_03_システム徹底チェック]] に記録する。

自動で消す仕組みは、統括の承認を取ってから作る（今は作っていない）。

## 5. まだ良くない点と次の改善の提案

まだ良くない点:

- ログインした後の画面と、生成・保存の流れは自動で確かめていない（テスト用のアカウント待ち）。
- 運用 cron 以外の cron は、実行の記録が無いので止まっても分からない。
- 有料の確認は、承認を待って止めてある。
- 本番の Gemini の確認は、デプロイ後の最初の実行まで結果が分からない。

次の改善の提案:

1. 各 cron の最後に「最後に成功した時刻」を1行残す共通の部品を作り、system-watch で遅れを見る。
2. GitHub Actions の schedule で、外から `/api/health` を30分ごとに叩く。Vercel ごと止まったときにも気づける。
3. テスト用のアカウントを作り、4章の確認を足す。
4. Prisma のスキーマと本番 DB の列の差を、`information_schema` で毎日比べる。
5. 環境変数の更新時刻と最新のデプロイの時刻を Vercel の API で比べ、再デプロイ忘れを知らせる。
