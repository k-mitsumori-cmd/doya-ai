Goals

7つのゴール

どれも「完了した」と測れる形で定義しています。

G1

会社を1つに9系統の組織を Company と CompanyMember にまとめ、どのサービスも会社IDでデータを引く

G2

権限を1つに18本の権限チェックを共通の1つに置き換え、入口で全APIと画面を既定拒否で守る

G3

課金を1つにStripeの顧客＝会社。席（メンバー）単位の契約。使用量は1本の台帳で上限を管理

G4

会社情報を1つに7系統の会社情報を、共通の会社プロフィール・ブランド素材・ナレッジにまとめる

G5

経営エージェントホームで一言頼むと各サービスを横断して動く。外に出る操作は必ず人の承認を通す

G6

セキュリティ会社ごとのデータ分離・既定拒否・承認必須・改ざんしにくい記録を、自動テストで守り続ける

G7

1人1アカウントGoogleログインのみ、席課金、同時ログインの上限、共有の兆候の検知で使い回しを防ぐ

Agent

エージェントは、こう動く

ホームで「来月の売上を伸ばす作戦を立てて」と頼むと、エージェントが計画を立て、営業管理・AI検索の分析・リスト作成・バナー・記事・見積もりを段階ごとに同時に動かします。メール送信のように外に出る操作の前では、必ず止まって承認を待ちます。

作業の種類例承認理由
読むだけsfa.listDeals 商談一覧、kintai.monthlyOvertime 残業の集計不要何も変えない
下書き（取り消せる）quote.draftQuote 見積書の下書き、seo.createOutline 記事の構成会社の設定に従うあとで消せる
外に出る・取り消せないメール送信、求人の公開、勤怠申請の承認必ず必要相手に届いたら戻せない
費用が大きい画像生成、多数の会社の調査必ず必要無断課金を防ぐ（2026年8月の事故の再発防止）

Security

守りは7層、1枚破られても次で止める

他社のデータを見られない・書き換えられないことを最優先にしています。アプリの中の検査は「知らない操作は通さない」方式にし、さらに機微なデータ（HR・勤怠・面接）はデータベース側でも行単位で制限します。

1Googleログインのみパスワードは作らない。メールの確認済みを必須、会社のドメインで制限も可能
2端末とセッションの結びつけログイン情報だけ盗んでも別の端末では使えない。同時ログインは上限つき
3入口の検問（既定は拒否）全ルートを5分類で機械的に洗い出し、分類のない入口は通さない
4共通の権限チェック会社の役割とサービス内の役割の二段で判定。依頼者の権限を超えて動かない
5会社ごとのデータ分離Prismaの定義をたどり、許可リストにない書き込みは即拒否。192モデル・396の関連を走査して確認済み
6データベースの行単位の制限HR・勤怠・面接の表に限り、二重の守りとして採用（最後の段階）
7改ざんしにくい記録誰が・いつ・どの会社で・何をしたかを追記専用で3年保管
アカウントの使い回しへの3段の対策技術だけで完全には防げないことを明記したうえで、抑止・検知・契約を組み合わせる
1. 抑止する端末とセッションを結びつけ、ログイン情報だけ渡しても別の端末では使えないようにする。同時ログインは3台まで。会社の設定で、ログインにパスキー（端末に結びついた鍵）を必須にできる
2. 兆候を見つける同じセッションが短い時間に別の端末や回線から交互に使われる、離れた地域から同時に使われる、といった動きを検知する
3. 契約と運用で決める契約上「1席＝1つのGoogleアカウント」とする。検知したら管理者に通知して判断してもらい、誤検知で利用者を自動では止めない

Fix first

設計とは別に、先に強化するところ（16件）

改修を始める前に、今の本番コードで強化すべき点を、小さなPRで先に直します。どれも単独で出せて、すぐ戻せます。具体的な中身は修正が終わるまで社内の設計書だけに記載しています。

分野件数どう強化するか
管理者まわりの認証4秘密鍵や管理者セッションの確認を厳しくし、緊急用ログインの扱いを見直す
外部APIの鍵と課金2APIキーの送り方を見直し、画像生成は品質とサイズの指定を必須にする（無断課金の再発防止）
ログインと入力のチェック5Googleアカウントの確認状態、アップロード、ゲスト利用の入力などの検査を追加
通信と記録5外部ページの読み込み先の制限、アクセス元の記録方法、使われていない入口の整理など

Roadmap

進め方：足す → 両方に書く → 読み替える → 古いものを消す

いきなり作り替えず、どの段階でもスイッチ1つで前に戻せる順番にしています。データベースは「足すだけ」から始め、消すのは最後です。設計書の見積りは、実装2名とリード1名で約6か月です。

今の弱点16件を小さなPRで修正。

戻し方：各PRを個別に取り消し

段階0 準備3週間

共通部品の骨組み、18サービス全部の設定ファイル（マニフェスト）、本番データの件数をのぞくだけの確認、実機でしか確かめられない4点の確認。

Start conditions

実装に入るための4つの条件

最終確認の判定は「条件付きで着手可」です。

1. 先に直す16件を出す改修の前に、単独のPRで今の弱点をふさぐ
2. 実機で4点を確かめる一括処理の中で検査が働くか、裏の処理の時間上限、DB側の制限の保持、接続の固定
3. 自動テストを同梱する各段階のPRに、チェックリストの自動検査を入れる
4. 動く見本をテストに移すデータ分離の検査を本番の自動テストに移してから本番コードにする

まだ確かめていないこと　本番データベースの実際の件数（重複した組織、宙に浮いたデータなど）は見ていません。段階0で、書き込みをしない確認用の実行で数えます。
