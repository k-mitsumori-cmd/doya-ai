# ドヤAI 開発基盤の計画（2026-10-18）

デザイン変更や機能改善を、安全に、速く進めるための計画です。
この文書は計画と見積もりだけです。実装、有料サービスの契約、設定の変更はまだしていません。

## 1. まとめ

### おすすめの順番

| 順 | やること | 工数の目安 | 月額の目安 | 効果 |
|---|---|---|---|---|
| 1 | main を保護し、PR とチェックの合格を必須にする | 0.5 日 | 0 円 | 本番への直接の push を止める。いちばん安く、いちばん効く |
| 2 | 検証用の DB とプレビュー環境、テスト用ログイン | 3〜4 日 | 約 1,500〜3,000 円 | 本番に出す前に、本物に近い場所で触って確かめられる |
| 3 | ツール定義の一元化 | 3〜4 日 | 0 円 | ツールの追加・名前変更が 1 か所で済む |
| 4 | 見た目の一元化（直書きの禁止と自動チェック、画面の比較） | 4〜6 日（直書きの置き換えは別に段階的） | 0 円 | デザイン変更が一括で効く。崩れを PR で見つけられる |
| 5 | 機能フラグを DB で切り替える | 2〜3 日 | 0 円 | 新しい画面の公開・取り下げに、再デプロイが要らなくなる |
| 6 | 片付けと監視（エラー通知、外形監視、スキーマのずれの検知） | 2〜3 日 | 0 円から（無料枠） | 障害に早く気づける。古いブランチで迷わない |

- 合計の工数は、およそ 15〜20 日です。AI のセッションで進める前提の目安で、確認の待ち時間は含みません。
- 新しく増える月額は、検証用 DB の分だけで、およそ 1,500〜3,000 円です。エラー通知は無料枠で始められます。
- 金額は 2026-10 時点の公開価格からの目安です。契約前に、各社の料金ページで確かめてください。

### 決めてほしいこと

1. 検証用 DB を、Supabase のブランチ機能にするか、別のプロジェクトにするか（2 章。おすすめは別のプロジェクト）。
2. テスト用のログインを、プレビュー環境だけで使えるメールとパスワードの方式にしてよいか（2 章）。
3. エラー通知に Sentry を使うか（6 章。無料枠で始めて、足りなければ有料に上げる）。

## 2. 本番前に確かめられる場所

### 現状

- main への push が、そのまま本番のデプロイになります。保護の設定はありません。
- GitHub Actions の CI はすでにあり、PR と main への push で、tsc とセキュリティ回帰テストが動いています（`.github/workflows/ci.yml`）。ただし、合格しなくても merge できます。
- Vercel のプレビューデプロイは作られますが、接続先の DB が本番と同じかどうかが、環境変数しだいです。
  プレビューで本番の DB を書き換える恐れがあります。
- プレビューでは Google ログインが動きません。NEXTAUTH_URL が本番の URL に固定されているためです。

### やること

1. main の保護（GitHub の Branch protection）
   - main への直接の push を禁止し、PR からの merge だけにする。
   - CI の合格を merge の条件にする。
   - 管理者も同じ規則に従う設定にする。緊急時だけ一時的に外す手順を、docs に書いておく。
2. 検証用の DB
   - Supabase に、検証用のプロジェクトを 1 つ作る（おすすめ）。
     本番とは接続文字列もキーも別になるので、取り違えても本番を壊しません。
   - スキーマは `prisma db push` で検証用 DB にだけ反映します。本番の手順（手動の DDL）とは分けたままにします。
   - 中身は、テスト用の組織・ユーザー・各ツールの見本データを入れる種まきスクリプトで作ります。本番のデータは写しません。
   - Supabase のブランチ機能も候補です。ただ、プレビューのたびに DB ができる作りは、費用と待ち時間が読みにくいので、最初は使いません。
3. プレビュー環境の設定（Vercel）
   - Preview の環境変数を、検証用 DB・検証用の Stripe（テストモードのキー）・検証用のストレージに向ける。
   - 本番の秘密の値を Preview に入れない。
   - 従量課金の AI（Gemini・OpenAI・画像生成）は、Preview では止めるか、1 日の上限をごく小さくする。
4. テスト用のログイン
   - Google ログインは、プレビューごとに URL が変わるため使いにくいです。
   - プレビュー環境だけで有効になる「メールとパスワードのログイン」を足します。
     `VERCEL_ENV !== 'production'` のときだけ有効にし、本番では読み込まれないようにします。
     アカウントは種まきスクリプトで作り、パスワードは Vercel の Preview の環境変数に置きます。
   - 代わりに、固定の検証用ドメイン（例: staging.doya-ai.surisuta.jp）を用意して、Google ログインを使う方法もあります。
     こちらは Google 側の設定変更が要るので、2 段目の案にします。
5. PR ごとの確認 URL
   - Vercel が PR に自動でコメントするプレビューの URL を、そのまま使います。
   - PR の説明の雛形（`.github/pull_request_template.md`）に、確かめた画面と結果を書く欄を足します。

### 費用・工数・リスク

| 項目 | 月額の目安 | 工数 | リスク |
|---|---|---|---|
| main の保護 | 0 円 | 0.5 日 | 緊急の修正が PR を通る分だけ遅くなる。手順を決めておく |
| 検証用 DB（Supabase の別プロジェクト） | 約 1,500 円（Micro の計算資源、10 ドル前後） | 1.5 日 | 種まきの見本データが古くなる。CI で毎回作り直す |
| Preview の環境変数の分離 | 0 円 | 0.5 日 | 入れ忘れた変数が本番の値に落ちないよう、未設定なら起動で止める |
| テスト用ログイン | 0 円 | 1 日 | 本番で有効になる事故。CI に「本番の設定で読み込まれないこと」のテストを置く |
| PR の雛形 | 0 円 | 0.2 日 | なし |

## 3. ツール定義の一元化

### 現状

ツールを 1 つ足すたびに、次の場所を直しています。

- `src/lib/services.ts`（名前、説明、料金、公開状態）
- `src/lib/stripe.ts`（ALL_SERVICE_IDS）
- `src/components/shell/nav.ts`、`tools.ts`、`icons.tsx`（新しい枠のナビとアイコン）
- 各ツールの `src/lib/<id>/nav.ts`（収入管理・支出管理・展示会・社内インタビュー・ポップアップ）
- `src/lib/plan-limit.ts`（上限）
- `next.config.js`（提供終了の転送）
- LP の画面キャプチャ（`public/<id>/shots/`）

統合のときに、アイコンの登録漏れや、画面キャプチャの不足が実際に起きました。

### やること

1. 正本を `src/lib/services.ts` の 1 つにまとめます。
   - ナビの項目、アイコンの名前、上限、提供終了の転送先も、ここに書きます。
   - ほかのファイルは、この正本から値を読むだけにします。
2. 検証のテストを足します（`npm run test:services`、CI で実行）。
   - すべてのツールで、アイコンが icons.tsx にあること
   - 公開中のツールに、LP の画面キャプチャがそろっていること
   - 提供終了のツールに、画面の転送と API の 410 があること
   - stripe.ts の ID の一覧と、services.ts のツールの一覧が一致すること
3. 新しいツールの雛形を作るスクリプトを用意します（`npm run new:tool <id>`）。
   - layout、nav、LP、noindex、上限の行をまとめて作り、足りないものを一覧で出します。

### 費用・工数・リスク

- 月額 0 円、工数 3〜4 日。
- リスク: 既存のファイルの読み方を一度に変えると、ナビが壊れる恐れがあります。ツールを 1 つずつ移し、移したツールだけテストで守ります。

## 4. 見た目の一元化

### 現状

- デザイントークンは `src/components/ds/tokens.module.css` に 28 個あります。
- 画面の中には、色の直書き（#xxxxxx）が 264 ファイルに 2,828 か所あります。
- Tailwind の色の直接指定（bg-blue-500 など）が、約 2.2 万か所あります。
- そのため、色や余白を変えるときは、ファイルごとに手で直すことになります。

### やること

1. 決まりを書きます（docs/design/rules.md）。
   - 色・余白・文字サイズ・角丸は、トークンか、トークンに対応した Tailwind の名前だけを使う。
   - tailwind.config.ts の色を、トークンの名前（primary、surface、danger など）に置き換える。
2. 自動チェックを入れます。
   - ESLint の独自の決まりで、tsx の中の #xxxxxx と、パレットの色の直接指定を見つける。
   - 既存の違反は一覧（基準のファイル）に入れて許し、新しい違反だけを CI で止めます。
     置き換えが進むたびに一覧を減らし、増やせないようにします。
3. 画面の比較を PR で出します。
   - Playwright で、主要な画面を 375px と 1280px で撮ります。対象はトップ、ログイン、各ツールの LP、新しい枠の画面です。
   - main の画像と比べ、差がある画面だけを PR のコメントに並べます。
   - 撮影は、2 章の検証用 DB とテスト用ログインを使います。ログインが要る画面も撮れます。
   - 外部の有料サービス（Chromatic や Percy）は使わず、GitHub Actions の中で動かします。
4. 直書きの置き換えは、画面ごとに段階的に進めます。新しい枠（ds-shell）に載せた画面から先に置き換えます。

### 費用・工数・リスク

- 月額 0 円。GitHub Actions の実行時間は増えます（後述の「注意」を参照）。
- 工数: 決まりと自動チェックで 2 日、画面の比較で 2〜3 日、置き換えは別に、画面ごとに 0.2〜0.5 日。
- リスク: 画面の比較は、アニメーションや日付で、毎回少しずつ違う結果になりがちです。撮影のときは動きを止め、日付を固定します。

## 5. 機能フラグを DB で切り替える

### 現状

- 新しい枠の表示は、環境変数 UI_SHELL_SERVICES で切り替えています（`src/lib/ui-shell.ts`）。
- 切り替えるたびに、Vercel の環境変数の変更と再デプロイが要ります。
  本番移行では、そのために空のコミットで再デプロイしました。

### やること

1. 表 FeatureFlag を足します（key、enabled、対象のツール、対象のユーザーや組織、更新者、更新日時）。
   - 統合仕様の README に、すでに案があります。
2. 読み方
   - サーバーで読み、60 秒ほどメモリに置いて、DB への問い合わせを減らします。
   - DB が読めないときは、環境変数の値に戻します。今の UI_SHELL_SERVICES がそのまま予備になります。
3. 切り替えの画面
   - 管理画面（/admin）に一覧と切り替えのボタンを置き、変えた人と時刻を記録します。
4. 段階的な公開
   - 自社の組織だけ、指定したユーザーだけ、全員、の順に広げられるようにします。

### 費用・工数・リスク

- 月額 0 円、工数 2〜3 日。
- リスク: 本番の DB に表を 1 つ足すので、手動の DDL の手順が要ります。
  フラグの読み取りに失敗しても画面が止まらないよう、必ず環境変数の値に戻る作りにします。

## 6. 片付けと監視

### 現状

- ~/Code/09_Cursol の worktree が 25 個あり、ローカルのブランチが 41 本あります。どれが生きているか分かりにくい状態です。
- Google ドライブ側にも、古い 09_Cursol があります。
- prisma のスキーマと本番の DB に、ずれが残っています（persona と cunning の 4 文）。
- エラーは、console.error を Slack に送る自前の仕組みで知らせています。原因の手がかりが少なく、2026-09-23 の通知は原因が分からないままです。
- 外からの死活監視はありません。

### やること

1. worktree とブランチの片付け
   - main に入った作業の worktree は、変更が残っていないことを確かめてから外します（`git worktree remove`）。
   - 古い統合ブランチ（integrate/agent-renewal、codex/doya-integrate-20260923 など）は、main に入っていることを確かめてから消します。
   - 片付けの一覧は、コマンドで作り、ユーザーが確かめてから消します。消すのはユーザーの承認のあとです。
2. Google ドライブ側の古い 09_Cursol
   - ~/Code/09_Cursol と中身を比べ、そちらにしか無いファイルが無いかを確かめます。
   - 無ければ、「旧」と分かる名前に変えて 1 か月置き、問題が無ければ消します（ユーザーの承認のあと）。
3. スキーマと本番 DB のずれ
   - persona と cunning の 4 文は、本番移行と同じ手順（classify-diff.cjs と apply-sql.cjs）で反映します。
   - 週に 1 回、読み取り専用で `prisma migrate diff` を本番に向けて流し、ずれがあれば Slack に知らせる仕組みを足します。
     読み取り専用の DB ユーザーを作って使います。
4. 本番のエラー通知
   - Sentry を入れます。例外のスタック、発生した画面、デプロイの版がまとまって残ります。
   - 送る内容から、個人情報と秘密の値を除く設定にします。
   - 無料枠（月 5,000 件ほど）で始め、足りなければ有料（月 26 ドル前後）に上げます。
5. 外形監視
   - トップ、ログイン画面、/api/health を、外から 5 分ごとに見る監視を入れます（Better Stack や UptimeRobot の無料枠）。
   - Vercel のボット判定で監視が止められないよう、/api/health だけを除外します（Vercel の設定変更が要る）。

### 費用・工数・リスク

| 項目 | 月額の目安 | 工数 | リスク |
|---|---|---|---|
| worktree とブランチの片付け | 0 円 | 0.5 日 | 未コミットの作業を消す事故。必ず一覧を見てから |
| Google ドライブの整理 | 0 円 | 0.3 日 | そちらにしか無いファイルの見落とし。比べてから |
| スキーマのずれの解消と週次の検知 | 0 円 | 1 日 | 本番の DDL。承認と手順書が要る |
| Sentry | 0 円から（有料は月 26 ドル前後） | 0.5〜1 日 | 個人情報の送り過ぎ。送る前に除く設定を必ず入れる |
| 外形監視 | 0 円（無料枠） | 0.3 日 | Vercel のボット判定の除外は、ユーザーの操作が要る |

## 7. 注意

- GitHub Actions の実行時間: 今の CI は 86 個の手順があり、1 回の実行が長めです。
  画面の比較を足すと、さらに増えます。非公開のリポジトリは、プランごとに月の無料の時間が決まっています。
  実行時間を Actions の画面で確かめ、足りなければ、画面の比較を「画面に関わるファイルが変わった PR だけ」に絞ります。
- 有料サービスの契約、Vercel・Supabase・GitHub・Google の設定変更は、どれもユーザーの承認のあとに行います。
- この計画で増えるのは、主に「確かめる仕組み」です。機能の挙動は変えません。
