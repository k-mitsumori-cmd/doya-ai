## 1. 概要

**アバターが自律的に商談を進行し、見込み客の質問にその場で答え、商談ログと"自社に合うかどうか"の判定を残す**AI商談ツール。

営業担当が同席しなくても、見込み客が公開URLを開くだけで商談が始まり、
「サービス説明 → ヒアリング → 質疑応答 → 適合判定 → 次アクション」までを AI が完結させる。

| 項目 | 内容 |
|---|---|
| サービスID | `aishodan` |
| パス | `/aishodan`（管理側） / `/m/{roomToken}`（見込み客が入る商談ルーム） |
| カテゴリ | realtime / sales |
| ステータス（初期） | `coming_soon` → Phase 1 完了後に `beta` |
| アイコン | `support_agent`（Material Symbols） |
| カラー | ブランド `#0066ff` |

### 解く課題

| 課題 | 現状 | AI商談での解決 |
|---|---|---|
| 商談の母数がスケールしない | 営業1人が1日に持てる商談は数件 | 24時間・同時並行で無制限に商談できる |
| 初回商談の質が人によってブレる | トークスクリプトが守られない・製品知識にばらつき | シナリオ通りに進行、回答は資料に基づく（ハルシネーション抑止） |
| 有望度の判断が属人的 | 「感触が良かった」で終わる | ヒアリング項目を構造化抽出し、ICPと突き合わせてスコア化 |
| 商談内容が資産にならない | 議事録が残らない・CRMに入らない | 全発話ログ＋要約＋抽出項目を保存し、SFA/HubSpotへ連携 |

### やらないこと（スコープ外・MVP）

- 契約締結・与信・決済の代行（AIは「次アクションの合意」まで。クロージングは人間）
- 電話（PSTN）発信、Zoom/Google Meet への bot 参加（Phase 3で検討）
- 日本語以外の言語
- 見込み客リストへのアウトバウンド送信機能（送るのは既存のドリップ／IG・LINE Harness の役割）

## 2. 登場人物と用語

| 用語 | 意味 |
|---|---|
| **ホスト** | 自社側。ドヤAIにログインし、商材登録・シナリオ設定・ログ閲覧を行う（＝課金ユーザー） |
| **ゲスト** | 見込み客。**ログイン不要**で商談ルームURLを開き、AIと商談する |
| **商材（Product）** | 売る対象。URL・資料からナレッジを構築した単位 |
| **シナリオ（Scenario）** | 商談の進め方の定義。フェーズ構成・ヒアリング項目・ICP・ガードレール |
| **ルーム（Room）** | 公開URLの発行単位。シナリオ＋有効期限＋トラッキング情報を持つ |
| **セッション（Session）** | ゲスト1人の1回の商談。ターン・質問・判定を紐づける親 |
| **ターン（Turn）** | 1発話。`speaker: 'ai' | 'guest'`、テキスト・音声・フェーズ・レイテンシを持つ |
| **スロット（Slot）** | ヒアリングで埋める構造化項目（課題／人数／予算／導入時期／決裁者 など） |
| **フィットスコア** | 抽出スロット × ICP定義 から算出する適合度（0-100）と判定理由 |

## 3. 体験フロー

### 3-1. ホスト側（準備・5分）

1. `/aishodan` で組織を作成（または既存組織を選択）
2. **商材を登録** — 自社サービスURLを入力 → 自動クロールで本文抽出／PDF・PPTX・資料テキストをアップロード
3. 抽出結果から AI が「商材プロフィール」を自動生成 → ホストが修正
   - 一言説明 / 提供価値 / 対象顧客（ICP）/ 料金 / よくある質問 / 競合との違い / **話してはいけないこと**
4. **シナリオを確認** — フェーズ構成とヒアリング項目のデフォルトが自動生成される。編集可
5. **ルームを発行** → 公開URLを取得。メール・LP・広告のリンク先に設置

### 3-2. ゲスト側（商談・10〜20分）

1. 公開URLを開く → 冒頭に**AIである旨と録音・記録の同意画面**（同意しないと開始不可）
2. 名前・会社名・メールを入力（任意項目はシナリオで設定可）
3. アバターが登場して商談開始
   - **オープニング** — 挨拶・所要時間の提示・進め方の合意
   - **ヒアリング** — 課題・体制・予算・時期・決裁を対話で聴取（スロットが埋まるまで深掘り）
   - **提案** — 聴取した課題に紐づけて、資料に基づく説明（該当スライド／図を画面に表示）
   - **質疑応答** — ゲストの質問にRAGで即答。資料に無いことは「確認して折り返す」
   - **クロージング** — 次アクションの提案（人間の担当者との商談 / 資料送付 / トライアル）
4. 終了 → お礼画面＋その場で日程調整（Phase 2）

### 3-3. ホスト側（商談後）

1. Slack に即時通知（誰が・どのくらい話し・フィットスコア何点・次アクション）
2. `/aishodan/sessions/{id}` で全文ログ・要約・スロット・未回答質問を確認
3. ワンクリックで **SFA（`/sfa`）へ取引先＋商談として登録** / HubSpotへ同期

## 4. 機能要件

### F1. ナレッジ取り込み

- **URL取り込み**: サイトURLを入力 → 同一ドメイン内を最大N頁クロールして本文抽出
  - 実装は既存 `src/lib/cunning/scraper.ts` / `src/lib/net/safe-fetch.ts` を再利用（**SSRF対策済み**：DNS解決後の全IP検証・リダイレクト各ホップ再検証）
- **ファイル取り込み**: PDF / PPTX / DOCX / TXT / Markdown。Supabase Storage に保存し本文抽出
- **手入力**: FAQ・想定問答を直接記入
- 取り込んだテキストは**チャンク化して検索インデックス化**（`src/lib/cunning/rag.ts:chunkText()` を再利用）
- 商材プロフィールの自動生成（LLM）→ ホストが編集して確定。**確定したプロフィールが回答の最上位の根拠**

### F2. シナリオ設定

- **フェーズ定義**（デフォルト5段階、追加・削除・並べ替え可）
  | # | フェーズ | AIの目的 | 次へ進む条件 |
  |---|---|---|---|
  | 1 | オープニング | 名乗り・所要時間合意・AIである旨の再確認 | ゲストが開始に同意 |
  | 2 | ヒアリング | 必須スロットを埋める | 必須スロットが全て埋まる or 上限ターン到達 |
  | 3 | 提案 | 課題に紐づけて価値を説明 | 主要な提案ポイントを説明済み |
  | 4 | 質疑応答 | 疑問・不安の解消 | ゲストの質問が尽きる or 上限到達 |
  | 5 | クロージング | 次アクションの合意 | 次アクションが確定 or 明確な辞退 |
- **ヒアリング項目（スロット）**: 項目名・型（自由文/選択/数値/日付）・必須か・質問文の例
  - デフォルトはBANT+課題（課題 / 現状の運用 / 人数規模 / 予算感 / 導入時期 / 決裁プロセス）
- **ICP定義**: 適合条件（業種・規模・課題キーワード・予算下限 等）と重み。フィットスコアの算出根拠
- **ガードレール**（重要）
  - 価格の断定可否（「概算のみ」「非開示」「表示価格を提示可」から選択）
  - 競合他社への言及ポリシー
  - **禁止トピック**（訴訟・人事・未発表機能 など）
  - 資料に無い質問への挙動（既定：**推測せず「確認して折り返す」**）
- **話し方**: 敬語レベル・一人称・テンポ・1発話の最大文字数

### F3. 商談ルーム（公開）

- ルーム発行でトークン付きURL `/m/{roomToken}` を生成
- 設定: 有効期限 / 同時セッション上限 / パスコード（任意） / 事前入力フォーム項目
- **ゲストは未ログイン**。セッションはCookieの `guestId` で識別（既存 `adbanner` の guestId パターンを踏襲）
- 流入計測: `?utm_*` / 参照元をセッションに記録

### F4. 対話エンジン（本サービスの中核）

**フェーズ・ステートマシン + LLM** のハイブリッド。LLMに丸投げすると商談が脱線し、進行が制御できないため。

各ターンの処理:
1. ゲスト発話を受信（音声 → STT、またはテキスト入力）
2. **意図分類**（既存 `src/lib/cunning/classify.ts` を拡張）— 質問 / 回答 / 反論 / 雑談 / 終了希望
3. **スロット抽出** — 発話から埋まった項目を構造化抽出して保存
4. **フェーズ判定** — 完了条件を満たせば次フェーズへ遷移
5. **応答生成** — 現フェーズの目的 + 商材プロフィール + RAG検索結果 + 直近履歴 を文脈にLLM生成
   - 出力は `{ speech, displayText, showAsset?, nextPhase?, endSession? }` の構造化JSON
6. 生成文をTTS → アバター発話（Phase 2以降）

- **モデル**: 低レイテンシ必須のため `gemini-2.0-flash`（`@seo/lib/gemini` ラッパー経由）優先 / `gpt-4o` フォールバック。要約・フィット判定はレイテンシ不要のため上位モデル可
- **割り込み対応**: ゲストが話し始めたらAI発話を停止（barge-in）
- **沈黙対応**: N秒無言でAIから促し。M回続けば終了処理

### F5. 質疑応答（RAG）

- 質問 → チャンク検索 → 上位K件を根拠にして回答生成
- MVPは**字句バイグラム類似**（`cunning/rag.ts` と同方式、pgvector不要・日本語に強い・低レイテンシ）
- Phase 2 で pgvector + embeddings へ差し替え（インターフェースを先に切っておく）
- **根拠が見つからない場合は回答を作らない**。「確認して折り返す」＋ `aishodan_question.unanswered=true` で記録 → ホストへ通知（＝FAQ拡充のネタになる）
- 回答には出典チャンクIDを保持し、ログ画面で「どの資料のどこを根拠にしたか」を表示

### F6. アバターと音声

- **入力（ゲスト）**: **音声とテキストの両対応**（確定事項）。商談画面に常時テキスト入力欄を置き、いつでも切り替えられる
  - 開始前にマイク疎通チェック。マイク不許可・デバイス無し・雑音過多を検知したら**テキストモードへ自動フォールバック**（「商談が始まらない」を最優先で防ぐ）
  - 音声入力: ブラウザ `getUserMedia` でマイク取得 → 数秒チャンクを `/api/aishodan/room/[token]/transcribe` にPOST
  - ⚠️ **Vercel Serverless は WebSocket の長時間保持ができない**（ドヤカンニングで実証済み）。ストリーミングSTT直結は不可のため near-realtime チャンク方式を採る
  - STT: `gpt-4o-transcribe`（`src/lib/cunning/transcribe.ts` を再利用。モデル起因エラー時 `whisper-1` 自動フォールバック済み）
  - 発話区切りは VAD（クライアント側の音量ベース）で検出
- **出力（AI音声）**: Google Cloud TTS。既存 `src/lib/voice/tts.ts` / `speakers.ts`（`ja-JP-Neural2-*` の5話者）をそのまま利用
- **アバター描画**: 方式は下表参照。**MVPは自前2D**、差し替え可能なインターフェース `AvatarDriver` を切る

| # | 方式 | レイテンシ | 追加コスト | 品質 | 採否 |
|---|---|---|---|---|---|
| A | **自前2D立ち絵 + 口パク同期**（gpt-image-2 生成の差分パーツをTTSのタイムポイントで切替） | 最速（TTS到着即） | ほぼゼロ | 「動く立ち絵」レベル | **MVP採用** |
| B | 外部リアルタイムアバターSDK（HeyGen Interactive / D-ID / Tavus 等、WebRTC） | 1秒前後 | **従量課金が重い**（分単位・概算 数百円/商談・要実測） | 実写級 | Phase 3で差し替え検討 |
| C | 3D VRM + Three.js（`~/Code/tools/doya-ai-office` に Three.js の知見あり） | 速い | ゼロ | アニメ調3D | Bの代替候補 |
| D | 事前レンダリング動画生成API | 数秒〜数十秒 | 中 | 高い | **不採用**（リアルタイム商談に致命的） |

> 判断根拠: 本サービスの難所は「商談を破綻なく進行させるAI」であってアバターの見た目ではない。
> 最初に高額な外部SDKへ依存すると、コスト構造（¥9,980の統一プランに乗らない）と
> Vercel での WebRTC 中継という二重の難題を、価値検証の前に背負うことになる。

### F7. 適合判定（フィットスコア）

- 商談終了時に算出: 抽出スロット × ICP定義の重み付け → 0-100
- 出力: スコア / 判定（`hot` / `warm` / `cold` / `不適合`） / **判定理由の日本語説明** / 推奨アクション
- 「自社に合うのか」はゲスト側にも価値がある → 終了画面に**ゲスト向けの適合サマリ**を表示（オプション）
- ⚠️ スコアは参考値。ホストが手動で上書きでき、上書きは学習材料として記録

### F8. ログと活用

セッションごとに保存するもの:

- 全ターンの発話ログ（テキスト＋任意で音声）
- AI要約（3行サマリ / 課題 / 提案内容 / 反論 / 次アクション）
- 抽出スロット一覧
- 質問一覧（回答済み / **未回答**、出典付き）
- フィットスコアと理由
- 所要時間・離脱フェーズ・レイテンシ統計

活用先:

| 連携先 | 内容 | 時期 |
|---|---|---|
| Slack | 商談終了の即時通知（`src/lib/notifications.ts` 再利用） | Phase 1 |
| CSV / Markdown | ログのエクスポート | Phase 1 |
| **ドヤ営業管理（`/sfa`）** | 取引先＋商談レコードとして登録 | Phase 2 |
| HubSpot | コンタクト作成・同期（既存 `hubspot-sync` cron の仕組みを流用） | Phase 2 |

| ドヤ商談準備（`/shodan`） | 相手企業の事前調査結果をAIの文脈に注入 | Phase 2 |

### F9. ホスト向けダッシュボード

- 商談件数 / 完了率 / 平均所要時間 / フィット分布 / 離脱フェーズ分布
- **未回答質問ランキング**（＝ナレッジ強化の優先順位）
- 反論の頻出パターン

## 5. 非機能要件

| 項目 | 目標 |
|---|---|
| 応答レイテンシ | ゲスト発話終了 → AI発話開始 **2.0秒以内**（内訳: STT 0.8s / 生成 0.8s / TTS 0.4s） |

```
aishodan_slot_value     抽出値（sessionId, key, value, confidence, sourceTurnId）
aishodan_outcome        結果（sessionId, fitScore, verdict, reason, summary Json,
                              nextAction, overriddenBy, exportedToSfaAt）
```

- 全ての `[id]` 系APIは `findFirst({ where: { id, organizationId } })` の**二重条件**必須（IDOR防止）
- ⚠️ ゲスト向けAPI（`/api/aishodan/room/*`）だけは**未認証で叩ける**。`roomToken` と `guestId` でスコープし、
  組織データが漏れないよう**返却フィールドをホワイトリスト**する（本サービス最大のセキュリティ論点）
- ⚠️ モデル追加後は `npx prisma generate` ＋ **本番は手動 db push**（Vercelビルドは設計上スキップ。怠ると当該テーブルの全クエリが500）

## 10. コンプライアンス（このサービス特有・必須）

商談相手が**第三者（見込み客）**である点が、他サービスと決定的に違う。

1. **AIであることの明示** — 冒頭で必ず告知。人間になりすまさない。問われたら常に肯定する
2. **記録の同意** — 商談開始前に、発話の記録・AI処理・保存期間を提示し**明示同意**を取得（同意ログを保存）
3. **音声保存の既定はOFF** — テキストのみ保存を既定とし、音声保存はホストが明示的に有効化
4. **個人情報** — 取得項目を最小化。プライバシーポリシー・削除請求の導線をルーム画面に配置
5. **不当表示の防止** — 効果の断定・優良誤認を避ける。**資料に無いことは言わせない**（F5の設計がそのまま統制になる）
6. **価格・契約** — AIの発言は「参考情報」である旨をUIに常時表示。契約締結行為は行わない
7. **不適切発話への対処** — ゲストからの攻撃的・不適切発話を検知したら丁寧に終了し、ホストへ通知

### Phase 1 の内部ビルド順（重要）

Phase 1 は音声＋アバター込みで完成させるが、**作る順番**は下記で固定する。
このサービスの成否は「AIが商談を進行しきれるか」で決まり、音声とアバターは
進行が破綻したままだと**破綻を高価に演出するだけ**になるため。

1. **商材取り込み → シナリオ → 進行ステートマシン → RAG** を、**テキストのデバッグモード**（`/aishodan/preview`）で完成させる
   - ここは1ターンの検証が数秒で回るため、シナリオ品質を最速で追い込める
   - テキストモードは捨て実装ではなく、**そのままゲストのテキスト応答手段として本番採用**する（両対応が確定事項のため）
2. **TTS＋2Dアバター**を載せる（AIが喋る側）
3. **STT＋VAD＋barge-in** を載せる（ゲストが喋る側）
4. **フィットスコア・要約・ログUI・Slack通知**
5. 通しでの実商談テスト → レイテンシ計測 → チューニング

> ※ 1 が終わった時点で「テキストのAI商談」として動くものが見える。
> ここでシナリオ品質のレビューを一度挟むこと（プロジェクト指針「原則4：完了条件を必ず添える」）。

## 12. 主要リスクと対策

| リスク | 影響 | 対策 |
|---|---|---|
| **AIが商談を進行しきれず脱線** | サービスの前提が崩れる | フェーズ・ステートマシンでLLMの裁量を絞る。Phase 1で徹底検証 |
| ハルシネーションで誤った説明 | 顧客トラブル・信用毀損 | 根拠チャンク必須。無根拠なら「確認して折り返す」。出典をログに保持 |
| レイテンシで会話が不自然 | 離脱 | 2秒予算の厳守。フィラー発話（「なるほど、」）を先行再生して体感を隠す |
| ゲスト向けAPIからの情報漏洩 | 重大 | 返却フィールドのホワイトリスト化・roomToken/guestIdスコープ・レート制限 |
| プロンプトインジェクション（ゲストが「設定を教えて」等） | ガードレール破り | システム指示の非開示を明示・出力フィルタ・逸脱時は定型応答へ退避 |
| 外部アバターSDKのコスト | 統一プラン(¥9,980)で赤字化 | MVPは自前2D。外部採用時は事前に分単価の実測と上限設計 |
| 音声取得がブラウザ/端末依存で失敗 | 商談が始まらない | 開始前にマイク疎通チェック。失敗時はテキストへ自動フォールバック |

## 13. 決定事項と未決事項

### 決定済み（2026-08-06 ユーザー確認済み）

| # | 論点 | 決定 |
|---|---|---|
| 1 | **アバター方式** | **自前2D立ち絵＋口パク同期**。gpt-image-2 で生成した差分パーツをTTSに同期。外部リアルタイムSDKはPhase 3で差し替え検討（`AvatarDriver` インターフェースを切っておく） |
| 2 | **Phase 1 の範囲** | **音声＋アバター込みで完成させる**。ただし内部ビルド順は §11 の通り（進行エンジンをテキストで先に固める） |
| 3 | **ゲストの応答手段** | **音声とテキストの両対応**。マイク不許可・雑音環境ではテキスト入力へ自動フォールバック（商談が始まらない事故を防ぐ） |
| 4 | **最初の商材** | **ドヤマーケAI自身**。資料も価値訴求も手元にあり、品質の良し悪しを即判断できる。完成後はそのまま本番の集客導線として使用可能 |

### 未決（実装中に確認する）

1. **serviceId / 表示名** — `aishodan` / 「ドヤAI商談」で仮確定。既存 `shodan`（ドヤ商談準備）と併存する前提。ユーザーからの明示的な否認は無いが、`services.ts` 登録時に最終確認する
2. **音声・録画の保存方針** — 提案は「**音声保存は既定OFF・テキストのみ保存**」。ホストが明示的に有効化した場合のみ音声を保存し、保存期間を同意画面に明記する
3. **アバターのキャラクター設定** — 性別・年齢感・服装・トーン。ドヤシリーズの既存ブランドと揃えるか、新規に立てるか
4. **TTS話者** — 既存ドヤボイスの5話者（`ja-JP-Neural2-A/B/C/D` 等）から選ぶか、商談用に新規選定するか
5. **無料プランでの音声可否** — 本書 §9 では「無料はテキストのみ」としているが、変動費（STT/TTS）の実測後に再検討
