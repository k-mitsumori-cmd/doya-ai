# ドヤバナーAI テンプレート画像 刷新 依頼書

> 宛先: Codex（画像生成の実作業を担当）
> 目的: ギャラリー最初の画面に出る見本の質を上げ、既存画像は後段へ下げる
> 形式: 画像1枚ずつの指示ではなく、**ジャンル単位**の依頼。細部はCodex側の判断でよい

---

| 項目 | 実測 |
|---|---|

## 1. 成果物

### 1-1. 新規バナー画像

**15ジャンル × 各10枚 = 合計150枚**（§3のジャンル表を参照）

- サイズ: **1200x628**（必須。ギャラリーの標準）
- 形式: **WebP**（品質85前後）。PNG入稿も可だが最終はWebPに変換する
- 文字: **日本語コピーを画像に焼き込む**（実運用のバナーは文字込みで成立するため）
- 命名: `{genre-slug}-{連番2桁}.webp`（例 `beauty-cosme-01.webp`）

### 1-2. 参考画像の収集記録

各ジャンルにつき**最低8枚**の参考バナーを実サイトから収集し、記録すること（§2）。

### 1-3. メタデータ

`metadata.json` を1本。DBの `banner_template` にそのまま流し込める形にする。

```json
[
  {
    "templateId": "beauty-cosme-01",
    "industry": "美容・コスメ",
    "category": "beauty",
    "size": "1200x628",
    "prompt": "実際に画像生成へ渡したプロンプト全文",
    "file": "beauty-cosme-01.webp",
    "referenceUrls": ["https://design-library.jp/...", "..."],
    "copy": { "headline": "焼き込んだ見出し", "sub": "サブコピー", "cta": "CTAの文言" }
  }
]
```

`templateId` は既存と重複しないこと（既存は `seo-article-guide-1` のような形式）。

## 2. 参考の集め方（**ここが最重要**）

### 2-1. 必ず実在のバナーを見てから作る

**プロンプトを想像で書かない。** 日本で実際に配信されたバナーを見て、そこにある構図・余白・文字量・色数の作法を写し取ること。日本のバナーは欧米のものと文字量も密度も違うため、海外のデザイン参考だけで作ると「日本のバナーに見えない」ものができる。

### 2-2. 参照先（すべて到達確認済み・2026-08-22）

**主参照:**

- **BANNER LIBRARY** — https://design-library.jp/
  実配信された高品質バナーを厳選収録。**業種・色・サイズ・テイスト（かわいい/スタイリッシュ等）・デザイン要素（人物あり/イラスト/手書き文字）で絞り込める**ので、ジャンル別の収集に最も適している。ここを軸にする。

**補助参照:**

- **バナー広場** — https://banner-hiroba.com/
- **Bannnner.com** — https://bannnner.com/ （国内で実運用された広告・キャンペーンバナー）
- **BANNER DESIGN ARCHIVE** — http://banner.keizine.net/
- **SANKOU!** — https://sankoudesign.com/ （Webデザイン寄り。世界観の参考に）
- **retrobanner** — https://retrobanner.net/ （日本のバナーを1日4件更新。※自動取得は403になるためブラウザで閲覧すること）

### 2-3. 収集の手順

1. ジャンルごとに BANNER LIBRARY の業種/テイスト絞り込みで**最低8枚**を選ぶ
2. 各参考について次を記録する
   - 出典URL
   - 構図（写真の位置、文字の置き方、余白の取り方）
   - 文字量（見出し何文字／サブ何文字／CTAの有無）
   - 配色（主色・強調色の2〜3色）
3. 8枚から**共通する型**を2〜3パターン抽出し、それを土台に10枚を作る
   （10枚が全部同じ構図にならないよう、型を散らす）

### 2-4. やってはいけないこと

- **既存のドヤバナーAI画像を参考にしない。** 今回はその質を上げるための刷新なので、既存を見ると同じ水準に引っ張られる
- 参考バナーの**模写・トレース・ロゴや商品名の流用をしない**。参考にするのは構図・配色・文字量の作法まで
- 実在企業名・実在ブランドロゴを画像に入れない（架空の名称を使う）
- 人物写真は**東アジア系（日本人・韓国系）の顔**にすること（欧米人モデルにしない）

## 4. 品質基準

作ったものが「使える見本」になっているかの判定基準。

- [ ] **1200x628 に収まって文字が読める**（縮小してサムネイル表示されるので、細い文字は破綻する）
- [ ] 日本語が**正しく表示されている**（文字化け・意味不明な字形がない）
- [ ] 見出しは**15文字前後まで**、サブは25文字前後まで（日本のバナーの実測レンジ）
- [ ] 色数は**主色＋強調色の2〜3色**に収める
- [ ] CTAがある場合は**ボタンとして認識できる**形にする
- [ ] 実在の企業名・ブランド・ロゴが写り込んでいない
- [ ] 人物は東アジア系の顔
- [ ] 10枚が並んだとき**同じ構図の繰り返しに見えない**

## 5. 納品と反映

### 5-1. 納品

1. `images/` に150枚のWebP
2. `metadata.json`（§1-3の形式）
3. `references.md`（ジャンルごとの参考URL一覧と、抽出した型のメモ）

### 5-2. 反映（実装側の作業・Codexは不要）

**重要: 新規画像はDBにbase64で入れない。**

既存348件は `imageUrl` にbase64データURIが入っており、**それだけでDBが608MBある**。表示のたびに Postgres から平均1.79MBの文字列を読み、サーバ側で毎回リサイズしている。新規分を同じ方式で入れると、この負債がそのまま倍増する。

新規分は次の形にする。

1. 画像は **Supabase Storage** に置く
2. `banner_template.imageUrl` には**そのURL**を入れる（データURIではなく `https://...`）
3. サムネイル（w=300 / w=600 / w=1280 のWebP）は**投入時に生成して一緒に置く**
   → 実行時の sharp 処理が不要になり、CDNが直接返せる

## 6. 表示順序をどう変えるか（実装側）

「新しい画像を前に、既存を『もっと見る』の後ろへ」は、**スキーマ変更なしで実現できる**。

現在のAPI（`src/app/api/banner/test/templates/route.ts`）は

```ts
orderBy: { isFeatured: 'desc' }
```

だけで並べている。そして `isFeatured=true` の行は**現在0件**。つまりこのフラグは丸ごと空いている。

- 新規150件を `isFeatured: true` で投入する → 自動的に全て先頭に来る
- 既存348件は `isFeatured: false` のまま → 後段（「もっと見る」の先）に回る

より細かい序列（新規の中での並び順）まで制御したい場合のみ、`sortOrder Int @default(0)` を追加して
`orderBy: [{ sortOrder: 'desc' }, { isFeatured: 'desc' }, { updatedAt: 'desc' }]` にする。
その場合は**本番DBへの手動 db push が必要**（Vercelビルドは db push をスキップする設計。`skills/doya-db-push` を参照）。

## 7. 表示スピードについて（実装側・実測で訂正済み）

**本番で実測した結果、当初の見立ては誤っていた。** 記録として経緯も残す。

### 7-1. 実測値（2026-08-22）

| 対象 | 実測 |
|---|---|
| サムネイル1枚（`w=300&fmt=webp`・CDNヒット） | 0.34〜0.72秒 / 3〜20KB |
| サムネイル1枚（CDN未ヒット＝DB読み+sharp変換） | **0.54秒** |
| **テンプレート一覧API（初回）** | **17〜22秒** |
| テンプレート一覧API（2回目以降） | 0.09秒 |

つまり画像パイプラインは問題なかった。**律速は一覧APIの初回22秒**で、その間ギャラリーは空のまま。画像リクエストはそれが返るまで始まりもしない。

### 7-2. 原因

一覧APIのクエリに、こういう条件が入っていた。

```ts
NOT: { imageUrl: { contains: 'placehold.co' } }
```

`imageUrl` には base64 データURI（平均1.79MB・全348件で608MB）が入っている。
`LIKE '%placehold.co%'` を書くと Postgres は TOAST を全件展開して608MBを走査する。

しかも **`placehold.co` を含む行は0件**で、この条件は1件も除外していなかった。

実測での切り分け:

| クエリ | 実測 |
|---|---|
| `count`（この条件あり） | **21,849ms** |
| `count`（この条件なし） | **590ms** |
| `findMany`（条件あり・30件） | 2,662ms |
| `findMany`（条件なし・30件） | 370ms |

`count` は LIMIT が効かないため全行を走査せざるを得ず、影響が最大だった。

### 7-3. 対応済み

この条件を2箇所とも撤去した（`src/app/api/banner/test/templates/route.ts`）。
プレースホルダー画像は配信側（`/api/banner/test/image/[templateId]`）がフォールバックで処理するので、
除外条件そのものが不要だった。

**今後の禁止事項: `imageUrl` に `contains` / `startsWith` / `endsWith` を書かないこと。**
巨大なbase64列に対する部分一致は、必ず全件展開を引き起こす。

### 7-4. それでも画像をDBから出す価値はある（§5-2）

一覧APIが直ったので体感速度の問題は解消するが、次の点は残る。

- DBが608MB膨らんでおり、バックアップ・復元・マイグレーションが重い
- CDN未ヒット時は毎回 Postgres から1.79MBを読んで sharp で変換している（0.54秒）
- 上記のような「巨大列を踏む事故」が今後も起きうる

新規150枚は Supabase Storage に置く方針を維持する。既存348件の移行は別タスクとする。

## 8. 進め方

1. Codex がジャンル1つ分（10枚）を先に作る → 三森さんが見て方向性を確認
2. OKが出たら残り14ジャンルを進める
3. 全150枚が揃ったら実装側が Storage 投入＋`isFeatured` 付与で反映
4. 反映後、ギャラリー最初の4枚が新規に入れ替わっていることを確認

最初の1ジャンルは **「1. 美容・コスメ」** を推奨（参考が最も集めやすく、良し悪しの判断もつけやすいため）。
