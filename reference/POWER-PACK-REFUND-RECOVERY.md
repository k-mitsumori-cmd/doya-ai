# 追加購入の返金と復旧

この文書は修正候補の運用手順です。本番へのスキーマ適用・この候補の公開は未実施です。

## 守る条件

- `power_pack_purchases` は会社に結ぶ現金記録です。ポイント口座がなくても保存します。`amount` は元のポイント数、`cancelTarget` は取り消すポイント数、`cashAmount` と `cashRefunded` はJPYです。
- 決済IDは会社・元のポイント数・支払金額・PaymentIntentに固定します。別会社の購入として再利用しません。
- 累計返金額と取消目標は減らしません。古い通知や再確認が全額返金を一部返金へ戻すことはありません。
- Webhookの成功応答は、確認済みの現金事実を永続化した後に返します。保存失敗は失敗受領として再送に備えます。
- 付与前の返金、台帳停止中の返金も記録します。残高・消費・付与・失敗ジョブの返却は取消目標を照合します。無関係な付与から取り立てません。
- 購入の再確認はPaymentIntentの最新Chargeも読み、返金通知が未受信でも返金分を付与しません。Charge未取得や通信失敗は再試行できる失敗です。
- 全額・一部返金や反映済み購入には、新規購入の完了ポップアップを出しません。確認結果に沿う文面を表示します。

## 返金状態の通知

- `charge.refunded` は購入ポイントの取消を照合します。`refund.created`・`refund.updated`・`refund.failed` では、追加購入に結び付く `failed`・`canceled`・`requires_action` を運営の対応対象にします。
- 状態通知は既存の `StripeWebhookNotification` へ保存してから受信を完了します。送信失敗はpendingに戻し、既存の再送処理に引き継ぎます。保存失敗・Stripe読取失敗はWebhookを失敗扱いにして再送を受けます。
- 状態通知そのものは現金記録・ポイントを変更しません。失敗やキャンセルを理由に、自動でポイントを戻したり、別の返金を実行したりしません。運営がStripeで元の返金を確認して対応を判断します。
- `amount_refunded` の記録と、受取銀行側の返金完了は分けます。購入確認は「返金処理が記録されている」と案内し、銀行側の完了を保証しません。
- 公開後に購読が必要な追加イベントは `charge.refunded`・`refund.created`・`refund.updated`・`refund.failed` です。既存の契約・請求イベントは維持します。2026-11-06の本番読取ではこの4イベントは未購読でした。案件ノートでは変更は本人操作です。購読変更と実イベント配送は未検証です。

## スキーマと公開の順序

1. 最新mainとの差分、対象プロジェクト、既存変更、実際の本番スキーマを再確認します。候補を組み込んだ型検査・全回帰・ビルドを合格させます。
2. `prisma/migrations-refund-v3.sql` を1文ずつ確認します。追加テーブル・制約・索引と、新しい購入記録表のRLSだけを適用します。新しい表の作成・RLS・クライアント権限の取り消しは同じトランザクションで確定し、無保護の表を途中公開しません。`CREATE INDEX CONCURRENTLY` はそのCOMMIT後、トランザクション外で実行します。`prisma db push` で本番全体を同期しません。
3. 会社の外部キー・sourceKeyの一意性・CHECK制約・索引の有効性・RLSを検査します。購入記録にはクライアント向けの読書きポリシーを作らず、認証済みのサーバー処理だけが扱います。既存付与の件数・量・残高が移行だけで変化していないことを確認します。
4. 現金記録を読める候補を公開します。対象SHAと配信先を確認し、読み取り検証とエラーログを検査します。実際の決済や返金を検証する場合は、合成検証と分けて対象・金額を確定します。
5. 既存の処理失敗通知・Webhook受領記録を確認します。保存済み購入で付与が未実施のものは、元の購入IDと会社IDを指定し、管理者認証済みの `POST /api/admin/doya-power/purchase/replay` に `{sessionId, companyId, apply: true}` を送って復旧します。同じfulfill処理を使い、会社・明細・金額・最新返金額を再検証します。同じ決済IDで再実行しても二重に付けません。手動でgrantやremainingを書き換えません。自動一括再照合と本番バックフィルは未実施です。

## ロールバックの制約

現金記録を読まない旧版では、返金済みのポイントが使えてしまいます。旧版を動かしている間は、V3に戻した後で精算できることだけでは安全になりません。

- ロールバック先も現金記録・取消照合・refund_attention通知型と返金状態イベントに対応した版を選び、SHAを公開前に固定します。対応版がない場合は任意の旧版へ戻さず、互換修正を行います。
- 台帳の旗をoffにするだけで、現金記録を読まない旧版が安全になるとは扱いません。再開前に保存済みの返金を照合します。
- テーブルや取消記録は削除しません。取り消したポイントを正数の補償付与で復元しません。
- 現時点で互換ロールバック先の本番受入・自動一括復旧の全経路・歴史データのバックフィルは未完了です。この候補の局所テスト合格を、運用全体の完了とは扱いません。

## 検証の境界

実PostgreSQLでは付与/取消/返却の順序・競合・障害時の原子性を検証しています。HTTP検証では全Webhookモジュール、確認API、Prismaの現金/ポイント/受領記録を接続しています。認証・Stripe応答・通知は合成です。実決済・実返金やNextアプリ全体の公開経路を実行した証拠ではありません。
